26.2 Four-Layer Auth ¶

The platform's defense in depth for tenant isolation runs through four layers. Each is necessary; none is sufficient on its own.

Layer 1: Identity (who are you?)
  Supabase Auth + OAuth providers
  │
  ▼
Layer 2: Tenant context (which tenant?)
  Middleware resolves tenant from host header
  Validates user has a public.users row in this tenant
  Produces a TenantContext (§5.4.2) with source = http_request
  │
  ▼
Layer 3: Authorization (what can you do?)
  assertPermission() at handler entry
  Returns enriched ctx with role + resource access decisions
  │
  ▼
Layer 4: Data access scoping (which rows can you touch?)
  tenantClient(ctx) wraps the DB client (§5.4.3)
  All queries against tenant-scoped tables auto-filtered by tenant_id
  RLS policies (§5.1) backstop the application-layer scoping

Each layer's purpose:

  • Layer 1 answers "is this request from a real authenticated user?" — handled by Supabase Auth and the OAuth providers.
  • Layer 2 answers "which tenant is this request operating inside?" — handled by middleware that resolves the tenant from the request's host header (subdomain or custom domain per §1.4) and validates the user has membership.
  • Layer 3 answers "is this user allowed to do this action on this resource?" — handled by assertPermission() at handler entry.
  • Layer 4 answers "for queries this handler issues, can the database actually return cross-tenant data?" — handled by the tenantClient wrapper AND by RLS policies. Two independent defenses; either alone is insufficient.

Layers 1–3 are application-layer checks. Layer 4 is the boundary between application and database. Layers 2 and 3 produce the TenantContext that Layer 4 consumes — the type system threads context through the call chain so it cannot be lost.

For non-HTTP contexts (Inngest jobs, webhook handlers), Layers 1 and 2 are replaced by the appropriate TenantContext factory per §5.4.5. Layer 4 is identical regardless of context source — the same tenantClient(ctx) wrapper applies.

26.3 Authorization Pattern ¶

Every protected HTTP handler entry calls assertPermission() to produce a TenantContext (§5.4.2) plus role/resource access decisions. The handler then uses the returned ctx to construct a scoped database client via tenantClient(ctx) (§5.4.3).

// Every protected handler entry:
export async function POST(req: Request) {
  const { ctx, user, permissions } = await assertPermission(req, {
    resource: 'booking',
    action: 'modify',
    resourceId: bookingId,
  });
  const db = tenantClient(ctx);
  // ...handler body, using db for all queries...
}

Inside assertPermission()

  1. Decode JWT → auth.users.id.
  2. Resolve tenant from request host per §1.4 → tenant_id.
  3. Verify the user has a public.users row for this tenant with status = 'active'. If not, throw 403.
  4. For write actions, verify tenant_is_active(tenant_id) — see §5.1's policy convention. A user can read their data from a suspended tenant; they cannot write. If write requested against a non-active tenant, throw 403 with a structured error (tenant_suspended, tenant_terminated, etc.) so the client UI can render the right message.
  5. Check role permissions per the role matrix and resource-specific rules.
  6. Construct a TenantContext via tenantContextFromRequest() (§5.4.5). The context records source = http_request, user_id.
  7. Return { ctx, user, permissions } or throw 403.

Returned context shape

type AssertPermissionResult = {
  ctx: TenantContext;           // For tenantClient(ctx)
  user: { id: string; email: string; roles: string[] };
  permissions: { allowed: true; expires_at: Date }; // Time-bounded for sensitive ops per §17.7
};

Sensitive-action re-auth

Per §17.7, certain operations (commission overrides, role changes, ICA acceptance) require re-auth within 4 hours of the action. The assertPermission() function checks the JWT's auth_time claim against the action's sensitivity classification. Failing the freshness check throws a structured 401 with a re-auth challenge.

26.3a Service-Role Discipline ¶

The Supabase service role bypasses RLS. It is the most powerful credential in the platform. Its use is restricted by both convention and lint enforcement.

26.3a.1 The four authorized service-role contexts ¶

Service-role usage is permitted only in these four contexts. Code in any other location that imports createServiceRoleClient is a CI failure.

ContextWrapperTenant scoping
tenantClient(ctx) per §5.4.3Yes — automatic .eq('tenant_id', …) injectionTenant-scoped
platformAdminClient() per §5.4.1No wrapper; raw accessNone — cross-tenant by design
Database migrations (supabase db push)Run via dedicated migration role per CI/CD §5N/A — DDL only
Backup/restore toolingRun from operator workstation; not from application codeN/A — out-of-band

26.3a.2 The forbidden patterns ¶

Each of these is a hard CI failure:

  • createServiceRoleClient() called outside src/lib/db/tenant-client.ts or src/lib/db/platform-admin-client.ts.
  • Importing SUPABASE_SERVICE_ROLE_KEY directly into application code (the env var is read once, in the client factories, never re-read elsewhere).
  • A tenantClient constructed from anything other than one of the four TenantContext factories in §5.4.5.
  • A function signature accepting tenant_id: string and constructing database queries from it — instead it must accept ctx: TenantContext and use tenantClient(ctx).

26.3a.3 The exception: platformAdminClient ¶

platformAdminClient exists because some operations legitimately cross tenant boundaries — the global RAG promotion queue, platform-wide abuse-monitoring rollups, tenant-listing for platform admin dashboards. These call sites:

  • MUST be named with platformAdmin* prefixes so they're searchable.
  • MUST be wrapped in assertPlatformAdmin(req) (the platform-admin variant of assertPermission) before the client is constructed.
  • MUST audit at the JOB level (one audit_log row per function invocation), not per query.

The set of platformAdminClient call sites is small (target: under 20 across the whole codebase) and reviewed quarterly per §26.11.

Per-job audit pattern

A platform-admin operation is one function from entry to exit. One audit row is written for each such operation, capturing what the operation did across all its queries. The row is constructed at the function's entry point with a reason and a correlation_id, and is committed at the function's exit with the accumulated query summary filled in.

The pattern is enforced by wrapping platformAdminClient() calls in a single utility: withPlatformAdminAudit(reason, fn). The utility manages the audit row's lifecycle so handler code cannot construct a platformAdminClient without going through it. See §5.4.8 for the utility definition.

// Platform-admin handler — the only correct shape
export async function GET(req: Request) {
  const admin = await assertPlatformAdmin(req);

  const result = await withPlatformAdminAudit(
    {
      admin_user_id: admin.user_id,
      reason: 'tenant_listing_for_admin_dashboard',
      operation: 'platformAdminListTenants',
    },
    async (db, recordQuery) => {
      // db is platformAdminClient
      // recordQuery is a callback to log a query summary into the audit row

      const tenants = await db.from('tenants').select('id, display_name, status');
      recordQuery({
        op: 'select',
        table: 'tenants',
        columns: ['id', 'display_name', 'status'],
        row_count: tenants.data?.length ?? 0,
      });

      return tenants.data;
    },
  );

  return Response.json(result);
}

What the audit row looks like

The audit_log row written by withPlatformAdminAudit:

{
  "id": "uuid-of-the-audit-row",
  "tenant_id": null,                // platform-admin operations are not tenant-scoped
  "actor_user_id": "uuid-of-admin",
  "actor_type": "admin",
  "action": "platformAdmin.tenant_listing_for_admin_dashboard",
  "resource_type": "platform_admin_operation",
  "resource_id": null,
  "changes": {                       // accumulated query summary
    "correlation_id": "01H...ULID",  // tracks all queries in this job
    "operation": "platformAdminListTenants",
    "reason": "tenant_listing_for_admin_dashboard",
    "reason_detail": null,           // populated only when reason = 'manual_emergency_intervention'
    "outcome": "success",            // or "error_thrown"
    "duration_ms": 47,
    "queries": [
      {
        "op": "select",
        "table": "tenants",
        "columns": ["id", "display_name", "status"],
        "row_count": 12
      }
    ],
    "error_message": null            // populated on failure
  },
  "context": {
    "ip": "10.0.0.5",
    "user_agent": "...",
    "request_id": "..."              // links to access logs
  },
  "occurred_at": "2026-05-17T14:23:11.000Z"
}

Failure path

If the wrapped function throws, the audit row is STILL written, with outcome = "error_thrown", the error message captured, and any queries that had completed before the throw recorded. This means a failed platform-admin operation is auditable — partial work is documented rather than invisible.

The audit row write is non-transactional with respect to the wrapped function's queries. The audit row commits even if the wrapped function's database work was rolled back. This is deliberate: we want the audit record of an attempted action regardless of whether the action succeeded.

What "one job" means

One withPlatformAdminAudit invocation = one job = one audit row. Concretely:

  • One HTTP request that hits a platformAdmin* handler → one job.
  • One Inngest function execution that uses platformAdminClient → one job per execution (Inngest retries produce separate jobs, each with its own audit row).
  • A nested call where one platformAdmin* function calls another: the OUTER withPlatformAdminAudit is the job; the inner call uses the same client and reports queries into the same audit row. Nesting is detected by the utility and short-circuits to a no-op so we don't produce two rows for one logical job.

Forensic queries against this audit shape

The trade-off vs per-query-batch audit: investigations now need to read JSONB rather than filter rows by timestamp. The queries that matter remain answerable, but with a different query shape:

-- "What did admin X do across the last 30 days?"
SELECT
  occurred_at,
  action,
  changes->>'reason' AS reason,
  changes->>'outcome' AS outcome,
  jsonb_array_length(changes->'queries') AS query_count
FROM public.audit_log
WHERE actor_user_id = '<admin_uuid>'
  AND actor_type = 'admin'
  AND occurred_at > NOW() - INTERVAL '30 days'
ORDER BY occurred_at DESC;

-- "Did any platform-admin operation touch the `bookings` table?"
SELECT id, occurred_at, actor_user_id, changes->>'reason' AS reason
FROM public.audit_log
WHERE actor_type = 'admin'
  AND changes @> '{"queries": [{"table": "bookings"}]}'::jsonb
ORDER BY occurred_at DESC;

The second query uses a JSONB containment check; it benefits from a partial GIN index on audit_log.changes scoped to admin rows only:

CREATE INDEX audit_log_changes_admin_gin_idx ON public.audit_log
USING GIN (changes jsonb_path_ops)
WHERE actor_type = 'admin';

The index is partial — it only covers rows where actor_type = 'admin'. This is the only actor_type whose changes JSONB needs JSONB-shape querying; user-action audit rows (actor_type = 'user') are queried by actor_user_id and timestamp, which are covered by existing indexes (per §26.5).

GIN indexes impose write cost. A partial index limits that cost to the low-volume admin-row write path. User-action writes (which dominate audit-log throughput) pay nothing.

If a future need arises to JSONB-query changes for non-admin rows (e.g., an investigation into a specific booking lifecycle through its changes->'before' and changes->'after'), add a second partial index scoped to that actor_type rather than promoting this one to a full index. The user-action path's write performance is a hot path and small percentages matter.

26.3a.4 Inngest jobs and webhook handlers ¶

Inngest jobs and webhook handlers run without a user JWT, so they cannot use userClient. They MUST use tenantClient with a TenantContext constructed via the appropriate factory:

  • Inngest jobs: tenantContextFromInngestEvent(event). The event's payload MUST contain a tenant_id. Jobs that genuinely cross tenants (e.g., the daily promo-state-transition cron) iterate tenants explicitly and construct a fresh TenantContext per tenant, rather than using platformAdminClient to update across tenants in one query.
  • Webhooks: tenantContextFromStripeEvent(event) for Stripe, similar factories for Resend and Gmail. Each factory validates that the webhook payload corresponds to a known tenant before constructing the context.

26.3a.5 Calls Worth Flagging ¶

  • The discipline only works if the lint rule is enforced. A warning that engineers can override is not a discipline; it's a suggestion. The CI gate must be hard (red = no merge), with override requiring a documented exception in MEMORY.md.
  • Inngest events must carry tenant_id. This is a design constraint on every Inngest event definition. Event types without tenant_id are platform-admin events and use platformAdminClient explicitly.
  • platformAdminClient call sites are the highest-value review target. Anything that crosses tenants is anything that can leak data. Quarterly review of the set per §26.11 isn't paperwork — it's the audit point.
  • Per-job audit trades granularity for cost. The pattern in §26.3a.3 writes one audit row per platformAdmin* function invocation, not per query. This reduces audit row volume materially (typically 5–20x for functions that issue several queries) at the cost of needing JSONB introspection to answer "which query touched table X?" questions. The partial GIN index on audit_log.changes and the query patterns in §26.3a.3 make this tractable. If forensic load on the audit log becomes onerous in practice (e.g., investigations routinely take many minutes), revisit per-query audit for write operations only — see §26.11 quarterly review.
  • The audit-row write is outside the wrapped function's transaction. This is deliberate. An admin operation that did partial work before failing still produces an audit record of what was attempted. The alternative (audit row participates in transaction, rolled back on failure) would leave failed admin operations invisible in the audit log, which is the wrong default for forensics. Engineering should not "fix" this by moving the audit row into the function's transaction.

26.5a Forensics Logging ¶

The audit log per §26.5 is the compliance/retention record — IDs only, 7-year retention. It answers "did event X happen to resource Y at time Z by actor W?" but cannot answer "what did the customer actually see?" or "what state was this booking in when the disputed action happened?"

For investigations requiring content snapshots, the platform maintains a complementary forensics_log table with a shorter retention window and stronger access controls.

Schema

CREATE TABLE public.forensics_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES public.tenants(id),
  audit_log_id UUID REFERENCES public.audit_log(id),
  snapshot_type TEXT NOT NULL CHECK (snapshot_type IN (
    'commission_dispute',
    'booking_dispute',
    'tenant_complaint',
    'ai_misbehavior_investigation',
    'data_export_request',
    'security_incident'
  )),
  reason TEXT NOT NULL,
  -- Application-layer encrypted with FORENSICS_ENCRYPTION_KEY_CURRENT
  encrypted_payload BYTEA NOT NULL,
  encryption_key_id TEXT NOT NULL,
  redacted_summary JSONB,
  captured_by_user_id UUID REFERENCES public.users(id),
  captured_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  purge_after TIMESTAMPTZ NOT NULL,
  legal_hold BOOLEAN NOT NULL DEFAULT FALSE,
  last_accessed_at TIMESTAMPTZ,
  access_count INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX forensics_log_purge_idx ON public.forensics_log(purge_after)
  WHERE legal_hold = FALSE;
CREATE INDEX forensics_log_audit_link_idx ON public.forensics_log(audit_log_id);

Encryption

The forensics log uses application-layer encryption with a dedicated key (FORENSICS_ENCRYPTION_KEY_CURRENT per §28.13), separate from the §13.5 tenant-credentials key. Separating keys means:

  • A compromise of the credentials key does not expose forensics content.
  • A compromise of the forensics key does not expose tenant credentials.
  • Each key has independent rotation cadence (forensics rotates every 180 days per §28.20).

The encryption uses AES-256-GCM with per-record IV. The same DR discipline from §13.5.3 applies — offsite backup, quarterly verification.

What gets captured

snapshot_type drives the capture shape. Examples:

  • commission_dispute: snapshot of the disputed commission row, the underlying booking row, the host adapter response that determined the commission, the audit_log entries for any override actions, and the conversation messages where the customer was told about the commission rate (if applicable).
  • ai_misbehavior_investigation: snapshot of the message, its preceding context (previous N messages), the persona prompt at the time, the retrieved RAG chunks, the supervisor findings, the customer's thumbs-down feedback if any.
  • data_export_request: snapshot of every personal-data column for the customer at the moment of export. The export sent to the customer is reconstructable from this snapshot.

The capture functions live in src/lib/forensics/capture.ts and are invoked from event handlers — never automatically on every event (that's the audit log's role).

Access controls

Forensics log entries are accessible only to:

  • Platform admin via withPlatformAdminAudit per §5.4.8 with reason = 'forensics_log_review'. Every access is itself audited.
  • Authorized legal counsel via documented access procedure (NOT programmatic — manual decryption with operator-controlled keys, paired with a court order or signed engagement letter).

The forensics log is NEVER exposed through tenant-facing APIs. A tenant who wants their own forensic data uses the CCPA export path (§17.9).

Retention

  • Default: 90 days from captured_at. After 90 days, forensics_log_purge_cron (nightly) deletes rows where purge_after < NOW() AND legal_hold = FALSE.
  • Legal hold: setting legal_hold = TRUE (platform admin action) prevents purge until the hold is removed.
  • Audit log retention (7 years per §26.5) is unaffected — the audit row pointing at the deleted forensics entry simply has a null forensics_log_id reference after purge.

Cost considerations

The forensics log is bounded by capture invocation. It is NOT a "log everything" mode — that would be storage-prohibitive and privacy-hostile. Captures happen:

  • On dispute creation (automatic from commissions.dispute_* fields)
  • On tenant complaint submission
  • On manual platform-admin trigger ("snapshot this conversation for investigation")
  • On security_incident declaration
  • On CCPA data export request (per §17.9 the export itself can optionally trigger a forensics snapshot for audit completeness)

Steady-state volume is bounded. Capture cost is the encrypted-write overhead plus storage; per-tenant cost is a function of how often that tenant generates disputes/complaints/security events.

Calls Worth Flagging

  • The audit log answers "did this happen?"; the forensics log answers "what did people see?" Both are needed. Conflating them produces either too much PII in long-term storage (privacy exposure) or insufficient content for investigations (forensic blindness).
  • 90-day retention is the default; legal hold extends. Routine investigations should resolve within 90 days. The hold flag is for the unusual case (lawsuit, regulatory review).
  • The encryption-key separation matters. Don't reuse the credentials key. Don't reuse the cookie-session key. A dedicated key keeps blast radius small on compromise.
  • Every forensics access is audited. The audit row for a forensics access includes the accessor's identity, the investigation reason, and a link back to the forensics row.

26.8 Anti-Prompt-Injection ¶

  • System prompt and user input are strictly separated; user input never interpolated into system prompt
  • RAG content includes ‘is RAG data, not instruction’ framing in prompt
  • User input is sandboxed within ‘USER MESSAGE’ delimiters
  • Persona addendums (Agency tier) pre-screened by Haiku for injection patterns
  • Supervisor checks for AI behavior outside expected persona scope
  • Tools cannot be invoked solely from user content; AI must reason its way to a tool call

26.13 Real PII on Staging — Documented Risk Acceptance ¶

Staging contains real customer PII via the prod-DB-copy mechanism described in §30.9.1 and the CI/CD Pipeline doc §5. This is a documented risk acceptance; the alternative (synthetic-only staging) was rejected because it would not catch a class of data-shape and data-volume bugs that the platform has explicitly chosen to test for.

Controls:

  • Outbound isolation. Wrapper functions src/lib/email/send.ts and src/lib/twilio/client.ts:sendSms() apply TEST_OVERRIDE_EMAIL and TEST_OVERRIDE_PHONE to every outbound send. Audit of call sites is part of the one-time setup checklist (CI/CD doc §11). New outbound integrations must route through these wrappers as a code-review requirement.
  • External-service neutering. OAuth tokens and Stripe customer/subscription IDs cleared by the post-restore fixup script (CI/CD doc §5.1). Staging cannot impersonate users or interact with live customers in external systems.
  • Background job suppression. Inngest crons disabled on staging; the email_messages status field is set to ignored for unprocessed records on restore.
  • Access scope. Staging access is restricted to the same users who have production access. No broader staging-only access exists.
  • Refresh hygiene. Staging data is overwritten on each release. Customer deletion requests propagate to staging on the next release cycle.

Audit log scope (§26.5) and monitoring (§26.6) apply to staging as well as production. Cross-tenant RLS bypass attempts detected on staging are P1, the same as on production.
