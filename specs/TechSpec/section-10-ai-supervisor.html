Section 10 — AI Supervisor

The supervisor is a safety and quality layer that runs around every AI response. It performs preflight checks before responses are surfaced to customers, handles escalations, and feeds into platform-wide monitoring.

10.1 Architecture ¶

[User message arrives]
  │
  ▼
[AI generates response candidate]
  │
  ▼
[Supervisor preflight checks]
  ├──► hallucination_risk
  ├──► persona_drift
  ├──► promise_detection
  ├──► arithmetic_check
  ├──► compliance_keyword
  ├──► tone_drift
  └──► topic_escalation
  │
  ▼
[Pass] ──► response surfaced to customer
  │
[Flag] ──► check regen budget (per §10.1a)
  │           │
  │           ├── budget exhausted ──► escalate to human (no further regens)
  │           │
  │           └── budget remaining ──► regenerate with stricter instructions
  │                                        │
  │                                        ▼
  │                                    [Re-check preflight]
  │                                        │
  │                                        └──► (loop back to budget check)
  ▼
[After 2 failed regens OR budget exhausted] ──► escalate to human

10.1a Per-Conversation Regen Budget ¶

A bad persona prompt, a prompt-injection attack, or genuinely challenging content can produce repeated regen cycles. Each regen is a full Sonnet call. Without a cap, a single afternoon of regen spirals can consume a tenant's entire monthly AI budget — and §27's monthly thresholds catch it too late.

Budget structure

Each conversations row tracks the cumulative regen activity:

ALTER TABLE public.conversations
  ADD COLUMN regen_tokens_consumed INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN regen_count_total INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN regen_budget_exhausted_at TIMESTAMPTZ;

The supervisor's regen loop reads two thresholds (configurable per §28.X — env vars below):

  • SUPERVISOR_REGEN_MAX_PER_CONVERSATION (default: 6) — absolute cap on regen attempts for a single conversation across its lifetime. Independent of message count.
  • SUPERVISOR_REGEN_MAX_TOKENS_PER_CONVERSATION (default: 25000) — cumulative token spend cap on regen attempts. Sonnet at ~$3/MTok input + $15/MTok output makes 25K tokens roughly $0.25 — a reasonable per-conversation ceiling.

EITHER threshold trips the exhaustion state. Once exhausted:

  • The current message gets one final escalation-to-human (no further regens; the in-flight regen attempt completes and is delivered or the existing response is surfaced with a warning marker).
  • regen_budget_exhausted_at is set on the conversation row.
  • ALL subsequent messages in this conversation skip the regen loop entirely — supervisor still preflights, but flag → direct escalation, no regeneration attempts.
  • Tenant is alerted (§10.5 supervisor dashboard shows a new "Exhausted regen budget" surface).

Budget recovery

Per-conversation exhaustion does not auto-reset. The conversation is flagged for human attention until either:

  • A human agent intervenes and resets the budget manually (sets regen_budget_exhausted_at = NULL, increments regen_count_total by 0 — explicit no-op so audit log records the reset).
  • The conversation is closed (status = 'closed'). A new conversation starts fresh.

Why per-conversation, not per-tenant or per-hour

  • Per-tenant: §27.4 already does this at monthly granularity. Too coarse to catch spirals within a single afternoon.
  • Per-hour-globally: rate-limiting AI calls at the tenant level affects ALL conversations including healthy ones; pathological conversations need to fail without dragging down everyone.
  • Per-conversation: the scope of the problem. A pathological conversation gets quarantined; other conversations in the same tenant continue normally.

Defense layering

The per-conversation cap is the FIRST line. Defense in depth:

LayerTriggerEffect
Per-conversation cap (§10.1a)6 regens OR 25K tokens in one conversationConversation quarantined, escalates to human
Per-tenant abuse monitoring (§27)Monthly thresholdsThrottle / hard limit per tier
Global kill switch (§10.6)Platform-wide misbehaviorAll AI paused

Calls Worth Flagging

  • Defaults are deliberately conservative. 6 regens / 25K tokens per conversation is a ceiling, not a target. Tune downward in Phase 1 if observation shows most healthy conversations need fewer regens.
  • Exhaustion is sticky on the conversation. A conversation that hits the budget stays human-escalated even after a successful human handoff back to AI, until a human explicitly resets it. This avoids re-entering the spiral.
  • The token cap protects against a "few small regens that add up" attack. A pathological prompt that produces 4 regens each with 6K tokens hits the token cap before the regen count cap. Both bounds together cover the failure space.

10.3 Topic-Level Escalation ¶

Unlike conversation-level escalation, the supervisor tracks escalation at the TOPIC level. A customer may have an active escalation about a refund (handled by human) while continuing to chat about an unrelated future trip (AI continues to handle).

CREATE TABLE public.escalation_topics (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

tenant_id UUID NOT NULL REFERENCES public.tenants(id),

conversation_id UUID NOT NULL REFERENCES public.conversations(id),

user_id UUID REFERENCES public.users(id),

topic_summary TEXT NOT NULL,

topic_tags TEXT[],

status TEXT NOT NULL CHECK (status IN (‘open’,‘in_progress’,‘resolved’,‘closed’)),

initiated_by TEXT, – ‘supervisor’,‘customer’,‘agent’

initiated_reason TEXT,

assigned_agent_id UUID REFERENCES public.users(id),

opened_at TIMESTAMPTZ DEFAULT NOW(),

resolved_at TIMESTAMPTZ,

resolution_notes TEXT

);

When uncertain whether a new message relates to an open escalation, the AI asks for clarification rather than guessing.

10.4 Supervisor Findings (per message) ¶

Every preflight check produces a finding (pass or flag). Findings stored in messages.supervisor_findings JSONB:

{

“checks_run”: [“hallucination_risk”,“persona_drift”,“promise_detection”,“arithmetic_check”,“compliance_keyword”,“tone_drift”,“topic_escalation”],

“findings”: [

{“check”:“hallucination_risk”,“severity”:“info”,“details”:“All factual claims supported”},

{“check”:“promise_detection”,“severity”:“warning”,“details”:“Soft-rewrote ‘always available’ to ‘typically available’”}

],

“regen_count”: 0,

“final_action”: “allow”

}

10.5 Supervisor Dashboard ¶

  • Open topic-level escalations (assigned + unassigned)
  • Recent flagged messages by check type
  • Per-persona metrics: response quality, thumbs-down rate, regen rate
  • Per-tenant aggregate metrics (visible to platform admin)
  • Alert feed (priority-sorted)

10.5a Supervisor Sampling and Review ¶

The supervisor pipeline per §10.1 has three outcomes per message: pass, regenerate (then re-evaluate), and escalate. The "pass" outcome includes a subset where supervisor findings include severity: warning items that were auto-rewritten or auto-corrected. These borderline passes are the highest-value source for tuning the supervisor itself — cases where a check fired, the system self-recovered, but a human eye might catch a residual issue the checks missed.

This subsection defines the sampling and review surface.

What gets sampled

Four sampling rates, applied per message at supervisor completion:

Outcome classDefault sample rateConfigurable
Pass with no findings1% (supervisor_sample_rate_clean_pass)Yes
Pass with warning findings (auto-rewritten)10% (supervisor_sample_rate_warning_pass)Yes
Regen attempted (regardless of final outcome)25% (supervisor_sample_rate_regen)Yes
Escalate to human100%No — every escalation is reviewable already via §10.5 dashboard

Sampled messages go into a supervisor_review_queue table. Random per-message (not per-conversation, not per-tenant).

Queue surface

/admin/supervisor/review-queue displays the queue with these tabs:

TabFilterAction shape
Recent (default)All sampled messages from last 7 daysMark as "OK" / "issue spotted"
Warning passesOnly severity: warning itemsSame
RegensAll sampled regensSame
DisputedItems previously marked "issue spotted"Adjudicate / annotate / close

Each item shows: original AI response, supervisor findings, conversation context (previous N messages), cited RAG chunks if applicable, customer's subsequent thumbs reaction if any. Reviewer marks "OK" (most cases, fast) or "issue spotted" (flagged for engineering attention with a free-text reason).

What "issue spotted" triggers

  • Engineering team alerted via existing audit-log + Sentry pipeline.
  • Item moves to "Disputed" tab.
  • Pattern surfaces in §10.7 supervisor performance metrics.
  • If 3+ items flagged "issue spotted" within a 7-day window cite similar supervisor finding types, an aggregated issue is auto-created for engineering with the pattern summary.

Why this isn't the §22.7 review queue

§22.7 reviews RAG content (chunks). This reviews supervisor verdicts on AI responses. Different domain expertise, different queue, different SLA.

Schema

CREATE TABLE public.supervisor_review_queue (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  message_id UUID NOT NULL REFERENCES public.messages(id),
  conversation_id UUID NOT NULL REFERENCES public.conversations(id),
  sample_category TEXT NOT NULL CHECK (sample_category IN (
    'clean_pass', 'warning_pass', 'regen_attempted', 'escalation'
  )),
  supervisor_findings_snapshot JSONB NOT NULL,
  conversation_context_snapshot JSONB,
  review_status TEXT NOT NULL CHECK (review_status IN (
    'pending', 'reviewed_ok', 'reviewed_issue', 'disputed_resolved'
  )) DEFAULT 'pending',
  reviewed_by_user_id UUID REFERENCES public.users(id),
  reviewed_at TIMESTAMPTZ,
  review_notes TEXT,
  sampled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  purge_after TIMESTAMPTZ NOT NULL DEFAULT (NOW() + INTERVAL '90 days')
);

CREATE INDEX supervisor_review_queue_status_idx
  ON public.supervisor_review_queue(review_status, sampled_at DESC)
  WHERE review_status = 'pending';

Configurable knobs (in platform_settings)

SettingDefaultRange
supervisor_sample_rate_clean_pass0.010.0–1.0

supervisor_sample_rate_regen0.250.0–1.0

Calls Worth Flagging

  • Sampling is at supervisor-completion time, not lazily. Atomic snapshot prevents "data I wanted to review changed before I got to it."
  • Reviewer notes drive pattern detection. The aggregated-issue trigger (3+ items in 7 days) is where the queue produces engineering signal.
  • Defaults err generous for launch. Tune downward once queue's signal-to-noise is understood.
  • Reviewer authority: any platform admin can review. Marking "issue spotted" without a reason is allowed (required only if it's the third item in a 7-day pattern).

10.6 Kill Switch ¶

If AI behavior becomes problematic platform-wide (model misbehavior, prompt injection campaign, etc.), platform admin can pause AI responses globally or per-tenant. Activated AI shows: ‘Our AI is taking a brief break. A human will be in touch shortly.’

10.7 Supervisor Performance Metrics ¶

  • Hallucination check fire rate
  • Block-after-regen rate
  • Compliance escalation rate
  • Thumbs-down rate per persona, per topic
  • Tone-drift detection rate
  • Average AI response latency (with supervisor overhead)
