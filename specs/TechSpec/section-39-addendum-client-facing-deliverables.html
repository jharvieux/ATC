Section 39 - Addendum — Client-Facing Deliverables (Itinerary & Trip Resources)

Status: Addendum. Lands after Part 1–9 build prompts. Adds two client-facing surfaces — a consolidated trip itinerary and a curated trip resources page — that agents can share with their booked customers. References existing sections by number; does not modify them in place.

Why an addendum, not a retrofit: These deliverables are post-booking customer touchpoints that didn't exist in Part 1–9. They draw from existing booking, conversation, and RAG data without modifying those structures. An earlier proposal for a "document vault" (storing customer PII docs like passport scans) was rejected on PII-minimization grounds; this section captures the link-curation-only approach that replaced it.

39.1 Overview ¶

Two client-facing surfaces share a common structure (tokenized URL, tenant-branded, mobile-responsive, AI-enabled for questions):

DeliverablePurposeData sources
Trip ItineraryConsolidated view of the booked cruise — sail dates, ship details, ports, cabin info, what's included, agent's personal notes. PDF and shareable web page.bookings, commissions (only non-financial fields), contacts, ship/port RAG (§33)
Trip Resources PageCurated external links for the customer to bookmark — cruise line check-in URL, insurer claims page, port authority info, agent contact card. NO file uploads, NO PII storage on the platform.Agent-entered URLs, cruise-line metadata, RAG-derived port-authority links

39.2 Trip Itinerary ¶

39.2.1 What it contains ¶

  • Cover — tenant logo & branding, cruise line, ship, sail date, primary passenger name(s), agent name and contact
  • At a glance — embarkation port + date/time, disembarkation port + date/time, duration nights, cabin category, cabin number (if known)
  • Day-by-day itinerary — for each day: port name, arrival time, departure time, "At Sea" days marked. Each port has a brief description sourced from RAG (CruiseMapper port content per §33.5)
  • Ship overview — ship name, year built, capacity, notable features. Sourced from RAG.
  • What's included — derived from the booking's line items (per §38.5 categories): "Beverage package included", "Gratuities pre-paid", etc.
  • Travel documentation reminders — generic checklist: passport validity, visa requirements (RAG-sourced for the itinerary's countries), required vaccinations (if any). No PII stored — just the checklist for the customer.
  • Agent's personal notes — free-text section the agent writes for this specific customer (e.g., "Don't miss the chef's table on Symphony — book day one")
  • Next steps timeline — automatically computed dates: final payment due, online check-in opens, embarkation. Surfaces upcoming dates relative to "today" when the page is loaded.

39.2.2 What it does NOT contain ¶

  • Commission amounts or any commission-related data
  • Other customers' information
  • Internal pricing markup, host adapter details, or agency-internal data
  • Customer's passport number, DOB, or other documents (per §39.4 PII posture)

39.2.3 Itinerary access ¶

Same tokenized URL pattern as the quote-send flow (§12.4 token-based access). The agent generates the itinerary from the booking's detail page; the system creates a unique tokenized URL and sends it to the customer via email per §23. Token is single-purpose (this one itinerary), tenant-scoped, and rotatable from the booking page.

PDF export is also generated at the time of itinerary creation; the email contains both the web link and the PDF attachment. PDF is regenerated when the agent edits the itinerary (the previously-sent PDF is not invalidated; if the customer keeps the PDF, it remains accurate to the moment of sending, while the web URL always reflects the latest state).

39.2.5 Schema ¶

CREATE TABLE public.trip_itineraries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),
  booking_id UUID NOT NULL REFERENCES public.bookings(id) ON DELETE CASCADE,

  -- Access
  access_token TEXT NOT NULL UNIQUE,    -- generated; URL-safe; rotated on agent action
  status TEXT NOT NULL DEFAULT 'draft'
    CHECK (status IN ('draft','sent','archived')),

  -- Content
  agent_notes TEXT,
  cover_image_url TEXT,                 -- optional, references rag_media_assets or tenant uploads

  -- Day-by-day overrides (agent can adjust the auto-generated itinerary)
  day_overrides JSONB,                  -- array indexed by day_number

  -- Travel docs checklist (computed, not stored verbatim — populated at render time)
  -- Computed fields not persisted; derived from booking's itinerary at render

  -- Lifecycle
  sent_at      TIMESTAMPTZ,
  archived_at  TIMESTAMPTZ,
  last_pdf_generated_at TIMESTAMPTZ,
  pdf_storage_key TEXT,                 -- Supabase storage key for the current PDF

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (booking_id)                    -- one itinerary per booking
);

  ON public.trip_itineraries(access_token)
  WHERE status <> 'draft';

39.2.6 Tokenized public access endpoint ¶

The public itinerary URL pattern is /i/<access_token>. The endpoint:

  1. Validates the token against trip_itineraries.access_token with status <> 'draft'.
  2. Loads the itinerary row, its booking, and the booking's primary contacts (names only, not full PII).
  3. Loads RAG content for ports and ship.
  4. Renders the itinerary page server-side via the existing Next.js routing; no client-side authentication is required.
  5. Records access in an audit log (token, IP, user-agent timestamp) for the agent to see who's viewed it.

Token rotation: agent can rotate the token from the booking page if they suspect it's been forwarded inappropriately. Old token immediately invalidated.

39.3 Trip Resources Page ¶

39.3.1 Purpose ¶

A separate page (linked from the itinerary) collecting external resources the customer will need throughout the booking-to-sailing journey: cruise line check-in URL, insurer claims page, port authority links, agent's contact info, packing list, etc.

39.3.2 What's in scope ¶

Only links and metadata. No file uploads. No PII storage. Examples:

  • Royal Caribbean's online check-in URL (auto-populated from cruise line metadata)
  • The customer's insurance policy provider's claims page (if agent enters the URL)
  • Port authority for embarkation port (RAG-sourced)
  • Travel advisory page for destination country (US State Department for US-based tenants)
  • Agent's contact card (email, phone, "best time to reach me")
  • Embedded packing checklist (text-only, derived from itinerary type — cold-weather cruise vs Caribbean)

39.3.3 What's explicitly out of scope ¶

  • Document storage. The platform does not store customer documents (passport scans, insurance policy PDFs, visa documents). An earlier design proposed this and was rejected on PII-minimization grounds: storing identity documents creates a significant security liability without commensurate value. Customers can hold their own documents in their own storage (Google Drive, Dropbox, etc.) — the trip resources page can link to a customer's own storage if they share a link, but the platform itself stores no files.
  • Live document collaboration. No shared workspace, no annotations on documents, no version history of customer-uploaded files.
  • Customer-uploaded photos or trip artifacts. Out of scope for v1; a future "post-trip memory book" deliverable could be added but is not part of this addendum.

39.3.4 Schema ¶

CREATE TABLE public.trip_resources (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),
  booking_id UUID NOT NULL REFERENCES public.bookings(id) ON DELETE CASCADE,

  access_token TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL DEFAULT 'draft'
    CHECK (status IN ('draft','published','archived')),

  -- Curated link sections (JSONB to avoid table-per-section sprawl)
  -- Shape: { section_label: string, links: [{label, url, description?, source: 'auto'|'agent'}] }
  sections JSONB,

  -- Agent's contact card (snapshot at publication time so it's stable)
  agent_contact JSONB,                  -- { name, email, phone, hours, photo_url? }

  -- Packing checklist (text body)
  packing_checklist TEXT,

  -- Lifecycle
  published_at TIMESTAMPTZ,
  archived_at  TIMESTAMPTZ,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (booking_id)                    -- one resources page per booking
);

CREATE INDEX trip_resources_token_idx
  ON public.trip_resources(access_token)
  WHERE status = 'published';

39.3.5 Auto-population sources ¶

When the resources page is generated, the system auto-populates the sections JSONB from:

SectionDefault content source
Cruise linePer-line metadata: check-in URL, customer service phone, mobile app link. Maintained as platform-admin config per §13 adapter pattern, or as static reference data.
PortsRAG-sourced port authority URLs and key info per §33.5
Travel advisoriesState Department links for destination countries (US tenants); equivalent for other tenant countries when supported
InsuranceEmpty by default; agent fills in if they sold the customer a policy
Agent contactFrom users table for the assigned agent
Packing checklistGenerated from itinerary type (Caribbean / Alaska / Europe / etc.) using a curated template library

Agent can edit any auto-populated content, add or remove sections, and re-publish.

39.4 PII Posture ¶

This section's deliberate posture: the platform does not become a custodian of customer identity documents. Reasons:

  • Storing passport scans, IDs, and visas turns the platform into a regulated identity document repository in many jurisdictions.
  • The security overhead (encryption at rest with separate keys, access logging at field level, breach notification obligations, retention policy with destruction proof) is disproportionate to the value of storing the documents centrally.
  • Customers already have their documents; the agent already has working processes outside the platform for collecting them. The platform's value is the link-curation, not the document custody.

What the platform DOES store: structured booking data (passenger names, sail date, ship — required for the booking itself), agent notes about the customer (no documents), and external URLs the customer can use to access their own documents wherever they store them.

If a future addendum revisits this decision, it would need a full PII-impact assessment, encryption-at-rest design with field-level keys, jurisdiction-specific compliance review (US, EU, UK at minimum), and a clear scoping of which document types the platform would accept. Not in v1 scope.

39.5 Customer-Side AI ¶

Both the itinerary and the resources page embed an AI chat panel. The AI persona is the same one assigned to the booking's contact. Context loaded into the AI:

  • The booking's itinerary details (ship, ports, sail date, cabin, what's included)
  • The customer memory (per §11)
  • The agent's notes from the itinerary
  • RAG retrieval enabled for ports and ship

The AI cannot make changes to the booking, cannot quote new bookings (per AI persona scoping in §9), and cannot expose commission or pricing-internal data. It can answer "what should I pack?", "tell me about the port of Cozumel", "what time do we sail?" — questions grounded in either the booking data or RAG content.

39.6 PDF Generation ¶

Itinerary PDF: full content of the web itinerary in print-friendly layout, multi-page. Cover, day-by-day, ship/port detail, agent notes, contact card, packing checklist. Generated via Puppeteer or react-pdf at the time of sending (or re-sending). Stored in Supabase storage; the email's PDF attachment is the latest generated version. Old PDFs are not retained server-side (the customer's email copy is the historical record); only the latest pdf_storage_key is referenced from trip_itineraries.

Resources page does NOT generate a PDF — its value is in the live, clickable links. Customers bookmark the URL or it lives in their inbox.

39.7 Editing and Re-sending ¶

From the booking detail page in the CRM, agents see two buttons: "Edit Itinerary" and "Edit Resources Page." Editing either:

  1. Opens an edit view with full content controls.
  2. "Save Draft" persists changes without re-notifying the customer.
  3. "Save & Re-send" persists changes, regenerates the PDF (itinerary only), and sends a fresh notification email to the customer indicating the deliverable has been updated.

Edit history is kept in audit_log per §26.5 — who edited what and when. Versioned content storage (full snapshots of each version) is not in v1; the audit log is action-level only.

39.8 Branding ¶

Both surfaces respect the tenant's branding configuration per §13 (logo, primary/accent colors, font family). For sub-host tenants, the platform applies the white-label theme. The agent's photo and contact card appear on both surfaces unless the agent has explicitly suppressed them in their profile.

39.10 Calls Worth Flagging ¶

  • Token-based public access means the URL itself is the credential. Customers forwarding the URL to spouses, family, etc. is expected and acceptable; forwarding to an adversary would expose the itinerary content. The content is non-sensitive by design (no PII beyond names, no financial data), but agent should be told that the URL is shareable.
  • RAG content quality affects port descriptions and ship overviews. Stale or wrong CruiseMapper content surfaces directly to customers. Per §33, refresh cadence and quality monitoring apply.
  • PDF generation cost. Each booking generates at least one PDF; high-volume tenants could see meaningful Puppeteer costs (or alternative library costs). Track per §27.
  • Packing checklist accuracy. Generic templates by itinerary type are a starting point; agents should review before sending. The customer-side AI can answer follow-up questions to fill gaps.
  • Customer-side AI cost per session is unbounded if customers chat extensively. Per-deliverable session budget caps (per §27) should apply.
  • "What's included" derivation from line items requires the booking to have populated line_items per §38.5. If a booking was created from a single-option quote without line items, the itinerary's "What's included" section shows only the high-level total with a generic "Contact your travel agent for inclusion details" note.
  • Resources page section ordering and visual design is not specified in detail here — defer to the build's design phase. Recommend section weights: cruise line, ports, agent contact, packing, advisory, insurance, other.
  • Agent contact snapshot at publication time (vs live read) means if the agent's contact info changes after publish, the customer sees stale info. Acceptable tradeoff: agent contact rarely changes; live read would require an additional DB query per public view. Re-publish updates the snapshot.
  • Travel advisory link integration needs per-country source mapping. US State Department is the obvious default for US tenants; international tenants need equivalents. Out of scope to fully map in v1; the field is free-text URL the agent can populate.
  • Reaffirming the no-PII-document-storage posture is critical at build time. The temptation to "just let customers upload their passports for safe keeping" will arise; the answer is: not in v1, and any future revisit requires the full PII assessment outlined in §39.4.
