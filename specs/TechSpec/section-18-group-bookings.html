18.2 Group Creation ¶

  • Coordinator picks cruise (line, ship, sailing date, departure port)
  • Sets group preferences (max cabins, target group rate reference)
  • Writes coordinator message (free text appearing prominently in invites)
  • Configures visibility (invitee names visible vs anonymous default)
  • Selects hero image (destination-relevant)
  • Adds invitees (individually or bulk up to 50)
  • Optional per-invitee personal notes
  • Preview invitation email
  • Send → transitions to active

18.3 Destination-Relevant Hero Images ¶

Hero image selection:

  • Coordinator override (if uploaded)
  • Match against destination_images library by tags
  • AI generation fallback (Stable Diffusion XL or DALL-E 3)
  • Cruise line default (last resort)

Library is platform-curated with licensed imagery. AI generation gated by tenant tier and rate-limited per tenant for cost control. Generated images cached by (destination, cruise_line) for reuse.

18.5 Invitee Landing Page ¶

URL: /group/invite/{token} — HMAC-signed. Single canonical page; role-aware rendering.

Token validation contract

Every request to the invite URL validates the token through these checks, in order. ANY failure produces a clear tenant-facing error page (not a 404 — invitees need to understand what happened).

  1. HMAC signature valid. Confirms the token was issued by the platform. Failure: "This invitation link is invalid. Please contact the trip coordinator for a new one."
  2. Token exists in invitations table. A valid HMAC for a deleted row is treated as invalid. Failure: same message as (1).
  3. Token not revoked. Check invitations.token_revoked_at IS NULL. If revoked, render with revocation reason:
  • invitee_removed: "You're no longer on the invitation list for this trip. Contact the coordinator if this is unexpected."
  • coordinator_revoked: "This invitation has been withdrawn. Contact the coordinator with questions."
  • suspected_compromise: same as coordinator_revoked.
  • expired_natural: see check (4).
  1. Token not naturally expired. Per §18.9, tokens expire at sailing_date + 30 days. After expiry, set token_revoked_at = NOW(), token_revoked_reason = 'expired_natural' (lazy revocation — only marks expired on access; a cron also sweeps but the access-time check is the authoritative gate).
  2. First-use binding (if applicable). If invitations.token_first_used_at IS NOT NULL:
  • The first use was anonymous (no session): the token is now "warm" and any session can use it (rare path; covers an invitee who clicked through, browsed, and later returned).
  • The first use was authenticated (user signed in during the invite flow): invitations.token_bound_email is set. ALL subsequent requests must come from an authenticated session where auth.users.email = invitations.token_bound_email. Mismatch produces: "This invitation has been linked to a different account. Please sign in with the account you used when first viewing this invitation, or contact the coordinator."

Render the canonical page only after all five checks pass.

Page contents

  • Hero banner with destination image
  • Coordinator's message
  • Trip details + itinerary
  • Cabin grid (booked / pending / available with color coding)
  • RSVP section (Interested / Can't make it / Already booked)
  • Group chat preview
  • Pricing context
  • Coordinator/admin section (visible only to coordinator and platform admin)

Coordinator revocation surface

Coordinators can revoke invitations from /groups/{id}/invitations:

  • Per-invitee "Remove from invitation" action: sets token_revoked_at = NOW(), token_revoked_reason = 'invitee_removed'. The invitee's RSVP record (if any) is retained for audit but the token no longer resolves.
  • "Suspected compromise" action: sets token_revoked_reason = 'suspected_compromise'. Audit-log entry records who flagged it.
  • Bulk revoke "Re-issue invitations" action: revokes all currently-outstanding tokens with reason coordinator_revoked and generates fresh ones. Useful if a coordinator suspects the invitation list was shared too widely.

All revocation actions write to audit_log per §26.5.

Schema additions

The invitations table gains these columns:

ALTER TABLE public.invitations
  ADD COLUMN token_revoked_at TIMESTAMPTZ,
  ADD COLUMN token_revoked_reason TEXT
    CHECK (token_revoked_reason IN (
      'invitee_removed', 'coordinator_revoked',
      'first_use_authenticated', 'suspected_compromise', 'expired_natural'
    )),
  ADD COLUMN token_first_used_at TIMESTAMPTZ,
  ADD COLUMN token_bound_email TEXT
    -- After first authenticated use, the token is bound to the
    -- specific email address. Subsequent uses with a different
    -- session must match. NULL until first authenticated use.
;

CREATE INDEX invitations_token_lookup_idx ON public.invitations(token)
  WHERE token_revoked_at IS NULL;

18.9 Token Lifecycle ¶

Invitation tokens have four lifecycle states tracked in invitations.token_revoked_at and related columns (per §18.5 schema):

StateStorage signalUse behavior
Activetoken_revoked_at IS NULL; not yet past sailing_date + 30dToken resolves; full landing page rendering per §18.5
First-used (anonymous)token_first_used_at IS NOT NULL, token_bound_email IS NULLToken resolves; still anonymous-accessible
First-used (bound)token_first_used_at IS NOT NULL, token_bound_email IS NOT NULLToken resolves ONLY for authenticated sessions matching the bound email
Revokedtoken_revoked_at IS NOT NULLToken does not resolve; reason-specific error page

Tokens accommodate cruise booking windows up to 24+ months by expiring lazily at sailing_date + 30 days. After acceptance and authenticated signup, the invitee accesses the group via authenticated session — the token becomes a backup identifier (binding the session to the original invitation), not a primary auth credential.

Lifecycle events that set revoked state:

  • Coordinator removes invitee → 'invitee_removed'
  • Coordinator manually revokes → 'coordinator_revoked'
  • Coordinator flags compromise → 'suspected_compromise'
  • Authenticated first-use completes → token NOT revoked, but token_bound_email set per §18.5 step 5
  • Natural expiry → 'expired_natural' (set on next access or by nightly cron, whichever first)

18.10 Sailed Status — Read-Only ¶

At travel_start_date, group becomes IMMEDIATELY read-only for group details, RSVP, and member management. No edits, no new invitees. Forum chat stays open separately for in-trip and post-trip discussion.
