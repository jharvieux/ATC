Section 38 - Addendum — Multi-Option Quote Builder

Status: Addendum. Extends the §12.4 quote schema to support multiple options per quote (side-by-side comparison). Does not modify §12.4 in place; introduces a sibling table and recasts the existing quotes table as the container while option-specific fields move to the new options table.

Why an addendum, not a retrofit: The existing §12.4 schema embeds option-specific fields (cruise_line, ship_name, sailing_date, cabin_category, commissionable_fare) directly on the quotes row. A real-world agent conversation produces multiple options ("here are three sailings to compare"), and the single-option schema cannot represent this without convoluted workarounds. This addendum lands the multi-option capability as an additive extension.

38.1 Overview ¶

A quote is now a container holding one or more options. Each option represents a single cruise alternative (a specific line/ship/sailing/cabin combination with its own pricing). The customer reviews all options side-by-side, the agent (or AI) can recommend one, and the customer's acceptance is per-option — they pick which one they want to book.

Backward compatibility: a single-option quote is still valid. The schema permits N=1 options without ceremony. Existing single-option quotes from before this addendum land migrate cleanly (one row in the new options table per existing quote).

38.2 Schema Migration ¶

38.2.1 New quote_options table ¶

CREATE TABLE public.quote_options (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  quote_id  UUID NOT NULL REFERENCES public.quotes(id) ON DELETE CASCADE,

  -- Position/labeling
  option_index INT NOT NULL,             -- 1, 2, 3 (display order)
  label TEXT,                            -- e.g., "Budget pick", "Best value", "Splurge"

  -- Trip details (moved from quotes per §38.2.2)
  cruise_line TEXT,
  ship_name TEXT,
  sailing_date DATE,
  duration_nights INTEGER,
  departure_port TEXT,
  cabin_category TEXT,
  passenger_count INTEGER,

  -- Financial (cents — money rules per §14.0)
  commissionable_fare_cents BIGINT,
  non_commissionable_total_cents BIGINT,
  total_amount_cents BIGINT,
  currency TEXT NOT NULL DEFAULT 'USD',

  -- Line-item breakdown (per §38.5)
  line_items JSONB,                      -- array of {description, amount_cents, is_commissionable, category}

  -- Status
  is_recommended BOOLEAN NOT NULL DEFAULT FALSE,  -- agent's flagged "best fit"
  customer_selected BOOLEAN NOT NULL DEFAULT FALSE,
  customer_selected_at TIMESTAMPTZ,

  -- Notes specific to this option
  option_notes TEXT,
  pros TEXT[],                           -- bullet list of pros
  cons TEXT[],                           -- bullet list of cons

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (quote_id, option_index)
);

CREATE INDEX quote_options_quote_idx ON public.quote_options(quote_id, option_index);
CREATE INDEX quote_options_tenant_idx ON public.quote_options(tenant_id);

ALTER TABLE public.quote_options ENABLE ROW LEVEL SECURITY;
-- RLS per §5.1.

-- At most one option per quote can be customer_selected = TRUE
CREATE UNIQUE INDEX quote_options_one_selected_idx
  ON public.quote_options(quote_id)
  WHERE customer_selected = TRUE;

38.2.2 quotes table changes ¶

The quotes table per §12.4 currently stores option-specific fields. These move to quote_options. The quotes row becomes the container:

-- Columns to remove from quotes (now on quote_options):
--   cruise_line, ship_name, sailing_date, duration_nights, cabin_category,
--   passenger_count, commissionable_fare, non_commissionable_total, total_amount
--
-- The §14.0 money refactor already renamed *_amount to *_amount_cents;
-- this addendum removes those columns from quotes entirely (they live on options).
--
-- Migration approach: keep the columns nullable during transition; the migration
-- script copies their values into a quote_options row (option_index=1) for each
-- existing quote; then a follow-up migration drops the columns from quotes.

-- Add new container-level columns:
ALTER TABLE public.quotes
  ADD COLUMN customer_facing_intro TEXT,        -- the message shown above the options list
  ADD COLUMN show_recommendation BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN recommendation_rationale TEXT;     -- if show_recommendation, this paragraph explains

38.2.3 Migration safety ¶

Single-step column drops on a live table risk locking. Recommended migration sequence:

  1. Add quote_options table (zero-downtime).
  2. Application code starts double-writing: new quotes write to both quotes (existing option-specific columns) AND quote_options. Reads still come from quotes.
  3. Backfill job: for each existing quote, create the corresponding quote_options row.
  4. Application code switches reads to quote_options. Continues double-writing.
  5. Verification window (1–2 weeks). Verify all reads are correct.
  6. Application code stops writing to quotes' option-specific columns.
  7. Migration drops the now-unused columns from quotes.

This is the standard "expand-migrate-contract" pattern. Cannot be done in a single deploy; spans 2–3 deploy cycles.

38.3 Building a Multi-Option Quote ¶

38.3.1 Agent path ¶

From a contact's detail page, the agent clicks "+ New Quote":

  1. Quote container is created (status = draft) with quotes row.
  2. UI shows an empty option grid. Agent adds option 1: picks cruise line, ship, sailing date, cabin category, fills financial fields (or imports pricing per §33.2 cached pricing if available).
  3. Agent clicks "+ Add option" — option 2 added with similar form. Defaults pulled from option 1 to reduce typing (same passenger_count, same departure port).
  4. Up to 5 options supported. UI caps at 5 to keep the side-by-side display readable.
  5. Agent optionally marks one option as is_recommended = TRUE and writes a recommendation_rationale on the quote container.
  6. Agent writes customer_facing_intro — the message shown above the options when the customer views the quote.
  7. Agent clicks "Send Quote" — status transitions to sent, customer is notified.

38.3.2 AI-assisted path ¶

From a chat conversation, the AI persona's generate_quote tool (per §9.6) is extended to produce a multi-option quote when the conversation indicates the customer is comparing. The tool input includes:

{
  contact_id: string,
  customer_facing_intro: string,
  recommendation: {
    show: boolean,
    rationale?: string,   // required if show=true
    recommended_option_index?: number
  },
  options: Array<{
    label?: string,
    cruise_line: string,
    ship_name: string,
    sailing_date: string,        // ISO date
    duration_nights: number,
    departure_port: string,
    cabin_category: string,
    passenger_count: number,
    commissionable_fare_cents: number,
    non_commissionable_total_cents: number,
    total_amount_cents: number,
    line_items: Array<LineItem>,
    pros?: string[],
    cons?: string[],
    option_notes?: string
  }>
}

The AI is prompted to suggest 2–3 options when the conversation evidence supports multiple alternatives. Hallucination safeguards from §21.10 apply: prices must come from search_host_inventory tool calls (not invented), arithmetic check enforces commissionable_fare + non_commissionable = total. The generated quote is in draft status; agent reviews and sends per §10 supervisor flow.

38.4.2 Recommendation marker ¶

If show_recommendation = TRUE on the quote AND exactly one option has is_recommended = TRUE, the recommended option gets a visual marker (badge, ribbon, highlighted border) and the recommendation_rationale appears below the option grid. If zero or multiple options are marked recommended, the UI suppresses the marker and the rationale (defensive — don't half-display a confused state).

38.4.3 Customer selection ¶

Customer clicks "Select this" on their preferred option. The UI:

  1. Sets quote_options.customer_selected = TRUE for that row (unique partial index ensures only one can be selected).
  2. Sets quotes.status = 'accepted' and quotes.accepted_at = NOW().
  3. Routes the customer to the booking flow (§20) pre-filled with the selected option's data.

If the customer revisits the quote and selects a different option (before booking is submitted), the prior selection is unselected and the new one selected. After a booking has been initiated against an option, switching requires the agent to intervene (creates a new draft booking; old booking remains in its current state).

38.4.4 Decline path ¶

Customer can decline the entire quote (button "None of these work for me — let's talk"). This sets quotes.status = 'declined' and declined_at = NOW() and prompts the customer for a brief reason (free text → declined_reason, existing field). Triggers a system task for the agent to follow up.

38.5 Line-Item Breakdown ¶

Each option's line_items JSONB array stores the cost breakdown:

[
  {
    "description": "Base cruise fare (2 guests, balcony)",
    "amount_cents": 248000,
    "is_commissionable": true,
    "category": "base_fare"
  },
  {
    "description": "Beverage package",
    "amount_cents": 45000,
    "is_commissionable": true,
    "category": "beverage_package"
  },
  {
    "description": "Taxes & port fees",
    "amount_cents": 28800,
    "is_commissionable": false,
    "category": "taxes_fees"
  },
  {
    "description": "Pre-paid gratuities",
    "amount_cents": 16800,
    "is_commissionable": false,
    "category": "gratuities"
  },
  {
    "description": "Travel insurance",
    "amount_cents": 12400,
    "is_commissionable": false,
    "category": "insurance"
  }
]

Category values follow §12.5 commissionable-fare table: base_fare, cabin_upgrade, loyalty_discount, taxes_fees, gratuities, insurance, dining, beverage_package, excursion, other. The application validates that the sum of line items matches the option's total_amount_cents and that the sum of commissionable line items matches commissionable_fare_cents. Mismatches block the quote from being sent.

38.6 PDF Generation ¶

Multi-option quotes generate a PDF with all options side-by-side on the first page (landscape orientation for ≥ 2 options; portrait acceptable for 1 option), followed by per-option detail pages with full line-item breakdown.

The §12.4 default of full line-item breakdown applies per-option; tenant can globally disable detail breakdown in settings if they prefer to show only totals (rare; defaults to full transparency).

PDF header includes "ESTIMATE" per §21.10 pricing-confidence safeguards, and the footer notes "subject to confirmation at booking" unless the host has provided price-lock guarantee. For each option, the line-item breakdown clearly identifies commissionable vs non-commissionable items so customer-facing pricing transparency is preserved.

38.7 Quote Lifecycle State Changes ¶

Existing §12.4 quote statuses still apply at the container level: draft, sent, viewed, accepted, declined, expired, converted. Per-option events are tracked on the options:

  • customer_selected_at on the chosen option (sets quote_options.customer_selected = TRUE)
  • An option_viewed_at field can be added for view tracking; deferred to a future analytics iteration

The container's converted_to_booking_id still applies — it points to the booking that resulted from whichever option the customer selected. Only one booking results from a quote; the unselected options become history.

38.8 AI Co-Pilot Behavior ¶

The AI co-pilot panel in the quote builder (analogous to the booking-flow co-pilot in §20.4) helps the agent:

  • Suggest a third option given two ("here's a budget alternative")
  • Auto-fill line items from cached pricing (per §33.2)
  • Generate pros/cons for each option based on conversation context and customer memory
  • Draft the customer_facing_intro and recommendation_rationale
  • Validate that the options actually differ meaningfully (warn if three options are essentially the same booking)

Co-pilot generations pass through §10 supervisor preflight. Agent retains full edit rights — co-pilot proposes, doesn't commit.

38.8.1 Customer-side AI ¶

When the customer views the quote, an AI chat panel is available to answer questions about the options. The AI persona is the same one assigned to the conversation; the quote options are loaded into the AI's context as structured data so it can answer questions like "what's the cabin size difference?" or "which has the better itinerary?" with reference to the actual options shown. RAG retrieval per §21 supplements with ship-specific facts.

38.10 Calls Worth Flagging ¶

  • Migration spans multiple deploys. The expand-migrate-contract pattern in §38.2.3 takes 2–3 deploy cycles. Build prompt sequencing matters: do not write code that assumes quote_options is the only source of truth until after step 4 (read switchover) completes.
  • 5-option cap is a soft UX decision. Schema permits any positive integer. The 5 cap is UI-side. Real-world agents who want 6 options would face a decision about extending the cap vs splitting into two quotes. Defer until tenant feedback.
  • Line-item validation strictness. Requiring line items to sum exactly to total_amount_cents protects data integrity but may frustrate agents who copy-paste fare info from host systems with minor rounding artifacts. Suggest a $1 tolerance window with a warning rather than a hard reject.
  • Customer-side AI access to all option data. Loading all options into AI context for chat means the AI can answer comparison questions but also means the AI's response generation cost scales with option count. Per-quote AI cost should be tracked separately (per §27) for cost attribution.
  • Per-option view tracking would let agents see "customer viewed option 3 most" and inform follow-up. Schema field (option_viewed_at) is mentioned but not added in v1 — defer if no clear demand.
  • Option labels are free-text. "Budget pick", "Best value", "Splurge" are example labels. Tenants will use varied conventions ("Family-friendly", "Romantic", etc.). No standardization required; labels are display-only.
  • Selecting an option locks the booking path. Once a booking is initiated against an option, changing the selected option requires the agent to intervene. This is correct behavior but should be clearly communicated in the customer-facing copy: "By clicking Select, you'll be taken to the booking flow for this option."
  • Quote-to-booking attribution carry-through. Per §35.6.2, the booking's conversion-touch is read fresh from the contact's latest touch, not copied from the quote. Multi-option quotes don't change this; the customer's session at the moment of "Select this" provides the conversion touch.
