Section 11 — Customer Memory

Memory gives the AI continuity across conversations. A returning customer doesn’t have to re-explain their travel preferences, family composition, or accessibility needs. Memory is tenant-scoped, customer-controlled, and respects opt-out.

11.1 Memory Storage ¶

CREATE TABLE public.customer_memories (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

tenant_id UUID NOT NULL REFERENCES public.tenants(id),

user_id UUID NOT NULL REFERENCES public.users(id),

contact_id UUID REFERENCES public.contacts(id),

– Structured data

preferences JSONB, – cruise lines, ports, cabin types, dining

travel_history JSONB, – past trips taken

family_composition JSONB, – partners, children (DOBs not ages), notable companions

accessibility_needs TEXT,

dietary_restrictions TEXT,

loyalty_programs JSONB,

important_dates JSONB, – anniversaries, birthdays

notes_freeform TEXT,

– Rapport (per §24 tone matching)

rapport_tone_level INTEGER DEFAULT 2 CHECK (rapport_tone_level BETWEEN 1 AND 5),

rapport_signals JSONB,

rapport_level_set_at TIMESTAMPTZ,

– Lifecycle

last_extracted_at TIMESTAMPTZ,

conversation_count INTEGER DEFAULT 0,

created_at TIMESTAMPTZ DEFAULT NOW(),

updated_at TIMESTAMPTZ DEFAULT NOW(),

UNIQUE (tenant_id, user_id)

);

11.1.1 Scope discipline ¶

The UNIQUE (tenant_id, user_id) constraint is the schema-level guarantee of memory isolation: a single user has exactly one memory row per tenant. Cross-tenant leak (a fact from tenant A's conversation written to tenant B's memory row) is impossible at the constraint level — the wrong tenant_id would produce a violation or an INSERT into a different row.

But the constraint only catches scope violations at write time. Read and update paths are protected by:

  • RLS policies per §5.1 (auth_user_in_tenant + tenant_is_active for writes).
  • The tenantClient proxy per §5.4.3 (auto-filters every query by tenant_id).
  • The extraction job's explicit scope contract per §11.2.2.

All three together. Removing any one is a regression.

11.2 Memory Extraction ¶

Memory extraction is the Inngest-driven background job that updates customer_memories from conversation content. The job's correctness depends on strict tenant scoping — a bug in scope handling produces the worst-case privacy bug shape (one tenant's customer facts written to another tenant's memory row). This subsection specifies the scoping contract and the debounce behavior.

11.2.1 Trigger conditions ¶

Extraction is enqueued when EITHER:

  • The conversation reaches a multiple of 10 messages.
  • The conversation enters a closed or abandoned state.

Enqueuing produces an Inngest event with tenant_id, conversation_id, user_id populated from the conversation row at enqueue time. The event's tenant_id is the authoritative tenant scope for the extraction — NOT the user's "current" tenant or the calling request's tenant.

11.2.2 The mandatory scope contract ¶

Extraction runs inside withPlatformAdminAudit is INCORRECT — it is a tenant-scoped operation, not a platform-admin one. The correct pattern:

export const extractMemory = inngest.createFunction(
  { id: 'customer-memory-extraction' },
  { event: 'conversation.memory_extract_requested' },
  async ({ event, step }) => {
    // tenant_id is sourced ONLY from the event payload.
    const ctx = await tenantContextFromInngestEvent(event);
    const db = tenantClient(ctx);

    // Every query MUST go through `db`. The proxy auto-injects
    // `tenant_id = ctx.tenant_id`. No raw service-role calls allowed
    // by the lint rule in §26.3a.
    const conversation = await step.run('fetch-conversation', async () => {
      return db
        .from('conversations')
        .select('id, user_id, status')
        .eq('id', event.data.conversation_id)
        .single();
    });

    // CRITICAL: assert the conversation's tenant matches the context.
    // The query above is already auto-filtered by tenant_id, so a
    // mismatched conversation_id would return zero rows (not a row
    // from another tenant). The assertion is defense in depth.
    if (!conversation.data || conversation.data.user_id !== event.data.user_id) {
      throw new Error('Conversation/user/tenant mismatch in extraction');
    }

    // ... rest of extraction ...

    // Write goes through `db` too — auto-scoped to tenant_id.
    await step.run('update-memory', async () => {
      return db
        .from('customer_memories')
        .upsert({
          tenant_id: ctx.tenant_id,
          user_id: event.data.user_id,
          // ... fields ...
        });
    });
  },
);

What this gets us:

  • Single source of tenant_id: the event payload. Not the user's default tenant, not the calling request's host header, not a derived field.
  • Auto-scoping at the query layer. Even if a developer writes a bare db.from('conversations').select(...) without an explicit tenant_id filter, the tenantClient proxy from §5.4.3 adds the filter. A cross-tenant read returns zero rows, not someone else's data.
  • Defense-in-depth assertion. The handler also explicitly verifies the conversation row's user_id matches the event's user_id. Belt-and-suspenders against a future change to the tenantClient proxy.
  • Inngest event_id audit trail. Every extraction run is traceable to the event that triggered it. Forensic investigations can ask "which extraction job processed conversation X?" and answer it from the audit log via §26.5.

11.2.3 Debounce ¶

A customer who sends 100 messages in 5 minutes would otherwise trigger 10 extraction jobs. Each job is a Haiku call. Debounce coalesces these:

  • The Inngest event handler checks customer_memories.last_extracted_at for the (tenant_id, user_id) row.
  • If last_extracted_at is within the last MEMORY_EXTRACTION_DEBOUNCE_SECONDS (default 120 — env var per §28.16), the handler exits without running extraction. The new state is processed by the next natural trigger.
  • This is rate-limit-by-design, not by-default — implementations must enforce it. The lint rule in §30.8 verifies that the extraction function reads last_extracted_at before issuing a Haiku call.

11.2.4 Optimistic locking on memory merge ¶

Multiple extraction jobs can race for the same (tenant_id, user_id) row (rare with debounce in place, possible during the debounce window). The merge step uses optimistic locking:

// Read current memory with its updated_at timestamp.
const current = await db
  .from('customer_memories')
  .select('*, updated_at')
  .eq('user_id', event.data.user_id)
  .single();

// Merge extracted facts into the current memory JSONB structures.
const merged = mergeMemory(current.data, extracted);

// Conditional update: only commit if updated_at hasn't changed.
const result = await db
  .from('customer_memories')
  .update({ ...merged, updated_at: new Date().toISOString() })
  .eq('user_id', event.data.user_id)
  .eq('updated_at', current.data.updated_at)
  .select();

if (!result.data || result.data.length === 0) {
  // Another extraction job committed between our read and write.
  // Re-enqueue with a small delay.
  await inngest.send({
    name: 'conversation.memory_extract_requested',
    data: event.data,
    ts: Date.now() + 5000,
  });
  return;
}

The optimistic-lock retry uses Inngest's natural retry/event-send mechanism rather than a tight loop — keeps the function simple and plays well with Inngest's observability.

11.2.5 Process ¶

  • Take the last N messages from the conversation (N = 50 default; configurable via env per §28.16).
  • Plus current customer_memories row content for the (tenant_id, user_id).
  • Haiku prompt: "Extract any new facts or updates about this customer; return structured JSON."
  • Result merged with existing memory using the optimistic-locking pattern in §11.2.4.

11.2.6 Calls Worth Flagging ¶

  • tenant_id source must be event payload, never derived. A helpful refactor that derives tenant_id from the conversation's user_id lookup is a bug — it removes the explicit "what tenant is this extraction for" decision from the path. The Inngest event is the authoritative scope.
  • The proxy auto-filter is the primary defense; the assertion in the handler is defense-in-depth. Both layers matter. If the proxy is ever bypassed (a bug in tenantClient, a future refactor that uses raw service role), the handler-level assertion catches it.
  • Debounce trades freshness for cost. A customer sending a flurry of messages won't have all those facts in memory immediately. For pre-cruise email personalization, the next natural extraction (conversation close, next 10-message boundary) catches up. Acceptable trade-off; document in tenant-facing copy where memory freshness matters.
  • Optimistic locking with re-enqueue is preferable to row-level DB locks for this workload. Locks held during a Haiku call (several seconds) are too long; optimistic-lock-and-retry handles contention cleanly.

11.3 Customer-Facing Memory Controls ¶

Customer can view, edit, and delete their memory at /settings/memory. Memory respects:

  • memory_opt_out flag on users — disables memory extraction entirely for that customer
  • Individual field editing — customer can correct or remove specific facts
  • Full memory deletion — clears all memory for this tenant
  • Per-tenant isolation — memory in tenant A invisible to tenant B

11.5 DOBs Not Ages ¶

Memory and CRM store dates of birth, never ages. Ages are computed at sailing date for booking validation (cruise lines have age rules for kids, drinking, etc.). The DOB lifecycle for estimated entries is specified below to prevent old estimates feeding into personalization indefinitely.

Storage shape

{
  "first_name": "Mike",
  "date_of_birth": "1985-01-01",
  "date_of_birth_is_estimated": true,
  "estimation_basis": "customer said 'about 40' on 2025-03-15",
  "estimation_recorded_at": "2025-03-15T14:23:00Z",
  "estimation_last_reprompt_at": null
}

Visual marker for estimated DOBs

Every UI rendering of an estimated DOB MUST include a visual marker:

SurfaceRendering
CRM contact detail view"(estimated, click to confirm)" link next to the DOB field
Booking submission gate (§20)"We need to confirm Mike's exact birthday before submitting — please ask Mike to verify"
Pre-cruise emails (§23)DOB-derived content (e.g., "celebrating Mike's 40th") is SUPPRESSED for estimated DOBs
Quote PDFsEstimated DOBs not rendered at all
Customer-facing memory view (§11.3)"(approx)" badge next to the DOB
Agent conversation context (§9)Persona instructed to never assert facts about birthdays for estimated DOBs

The principle: estimated DOBs participate in eligibility decisions but NOT in personalization content. Saying "celebrating Mike's milestone birthday!" when Mike's DOB is estimated risks an awkward customer experience if the estimate was off.

Aging-out and re-prompting

If an estimated DOB is:

  • Older than 365 days from estimation_recorded_at, AND
  • Never confirmed (no booking submitted that locked in the actual DOB via §20's confirmation gate), AND
  • The associated customer is still in active conversation with the tenant (any message in the last 90 days),

then on the customer's next conversation turn, the AI is prompted (via persona system prompt augmentation) to gently re-confirm:

"I have a quick reminder — when we first chatted, you mentioned Mike was around 40. For trip planning we should have an exact birthday — would you mind sharing it (or noting if my estimate was off)?"

The re-prompt is generated by the persona in-character. After the customer responds:

  • If they provide an exact DOB: date_of_birth_is_estimated = false, estimation_basis cleared, date_of_birth updated.
  • If they decline or ignore: estimation_last_reprompt_at = NOW(). No further re-prompt for another 365 days.

Background cleanup

Inngest cron dob-estimate-reprompt-eligible runs nightly:

  • Finds customer_memories rows where any family member has date_of_birth_is_estimated = true AND estimation_recorded_at < NOW() - 365 days AND (estimation_last_reprompt_at IS NULL OR estimation_last_reprompt_at < NOW() - 365 days).
  • Sets awaiting_dob_reprompt: true flag on the customer_memories row.
  • On the customer's next conversation turn, the persona prompt augmentation logic (per §9.7) reads this flag and includes the re-prompt instruction.
  • The flag clears once a re-prompt has been issued.

A customer who hasn't conversed with the tenant in 90+ days is not re-prompted — no point waking up a dormant relationship to ask about a birthday.

Schema

ALTER TABLE public.customer_memories
  ADD COLUMN awaiting_dob_reprompt BOOLEAN NOT NULL DEFAULT FALSE;

The estimation tracking fields live inside the family_composition JSONB per §11.1; this adds the gate flag for fast read by the conversation handler.

Calls Worth Flagging

  • Suppression in pre-cruise emails is the most important UX guard. A "celebrating Mike's 40th!" email when Mike is actually 38 is annoying; when Mike is actually 47, worse.
  • Re-prompt cadence (365 days) is generous. Re-prompting every 90 days creates conversation friction.
  • The persona delivers the re-prompt, not a system message. Fits the chat.
  • Estimated DOBs persist through customer deletion grace. On CCPA deletion, treated same as confirmed DOBs per §25.4a.

11.6 Anonymous-to-Authenticated Transfer ¶

Anonymous customers can chat for a limited number of messages before sign-up is required per §24.8. When they sign up, the platform offers explicit consent to transfer the anonymous session into their authenticated identity. The consent UX has three properties: preview before accept, distinct from sign-up flow, and 24-hour reversibility.

Flow

Anonymous user chats ──► identifier limits per §24.8
  │
  ▼
Sign-up prompt ──► User completes OAuth
  │
  ▼
Consent screen with PREVIEW:
  "We saved your previous conversation. Want to keep it?
   You'll be able to continue where you left off.
   You can undo this within 24 hours."

   [Preview shows: N messages, time range, first ~20 words of each]
   [Yes, keep it]  [No, start fresh]
  │
  ▼
On Yes: anonymous_session_id soft-linked to user_id with
        transfer_soft_commit_at = NOW()
  │
  ▼
Memory extraction + CRM contact creation deferred 24 hours
  │
  ├──► User does nothing for 24h: soft commit becomes hard commit;
  │    memory extraction proceeds; CRM contact created if applicable
  │
  └──► User clicks "Undo transfer" in settings within 24h:
       soft commit reverted; conversation re-anonymized; no
       downstream processing has happened

On No: anonymous session marked discarded; purged at retention.

Preview rendering

The consent screen MUST show:

  • Total message count being transferred.
  • Time span of the conversation (first message → last message).
  • The first ~20 words of each message (truncated, not full content).
  • A note: "These messages will be available to you and to your trip consultant (if you book through this organization). If anything in these messages was personal or sensitive, you can choose 'No, start fresh.'"

The preview is the H-3 fix: a user who clicked through a generic "keep your conversation?" prompt without thought now sees what's about to be associated with their authenticated identity.

24-hour soft commit

After the user clicks "Yes, keep it":

  • anonymous_sessions.transfer_soft_commit_at = NOW(), anonymous_sessions.transferred_to_user_id = user_id.
  • The session is now associated with the user — they can continue the conversation immediately.
  • BUT: downstream processing that creates derived data is DEFERRED for 24 hours.

Deferred-processing rule

For 24 hours after transfer_soft_commit_at, the following do NOT execute against the transferred messages:

  • Memory extraction (extractMemory per §11.2).
  • CRM contact creation.
  • Pre-cruise email scheduling.
  • Persona memory updates beyond what's needed to keep the conversation flowing.

If the user invokes "Undo transfer" within 24h:

  • anonymous_sessions.transfer_soft_commit_at = NULL, anonymous_sessions.transferred_to_user_id = NULL.
  • The conversation is moved back to anonymous-session state with the user's authenticated session unaffected. The user can start fresh immediately.
  • No derived data needs cleanup — the deferred-processing rule ensured none was created.

After 24h elapses without an undo:

  • anonymous_sessions.transfer_committed_at = NOW().
  • Inngest job transfer-finalize fires, running the deferred processing.
  • Subsequent thumbs / feedback / memory updates apply normally.

Where the "Undo" affordance lives

A persistent banner at the top of /settings/conversations for the 24h post-transfer window:

"We saved your previous (pre-signup) conversation with [Persona Name] from [DateTime]. [Undo this transfer] (available for [N hours] more)"

After 24h, the banner disappears and the link is replaced with "Transfer made permanent on [DateTime]."

Schema additions

ALTER TABLE public.anonymous_sessions
  ADD COLUMN transfer_soft_commit_at TIMESTAMPTZ,
  ADD COLUMN transferred_to_user_id UUID REFERENCES public.users(id),
  ADD COLUMN transfer_committed_at TIMESTAMPTZ,
  ADD COLUMN transfer_undo_count INTEGER NOT NULL DEFAULT 0;

CREATE INDEX anonymous_sessions_pending_commit_idx
  ON public.anonymous_sessions(transfer_soft_commit_at)
  WHERE transfer_soft_commit_at IS NOT NULL
    AND transfer_committed_at IS NULL;

Audit

Every undo writes to audit_log with action = 'session_transfer.undone', changes snapshot of message count and time range.

Calls Worth Flagging

  • 24h is the right window length for "I clicked through without thinking." Longer creates a long tail of pending commits; shorter doesn't accommodate users who returned next morning to reconsider.
  • Deferred-processing simplifies undo dramatically. Without it, undo would need to "un-extract memory," "delete CRM contact," etc. With it, undo is "set columns to NULL."
  • The preview is the H-3 fix; the undo is the safety net. Both are required.
  • transfer_undo_count is signal-not-surfaced. Logged for future observation if a customer pattern of "consent → undo → re-consent" emerges.

11.7 Memory Audit ¶

All memory changes audit-logged: who changed what when (customer self-edit, AI extraction, agent edit). 7-year retention.

11.8 Memory and CRM ¶

Memory is for the AI’s conversational context. CRM (§12) is for structured records used by agents. They share some data (DOB, dietary, accessibility) but serve different purposes. Updates to one don’t automatically propagate to the other unless explicitly handled in the data flow.
