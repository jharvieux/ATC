Section 40 - Addendum — Non-Cruise Line Items

Status: Addendum. Lands after Part 1–9 build prompts and the preceding addenda. Extends the booking record to support tracking of non-cruise ancillary items (flights, hotels, transfers, excursions, insurance) sold alongside or independently of a cruise. References existing sections by number; does not modify them in place.

Why an addendum, not a retrofit: The core platform is cruise-centric. Real-world agents sell flights, hotels, and transfers as supplemental items — sometimes through cruise-line packages, sometimes through other suppliers. Tracking these matters for commission accounting, customer service, and the itinerary display. This addendum adds the data model without building a full multi-product booking flow (out of scope).

40.1 Overview ¶

A booking (per §5 and §20) is anchored to one cruise. The booking can have ancillary line items representing other components of the trip:

  • Flights (one or more flight segments to/from embarkation/disembarkation ports)
  • Hotels (pre-cruise night, post-cruise night, mid-cruise hotels if applicable)
  • Transfers (airport-to-port shuttles, private car services)
  • Shore excursions (port-day activities — booked directly with cruise line OR with an independent operator)
  • Travel insurance (if separate from the cruise line's policy)
  • Other (visa fees, parking, miscellaneous)

Each line item is tracked with: supplier, cost, commissionability, sale price, commission rate (if applicable), booking reference, and commission lifecycle (matching the cruise's commission model where the line item carries commission).

This is NOT a full booking flow for non-cruise items. The agent typically books these directly with the supplier and records the result in the platform for tracking. A future addendum could add direct booking integrations for major suppliers (Sabre/Amadeus for flights, Expedia partners for hotels). For now, this section captures the data model and basic UI for manual entry.

40.2 Schema ¶

40.2.1 booking_line_items table ¶

CREATE TABLE public.booking_line_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),
  booking_id UUID NOT NULL REFERENCES public.bookings(id) ON DELETE CASCADE,

  -- Type and description
  item_type TEXT NOT NULL CHECK (item_type IN (
    'flight','hotel','transfer','excursion','insurance','other'
  )),
  description TEXT NOT NULL,           -- "United UA 123 LAX→FLL", "Hyatt Regency Miami 1 night"

  -- Supplier
  supplier_name TEXT,                  -- "United Airlines", "Hyatt", "Viator"
  supplier_booking_ref TEXT,           -- airline confirmation, hotel confirmation, etc.
  is_cruise_line_supplied BOOLEAN NOT NULL DEFAULT FALSE,
                                       -- TRUE when the cruise line itself sold the item
                                       -- (e.g., cruise-line flights, cruise-line excursions)

  -- Dates (semantically per-item)
  start_date DATE,
  end_date   DATE,
  -- For flights: start_date=departure, end_date=arrival
  -- For hotels: start_date=check-in, end_date=check-out
  -- For excursions: start_date=end_date=activity date
  -- For insurance: start_date=coverage start, end_date=coverage end

  -- Money (cents — §14.0 rules)
  customer_cost_cents BIGINT NOT NULL DEFAULT 0,        -- what the customer paid
  supplier_net_cents  BIGINT,                           -- what the supplier received (when known)
  commissionable BOOLEAN NOT NULL DEFAULT FALSE,
  commission_rate NUMERIC(5,4),                          -- rate for this item, e.g., 0.10 for 10%
  expected_commission_cents BIGINT,                      -- computed: customer_cost * commission_rate
  received_commission_cents BIGINT NOT NULL DEFAULT 0,   -- updated on §14.8 reconciliation
  currency TEXT NOT NULL DEFAULT 'USD',

  -- Lifecycle
  status TEXT NOT NULL DEFAULT 'planned'
    CHECK (status IN ('planned','booked','confirmed','cancelled','completed')),
  cancellation_reason TEXT,

  -- Item-specific structured data (JSONB to avoid type-per-table sprawl)
  -- Shape varies by item_type — see §40.3
  item_details JSONB,

  -- Audit
  created_by_user_id UUID REFERENCES public.users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX bli_booking_idx ON public.booking_line_items(booking_id);
CREATE INDEX bli_tenant_type_idx ON public.booking_line_items(tenant_id, item_type);
CREATE INDEX bli_supplier_ref_idx
  ON public.booking_line_items(tenant_id, supplier_booking_ref)
  WHERE supplier_booking_ref IS NOT NULL;

ALTER TABLE public.booking_line_items ENABLE ROW LEVEL SECURITY;
-- RLS per §5.1.

40.2.2 Why a single table with type discriminator ¶

Alternative was a table per item type (booking_flights, booking_hotels, etc.). Rejected because:

  • Aggregating across types (total ancillary revenue, total commission) requires UNION queries.
  • Type set will expand over time (cruise-only line, package, prepaid gratuities); per-table approach forces schema migrations.
  • Item-specific fields are bounded and JSONB-friendly. Indexed where queried; otherwise carried.

40.4 Commission Handling ¶

40.4.1 When line items carry commission ¶

Whether a line item is commissionable depends on supplier and the agent's relationship with that supplier:

  • Cruise-line-supplied items (is_cruise_line_supplied = TRUE) — flights, transfers, excursions, hotels booked through the cruise line typically generate commission, often at the same rate as the cruise itself or at a separate published rate. The host adapter (per §13) may provide the rate, or the agent enters it.
  • Third-party items — flights booked through Sabre, hotels through Booking.com or Expedia TAAP, etc. Commissionable if the agent has an account with that supplier. The agent enters the rate manually for now (future adapter integration could automate).
  • Non-commissionable items — direct-purchase items the customer bought themselves (the agent records for itinerary purposes but earns nothing).

40.4.2 Commission rollup into the cruise booking commission ¶

The cruise booking's commissions row tracks the cruise commission. Non-cruise line item commissions are tracked separately per line item (booking_line_items.expected_commission_cents and received_commission_cents). The booking's total commission view in the CRM is the SUM:

SELECT
  b.id AS booking_id,
  -- Cruise commission (existing per §14)
  c.gross_commission_cents AS cruise_gross_cents,
  c.net_commission_cents   AS cruise_net_cents,
  -- Ancillary commission (this addendum)
  COALESCE((
    SELECT SUM(expected_commission_cents)
    FROM public.booking_line_items
    WHERE booking_id = b.id AND commissionable = TRUE
  ), 0) AS ancillary_expected_cents,
  COALESCE((
    SELECT SUM(received_commission_cents)
    FROM public.booking_line_items
    WHERE booking_id = b.id
  ), 0) AS ancillary_received_cents,
  -- Combined
  c.gross_commission_cents
    + COALESCE((SELECT SUM(expected_commission_cents) FROM public.booking_line_items
                WHERE booking_id = b.id AND commissionable = TRUE), 0)
    AS total_expected_cents
FROM public.bookings b
LEFT JOIN public.commissions c ON c.booking_id = b.id
WHERE b.id = :booking_id;

40.4.3 Line-item commission reconciliation ¶

For cruise-line-supplied items where the host pays commission on the entire package (cruise + flights + excursions), the host's statement may aggregate everything into one cruise-level commission amount. In that case, the line items are tracked for visibility but their individual received_commission_cents values remain 0 — the cruise's commissions.received_commission_cents captures the aggregate.

For third-party items (Viator excursion, separate hotel through Booking.com), commission is paid separately by that supplier directly to the agent. Statement reconciliation per §14.8 applies the same matching pattern — provider_booking_ref exact match preferred, fuzzy match fallback — but matches against booking_line_items.supplier_booking_ref rather than (or in addition to) commissions.booking_id.

40.4.4 Commission state on line items ¶

Simplified compared to the cruise commission state machine in §14:

  • expected_commission_cents is computed when the line item is set to commissionable with a rate
  • received_commission_cents is updated by the reconciliation flow (manual or imported statement)
  • Variance between expected and received is surfaced in the CRM but doesn't have the formal §14.8 hold-states; line item commission is lower-value and lower-volume than cruise commission

Clawbacks: the §34.8 clawback fields (clawback_amount_cents, clawback_at, clawback_reason) added to the commissions table are NOT mirrored on booking_line_items in v1. If a third-party supplier claws back commission on a line item, the agent decreases received_commission_cents manually and notes the reason in the line item's description or via audit_log. Adequate for v1 volume; revisit if line-item clawback frequency increases.

40.5 UI / Agent Workflow ¶

40.5.1 On the booking detail page ¶

A "Trip Components" section lists all line items grouped by type. Each row shows description, dates, supplier, status, customer cost, commission (if applicable). "+ Add component" button opens a modal:

  1. Pick item_type (flight / hotel / transfer / excursion / insurance / other)
  2. Form adapts to the type-specific fields (per §40.3 shapes)
  3. Supplier dropdown — autocomplete from known suppliers; "+ new supplier" to add one not in the list
  4. Commission section — commissionable toggle, rate input, auto-computed expected commission
  5. Save

40.5.2 AI-assisted entry ¶

The AI co-pilot can extract line item data from forwarded confirmation emails (hooks into the §34 import pipeline). A forwarded "United UA1234 confirmation" email with IMPORT trigger is classified as a booking-related document, and if the platform detects an associated cruise booking for the same customer, the parsed flight data is offered as a new line item. The agent accepts/edits/rejects per §34.6 review queue.

40.5.3 Bulk view across bookings ¶

A "Components" view in the CRM nav (separate from the bookings list) shows all line items across the agent's bookings with filters by type, status, supplier, date range. Useful for end-of-month commission planning ("which suppliers do I expect commission from?") and for tracking suppliers' performance.

40.6 Display on the Itinerary ¶

The trip itinerary per §39.2 integrates non-cruise line items:

  • Flights — appear in a "Getting there & back" section at the start (outbound) and end (return) of the itinerary
  • Pre-cruise hotels — appear in "Getting there" alongside flights
  • Transfers — appear in transition zones (airport-to-port, port-to-airport)
  • Excursions — appear on the corresponding port day in the day-by-day itinerary
  • Post-cruise hotels — appear in "Heading home" section
  • Insurance — appears in the trip resources page (per §39.3), not in the itinerary body, since it's a reference document rather than an itinerary event
  • Other — agent decides where to show it via item-level "include in itinerary" toggle; defaults to suppressed

40.7 Cancellation Handling ¶

When a cruise booking is cancelled, the agent is prompted to decide what to do with each line item:

  • Cancel — set line item status to cancelled, record cancellation_reason
  • Keep — line item retained as-is (e.g., a hotel booking the customer still wants to use)
  • Convert to standalone — line item detached from the cancelled booking and attached to a new placeholder booking representing the customer's adjusted travel plans. Implementation: requires a "trip-only" booking type that has no cruise; deferred to a future iteration. v1: leave the line item on the cancelled booking and let the agent handle outside the platform.

Cancelled line items affect the §36.7 "Lost revenue from cancellations" report:

  • Lost ancillary expected commission contributes to the total lost-expected measure
  • If line item commission was already received and is now clawed back, the agent updates received_commission_cents downward and the change flows to the report's net financial impact

40.9 Calls Worth Flagging ¶

  • Cruise-line-supplied items vs third-party items create an accounting fork. Cruise-line packages typically pay one aggregate commission; third-party items pay separately. Tenants need to understand this when entering data, or the totals will mislead them. The line item form should make is_cruise_line_supplied prominent with a clear explainer.
  • No standalone trip bookings in v1. An agent who sells a flight without a cruise has no place to put it in v1. They could record a "ghost" cruise booking but that pollutes booking metrics. Acceptable v1 limitation; revisit if user demand emerges.
  • JSONB item_details is unindexed for arbitrary querying. Reports that need to filter on, say, "all flights to LAX" require a JSONB path expression and won't be fast at scale. Tradeoff accepted for schema flexibility; if specific dimensions become hot, promote them to columns.
  • Supplier-name normalization. "United Airlines" vs "United" vs "UAL" — without normalization, reports group inconsistently. v1 stores whatever the agent types. A normalized supplier table is a candidate for a future addendum.
  • Date semantics differ by item_type. The start_date/end_date columns mean different things for different types. The validation layer should enforce type-appropriate populations (e.g., excursion must have start_date = end_date).
  • Commission reconciliation for third-party items may require fetching statements from Viator, Booking.com, etc. — none of which have the structured integrations cruise host adapters provide. v1: agents enter received commission manually. Future: per-supplier statement parsing per §34.5.4.
  • Round-trip flights can be entered as one line item (with return_* fields) or two separate line items. Both shapes valid; UI should pick a default and let the agent override. Recommend: single round-trip line item by default for simpler totals.
  • Excursion bookings are often paid for directly by the customer on-board. Tracking them in the platform is useful for itinerary completeness but the commission situation is muddy (cruise line may pay agent commission on shipboard excursion sales, depending on host policy). Document carefully.
  • Insurance is a special case. Some insurers pay commission, some don't. Some are sold as part of the cruise (commissionable through the host), some as separate policies. The shape supports both; agent enters as appropriate.
  • Itinerary display ordering (per §40.6) is a UX recommendation, not a hard schema rule. The itinerary renderer in §39 needs to interleave cruise itinerary days with non-cruise line items based on their dates. Build coordination required.
