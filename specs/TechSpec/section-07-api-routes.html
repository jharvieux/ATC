7.9 Conventions ¶

  • Rate limiting: per-user (100/hour default), per-tenant, per-IP (anonymous)
  • Idempotency: critical mutations accept Idempotency-Key header (24-hour cache)
  • Streaming: chat uses Server-Sent Events (SSE) with Last-Event-ID for reconnect
  • Authorization: every protected route runs assertPermission() at handler entry
  • Audit logging: significant operations write to audit_log table

7.9a Stripe Webhook Handler Contract ¶

Every Stripe webhook handler — /api/webhooks/stripe/platform and /api/webhooks/stripe/connect — follows this contract. Failure to follow it produces duplicate-processing bugs that, for payment events, move real money twice. The contract is enforceable: integration tests per §30.8 verify a same-event-id delivered twice produces exactly one side-effect.

Step sequence

  1. Verify Stripe signature using the endpoint-specific webhook secret per §28.7. Reject with 400 on invalid signature; Stripe will not retry.
  2. Atomic dedup insert into public.stripe_webhook_events:

```ts const { data, error } = await db .from('stripe_webhook_events') .insert({ stripe_event_id: event.id, event_type: event.type, endpoint: endpointName, // 'platform' | 'connect' raw_event: event, processing_started_at: new Date().toISOString(), }) .select('id') .single();

if (error?.code === '23505') { // Unique violation on stripe_event_id — event already processed. // Return 200 OK to Stripe; do nothing else. return new Response('OK', { status: 200 }); } if (error) { // Different error — return 5xx so Stripe retries. return new Response('error', { status: 500 }); } ```

  1. Process the event in a function-level try/catch. The processing logic varies by event type — commission record updates, subscription state changes, transfer reconciliation, etc.
  2. Mark completion by updating the row with processing_completed_at, processing_outcome, and (for failures) error_detail. This is the audit record of "yes we handled this."
  3. Return 200 to Stripe. Stripe will not retry a 200-OK event.

Why the dedup insert is FIRST (not after signature verification)

Signature verification rejects forged events; dedup catches legitimate retries from Stripe. These are independent concerns. The order matters: signature first (cheap, syntactic), dedup second (transactional, before any business logic).

Why "Return 200 on duplicate" rather than "return 5xx and let Stripe retry forever"

A duplicate Stripe event is Stripe doing its job — retrying after a network blip on our side. Returning 200 stops the retry loop. We already have the event recorded.

Linking transfers back to payouts

For events from §14.7 (Stripe Connect transfers), the processed_idempotency_key column is populated from the event's metadata. The format payout-{payout_records.id}-gen{attempt_generation} lets reconciliation queries link:

-- "Did the transfer for payout X succeed?"
SELECT pr.id, pr.status, swe.event_type, swe.created_at
FROM public.payout_records pr
LEFT JOIN public.stripe_webhook_events swe
  ON swe.processed_idempotency_key =
     'payout-' || pr.id || '-gen' || pr.attempt_generation
WHERE pr.id = '<payout_id>'
ORDER BY swe.created_at;

Handlers MUST be idempotent in their own right

The dedup table catches Stripe-side retries. It does NOT catch our own bugs (handler crashes after partial state mutation; on retry the row exists but processing_outcome is unset). Handlers should be designed to be safely re-runnable, treating processing_completed_at IS NULL as "may need to re-run" and recovering gracefully.

A reconciliation Inngest job (stripe-webhook-incomplete-reconcile, runs every 15 minutes) finds rows with processing_started_at more than 5 minutes ago and processing_completed_at IS NULL, and either re-runs the handler or escalates to platform admin per the event type.

Retention and cleanup

  • processing_outcome = 'success': retain 90 days then delete.
  • processing_outcome = 'error': retain 1 year (investigation history).
  • processing_outcome = 'duplicate': retain 30 days (mostly noise).
  • processing_outcome = 'unhandled': retain 1 year (these are event types we received but had no handler for — surface for review).

Cleanup cron runs nightly.

Calls Worth Flagging

  • The INSERT ... ON CONFLICT pattern is the correctness gate. Reading first then inserting is a race: between read and insert, another concurrent webhook delivery can land. Atomic insert with unique-constraint-violation handling is the only safe shape.
  • Idempotency-key linkage requires the §14.7 fix to be in place. This handler depends on the deterministic idempotency-key contract from §14.7.
  • The reconciliation job is not optional. Without it, a handler crash mid-processing produces a permanently-stuck row that silently fails to complete. Build it in Phase 1 alongside the webhook handlers themselves.
