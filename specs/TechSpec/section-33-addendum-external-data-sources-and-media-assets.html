Section 33 - Addendum — External Data Sources & Media Assets

Status: Addendum. Lands after all Part 1–9 build prompts are complete. References existing sections by number; does not modify them in place.

Why an addendum, not a retrofit: This work adds external pricing data ingestion, a CruiseMapper-sourced platform corpus for RAG, and a new media-asset retrieval surface. Each touches existing sections (§6, §8, §13, §21, §22, §28) but the existing sections are stable and have build prompts already written. Threading these changes back into completed work would invalidate that work. The addendum keeps Part 1–9 intact and lands the new behavior as a clearly-scoped extension.

33.1 Overview ¶

The platform consumes two categories of external data:

  1. Cruise pricing data — used to give AI agents directional pricing context and to power subscriber-configurable price-watch notifications on existing bookings. Sourced via Apify actors that scrape per-cruise-line booking sites and the Booking.com Cruises aggregator. Not used for booking transactions; bookings under prong 2 (BYO host agency at launch) flow through the booking widget per §20.
  2. CruiseMapper reference data — ship registry, port detail, cruise line, and deck plan content. Ingested into the RAG service at global scope per §8.9. Provides factual grounding for AI agents on ship layouts, port details, and operator metadata. Two ingestion paths: Apify-backed for itineraries (because itineraries cross-cut with pricing) and direct HTTP fetch for static reference content (because CruiseMapper has no anti-bot protection and DIY is cheaper).

A new media-asset surface — deck plan images, ship photos, port maps — is added to the RAG service. Chunks link to assets via a new column; the consumer-side chat UI renders linked assets inline when AI responses include the display markup.

This section defines:

  • The PricingDataSource adapter interface (§33.2) and its Apify implementation (§33.3)
  • The CruiseMapper ingest pipeline (§33.4 Apify itinerary path, §33.5 DIY static path)
  • The new rag_media_assets table and knowledge_chunks.related_asset_ids column (§33.6)
  • The consumer-side display markup convention (§33.7)
  • The price-watch subscription mechanism (§33.8)
  • Operator obligations: ToS, robots.txt, rate limiting, budget caps (§33.9)
  • Environment variables added (§33.10)

33.2 PricingDataSource Adapter Interface ¶

Mirrors the §13 HostAgencyClient pattern: an interface defined in the main app, multiple potential implementations, swappable behind the abstraction.

interface PricingDataSource {
  // Bulk refresh for general directional pricing context. Writes to cache.
  // Called by monthly scheduled Inngest job.
  refreshGeneralPricing(opts: {
    lines: CruiseLineCode[];
    regions: RegionCode[];
    dateRange: { from: Date; to: Date };
  }): Promise<RefreshResult>;

  // Targeted refresh for specific tracked sailings. Groups by (line, region,
  // date-window) and dispatches minimum actor runs. Writes to cache.
  // Called by daily scheduled Inngest job, fed by active price_watches rows.
  refreshTrackedSailings(sailings: SailingKey[]): Promise<RefreshResult>;

  // Read-only cache access. Returns cached price with staleness metadata.
  // Used by AI agents (read-only — agents never trigger refresh) and by the
  // price-watch comparator.
  getCachedPrice(key: SailingKey): Promise<CachedPriceQuote | null>;
}

Key types:

type SailingKey = {
  line: CruiseLineCode;       // e.g., 'RCL', 'NCL', 'CCL'
  ship: string;                // canonical ship slug
  sailDate: string;            // ISO date
  departurePort: string;       // IATA-like port code
  durationNights: number;
};

type CachedPriceQuote = {
  key: SailingKey;
  cabinPrices: Record<CabinClass, { amount: number; currency: string }>;
  fetchedAt: Date;
  source: 'apify' | 'manual' | 'host_adapter';
  stalenessHours: number;     // computed at read time
  freshnessFlag: 'fresh' | 'stale' | 'expired';  // derived from stalenessHours
};

type CabinClass = 'interior' | 'oceanview' | 'balcony' | 'mini_suite' | 'suite';

Discipline points:

  • AI agents and the price-watch comparator MUST only call getCachedPrice. They MUST NOT trigger refresh operations directly. This protects cost and rate limits.
  • The freshnessFlag is computed at read time from stalenessHours against per-line freshness thresholds (configurable; default 72h = fresh, 168h = stale, beyond = expired).
  • The §6.8 pricing-authority cap still applies. When pricing data flows into a RAG chunk (e.g., for general context), the chunk's authority caps at 0.55 regardless of source. AI prompts that include cached prices outside of RAG attribute them as "approximate, last seen {fetchedAt}" per §21.7.

33.3 ApifyPricingAdapter ¶

Default implementation of PricingDataSource. Routes per-line requests to the appropriate Apify actor; normalizes outputs to the internal CachedPriceQuote shape.

Per-line actor routing (verified actor catalog at time of writing — re-verify before build):

LineActor (Apify ID)Notes
Royal Caribbeansercul/royal-caribbean6 markets, cabin-level pricing
Norwegiansercul/norwegian-cruise-scraper5 markets, cabin-level pricing
Princesssercul/princess-cruise-scraperUS, UK
Celebritysercul/celebrity-cruises6 markets
Costasercul/costa-cruises6 markets
Carnival(see Apify catalog)US, AU
Holland America(see Apify catalog)7 markets
MSC(see Apify catalog)5 markets
Disney(see Apify catalog)5 markets
Booking.com Cruises (aggregator fallback)vulnv/booking-cruises-scraperUsed for lines without direct actors

Lines not covered by Apify actors at time of writing (Virgin, Viking, Oceania, Regent, Silversea, Seabourn): adapter returns null from getCachedPrice for these. AI agents handle null per §21.9 (no-result handling). When booking a customer on an uncovered line, no price-watch is available; this is surfaced to subscribers in the price-watch UI.

Adapter responsibilities:

  1. Per-line actor routing. A failed actor run for one line does not affect others.
  2. Batching for daily tracked-sailings refresh. Groups active price_watches rows by (line, region, sail-date-window) and dispatches one actor run per group. The result set is then matched to individual watches by SailingKey.
  3. Normalization. Maps each actor's bespoke output shape to CachedPriceQuote. Adapter-specific mapping code per actor.
  4. Cache writes. Upserts on (line, ship, sail_date, departure_port, duration_nights, cabin_class) composite key. Stamps fetched_at = now().
  5. Cost ceilings. Adapter accepts a per-run budget cap (env var APIFY_RUN_BUDGET_USD_CEILING). On approach, returns partial results with a flag rather than running over.
  6. Kill switch. Env var APIFY_ADAPTER_ENABLED (default true). When false, adapter no-ops all refresh operations. Reads still served from cache. Used during cost incidents or ToS reviews.

Caching substrate: Postgres table pricing_cache in the main app DB. Reuses existing Supabase project. Redis was considered (per Session 3 open item) but rejected for now — pricing data is read-modestly and the write volume is well within Postgres's comfort zone. Revisit if read volume from AI agents creates pressure.

Test seam: A MockPricingDataSource implementation lives alongside the adapter. Returns deterministic fixtures. Used by tests and by local development without burning Apify credits.

33.4 CruiseMapper Itinerary Ingest (Apify Path) ¶

Itineraries cross-cut with pricing data, so they ride the Apify pipeline alongside the per-line scrapers.

Actor: crawlerbros/cruisemapper-cruises-scraper (HTTP-only, no proxy required per actor docs).

Schedule: Monthly, Inngest scheduled function, coordinated with the general-pricing pull to avoid redundant fetches.

Output handling: Itinerary records (ship, line, departure date, route, ports of call, duration) are written to:

  1. pricing_cache for the pricing flow (joined to per-line cabin pricing where available)
  2. A new itineraries table in the RAG service DB (see §33.6) for retrieval as RAG context

Authority tier: low (0.30-0.54) per §6.3. Itinerary data is community-aggregated; ship/line/port factual fields are reliable, but the data should not outweigh tenant-verified or official-source content during retrieval ranking.

33.5 CruiseMapper Static Reference Ingest (DIY Path) ¶

Ship registry, port detail pages, and deck plan pages are fetched directly via HTTP. CruiseMapper publishes these as static HTML with no anti-bot protection.

Why DIY: ~20,000 reference pages quarterly. Apify per-result fees would add unnecessary cost for content that needs no proxy infrastructure. Direct fetch keeps cost near-zero and gives the platform full control over parser logic.

Targets and URL patterns (verify against CruiseMapper at build time):

Content typeURL pattern (approx.)Volume
Ship detailcruisemapper.com/ships/{ship-slug}-{id}~1,500 ships
Deck plan pagecruisemapper.com/deckplans/{ship-slug}-{ship-id}/deck{NN}-{deck-id}~18,000 deck pages
Port detailcruisemapper.com/ports/{port-slug}~700 ports

Ingest pipeline:

[Inngest scheduled function — quarterly]
  │
  ▼
[robots.txt check — verify allowed paths]
  │
  ▼
[Enumerate target URLs — from existing ship/port discovery]
  │
  ▼
[For each URL: HTTP GET with rate limit + ETag/hash check]
  │
  ▼
[Parse HTML (cheerio or equivalent), extract text + image URLs]
  │
  ▼
[Download referenced images, normalize, store in Supabase Storage]
  │
  ▼
[Generate text chunks via §22.4 normalization pipeline]
  │
  ▼
[Write knowledge_chunks (global scope, authority = low) + rag_media_assets]
  │
  ▼
[Link chunks to assets via related_asset_ids]

Polite-scraping discipline (mandatory):

  • Rate limit: ≤1 request/second during initial backfill. ≤0.5 request/second on quarterly refreshes.
  • User-Agent: Must identify the platform and provide a contact email. Format: {PlatformBrand}-RAG-Ingest/1.0 (+mailto:{operations-email}).
  • robots.txt: Checked at the start of every scheduled run. If a previously-allowed path is newly disallowed, the run halts for that path and alerts platform admin.
  • Change detection: SHA-256 hash of the response body stored per URL. On refresh, hash unchanged = skip re-parsing and re-embedding. Saves both compute and OpenAI embedding cost.
  • Backoff: On any 4xx or 5xx response, exponential backoff with jitter; after 3 retries, defer to next run and alert if the failure rate exceeds 5% of the run.
  • Concurrency: Single-threaded for the initial implementation. Concurrency added only if a quarterly refresh fails to complete within its scheduled window.

Parser failure handling: If the parser breaks (CruiseMapper changes HTML structure), the run logs which URL pattern failed, halts further processing of that content type, and alerts platform admin. Other content types continue. The platform admin updates the parser; the next scheduled run resumes.

33.6 Media Assets — Schema & Storage ¶

Adds a new asset surface to the RAG service. Assets are first-class objects, retrievable alongside chunks.

33.6.1 rag_media_assets Table ¶

CREATE TABLE rag.rag_media_assets (
  asset_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  kind              TEXT NOT NULL CHECK (kind IN ('deck_plan','ship_photo','port_map','other')),
  entity_type       TEXT NOT NULL CHECK (entity_type IN ('ship','port','deck','cruise_line')),
  entity_id         TEXT NOT NULL,        -- e.g., ship slug, port slug
  scope             TEXT NOT NULL DEFAULT 'global' CHECK (scope IN ('global','tenant')),
  tenant_id         UUID NULL,            -- non-null only for tenant-scope assets
  source_url        TEXT NOT NULL,        -- original URL on source site
  storage_path      TEXT NOT NULL,        -- path in Supabase Storage bucket
  public_url        TEXT NULL,            -- if public bucket; else null and signed-URL generation used
  caption           TEXT NULL,            -- human-readable caption
  content_type      TEXT NOT NULL,        -- e.g., 'image/png', 'image/jpeg'
  width_px          INT NULL,
  height_px         INT NULL,
  file_bytes        INT NULL,
  file_hash         TEXT NOT NULL,        -- sha256 of file bytes, for change detection
  fetched_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  source            TEXT NOT NULL,        -- 'cruisemapper','tenant_upload', etc.
  CONSTRAINT tenant_id_when_tenant_scope
    CHECK ((scope = 'tenant' AND tenant_id IS NOT NULL)
        OR (scope = 'global' AND tenant_id IS NULL))
);

CREATE INDEX idx_assets_entity ON rag.rag_media_assets (entity_type, entity_id);
CREATE INDEX idx_assets_kind ON rag.rag_media_assets (kind);
CREATE INDEX idx_assets_tenant ON rag.rag_media_assets (tenant_id) WHERE tenant_id IS NOT NULL;

33.6.2 knowledge_chunks.related_asset_ids Column ¶

ALTER TABLE rag.knowledge_chunks
  ADD COLUMN related_asset_ids UUID[] NOT NULL DEFAULT '{}'::UUID[];

When a chunk has linked assets, retrieval returns the asset metadata alongside the chunk. Consumers of the retrieve API may then either ignore the metadata (text-only flows) or feed it into the system prompt for display markup (chat UI flow).

33.6.3 Storage Bucket ¶

  • Bucket name: rag-media-public (Supabase Storage)
  • Access: Public read. Deck plans, ship photos, and port maps are non-PII reference content; public access simplifies serving and avoids signed-URL generation overhead.
  • Tenant uploads (future): a separate rag-media-tenant private bucket with signed URLs is reserved for the tenant-scope asset case, but is not implemented in this addendum. Tenant-scope asset upload is a follow-up.
  • CDN: Supabase Storage's built-in CDN is sufficient at expected volumes. Cloudflare R2 / a separate CDN is a future optimization if egress regularly approaches the included 250 GB/month allowance.

33.6.4 Retrieval API Extension ¶

The /api/retrieve endpoint from §8.4 returns an extended response that includes asset metadata for any linked assets on returned chunks:

{
  "chunks": [
    {
      "chunk_id": "...",
      "text": "Deck 7 of Explorer of the Seas...",
      "authority": 0.55,
      "recency": 0.85,
      "match": 0.91,
      "confidence": 0.79,
      "category": "cabin_intel",
      "source": "cruisemapper.com/deckplans/...",
      "related_asset_ids": ["asset-uuid-1"]
    }
  ],
  "assets": [
    {
      "asset_id": "asset-uuid-1",
      "kind": "deck_plan",
      "entity_type": "deck",
      "entity_id": "explorer-of-the-seas-deck-7",
      "public_url": "https://...supabase.co/.../deck07.png",
      "caption": "Explorer of the Seas — Deck 7 plan",
      "width_px": 1200,
      "height_px": 800
    }
  ]
}

Asset metadata in the response is keyed by asset_id so multiple chunks referencing the same asset don't duplicate the entry.

33.7 Consumer-Side Display Markup ¶

Extends §21.4's RAG knowledge block format with a displayable-assets layer. Does not modify §21.4; appends a new instruction block when assets are present.

33.7.1 Extended System Prompt Block ¶

When at least one retrieved chunk has linked assets, the system prompt includes an additional section:

DISPLAYABLE ASSETS (available for this turn):
- [[display_asset:asset-uuid-1]] — Explorer of the Seas, Deck 7 plan (deck_plan)
- [[display_asset:asset-uuid-2]] — Explorer of the Seas, Deck 7 plan, cabin detail view (deck_plan)

DISPLAY INSTRUCTIONS:
- When your answer references the layout of a specific deck, cabin, or port,
  include the markup `[[display_asset:<id>]]` inline at the point where the
  customer would want to see the image.
- Use sparingly — only when the visual genuinely aids the answer.
- Do not invent asset IDs. Only use IDs from the DISPLAYABLE ASSETS list above.
- One image per response is usually sufficient; do not include more than 3.

33.7.2 Client-Side Rendering ¶

The chat UI parses AI output for [[display_asset:<uuid>]] markup. For each match:

  1. Look up the asset in the assets array returned by the retrieve call for that turn.
  2. Render an inline image element with src = public_url, alt = caption.
  3. If the asset is not in the available set (AI hallucinated an ID), drop the markup silently. Log to telemetry for prompt-tuning.
  4. The image displays with the AI's existing source-indicator UI (§21.6) — same hover-to-expand pattern, showing source URL and freshness.

33.7.3 Fallback to Tool-Call Shape ¶

If during build it is found that AI agents do not reliably emit [[display_asset:<id>]] inline markup, the implementation may fall back to a structured tool-call shape (e.g., AI calls a displayAsset(id) function). The wire format is an implementation detail; the user-visible behavior is identical.

33.7.4 Hallucination Defense Integration ¶

Adds one new check to §21.10's hallucination defense:

  • Layer (new): Asset ID validation. AI-emitted display markup with IDs not in the per-turn available set is dropped silently and logged. Prevents AI from inventing image references.

33.8 Price-Watch Subscriptions ¶

A subscriber (travel agent) may attach a price-watch to any booking they manage. When pricing for that sailing drops by a configurable amount or percentage, the subscriber is notified.

33.8.1 price_watches Table (main app DB) ¶

CREATE TABLE public.price_watches (
  watch_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id         UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  subscriber_user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  booking_id        UUID NULL REFERENCES bookings(id) ON DELETE CASCADE,
  -- Sailing identification (denormalized; survives booking deletion if NULL booking_id)
  cruise_line       TEXT NOT NULL,
  ship              TEXT NOT NULL,
  sail_date         DATE NOT NULL,
  departure_port    TEXT NOT NULL,
  cabin_class       TEXT NOT NULL,
  -- Baseline (the price the subscriber is comparing against)
  baseline_price    NUMERIC(10,2) NOT NULL,
  baseline_currency TEXT NOT NULL,
  baseline_set_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  -- Trigger configuration (set by subscriber when creating the watch)
  threshold_kind    TEXT NOT NULL CHECK (threshold_kind IN ('dollar_drop','percent_drop','either')),
  dollar_threshold  NUMERIC(10,2) NULL,
  percent_threshold NUMERIC(5,2) NULL,        -- e.g., 10.00 means 10%
  -- Lifecycle
  status            TEXT NOT NULL DEFAULT 'active'
                      CHECK (status IN ('active','triggered','paused','expired','cancelled')),
  triggered_at      TIMESTAMPTZ NULL,
  notified_at       TIMESTAMPTZ NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT threshold_present
    CHECK ((threshold_kind = 'dollar_drop' AND dollar_threshold IS NOT NULL)
        OR (threshold_kind = 'percent_drop' AND percent_threshold IS NOT NULL)
        OR (threshold_kind = 'either' AND dollar_threshold IS NOT NULL AND percent_threshold IS NOT NULL))
);

CREATE INDEX idx_watches_tenant_status ON public.price_watches (tenant_id, status);
CREATE INDEX idx_watches_sailing ON public.price_watches (cruise_line, ship, sail_date) WHERE status = 'active';

33.8.2 Watch Lifecycle ¶

active ──┬──► (price check matches threshold) ──► triggered ──► notified
         ├──► (subscriber pauses) ──► paused
         ├──► (sail_date passes) ──► expired
         └──► (subscriber cancels or booking deleted) ──► cancelled

33.8.3 Daily Price Check Job (Inngest) ¶

[Inngest daily scheduled function]
  │
  ▼
[SELECT active price_watches → distinct SailingKeys]
  │
  ▼
[PricingDataSource.refreshTrackedSailings(sailingKeys)]
  │
  ▼
[For each active watch: compare new cached price to baseline]
  │
  ▼
[If threshold met: status='triggered', enqueue notification]
  │
  ▼
[Notification fans out per §23 notification routing]

33.8.4 Notification Target ¶

Notifications go only to the subscriber (the travel agent who created the watch). The subscriber decides whether and how to contact their customer. The platform does not contact the customer directly under prong 2. This is a deliberate decision to preserve the subscriber-owns-the-customer-relationship boundary.

33.8.5 Re-Arming a Watch ¶

Once a watch is triggered and notified, it does not auto-re-arm. The subscriber may re-arm via the UI, which resets baseline_price to the current cached price and sets status back to active. This prevents spam from a sailing that's on a sustained discount.

33.8.6 Booking Re-Pricing Flow ¶

When the subscriber acts on a triggered watch:

  1. Subscriber opens the booking in the platform UI.
  2. UI offers "Open booking widget to adjust" — same widget flow as §20 (booking widget receives auto-populated fields and a flag indicating this is a rebook/re-price action).
  3. Subscriber completes the action in the booking widget. The platform observes the new booking reference and updates the booking record per existing §20 flows.

The platform does not directly modify host-system bookings even when a price drop is detected. This is consistent with the §13 host-adapter discipline.

33.9 Operator Obligations ¶

33.9.1 ToS & Legal Posture ¶

This addendum adds operational responsibilities that did not previously exist for the platform:

  • Per-cruise-line scraping (via Apify): The platform is the operator; Apify and the actor authors are not. The platform accepts the ToS risk of each cruise line whose actor it uses. Before launch, platform counsel reviews this posture and documents the risk acceptance. Cease-and-desist or IP blocking are the realistic worst-case outcomes; the adapter must handle being blocked gracefully (PricingDataSource.getCachedPrice returns stale data with freshnessFlag = 'expired' rather than failing the AI agent).
  • CruiseMapper scraping (DIY): Lower-risk than direct cruise-line scraping (aggregator, publicly published reference data) but still subject to CruiseMapper's ToS. Counsel reviews before launch.

33.9.2 robots.txt Compliance ¶

The DIY ingest pipeline (§33.5) checks robots.txt at the start of every scheduled run. The Apify-mediated flows rely on the actors to respect their target sites; platform admin reviews this stance per actor.

33.9.3 Budget Caps ¶

Apify has no native hard cap; overage rolls to the next invoice. The platform enforces caps in two layers:

  1. Per-run ceiling: APIFY_RUN_BUDGET_USD_CEILING env var. The adapter halts a run that projects to exceed this and emits a partial-result flag.
  2. Monthly ceiling: Inngest scheduler observes accumulated spend and pauses scheduled refresh jobs when the monthly cap (env var APIFY_MONTHLY_BUDGET_USD_CEILING) is reached. Cached reads continue to work; only new refreshes pause.

Both are operator-configured and surface in the platform admin dashboard.

33.9.4 Kill Switches ¶

Independent kill switches for each external dependency, configurable without code deploy:

  • APIFY_ADAPTER_ENABLED — when false, all Apify-mediated refresh halts; cache reads continue.
  • CRUISEMAPPER_DIY_INGEST_ENABLED — when false, CruiseMapper DIY refreshes halt; existing chunks remain in RAG.
  • PRICE_WATCH_NOTIFICATIONS_ENABLED — when false, watches continue to evaluate but no notifications are sent. Used during notification provider outages or spam-control situations.

33.11 Build Order ¶

When this addendum is implemented, the recommended prompt sequence is:

  1. Schema migration prompt: Adds pricing_cache, price_watches, rag_media_assets, the knowledge_chunks.related_asset_ids column, and the Supabase Storage bucket configuration. Pure migration; no behavior.
  2. PricingDataSource interface + ApifyPricingAdapter (per-line scrapers): Implements §33.2 and §33.3 for the major lines. Includes per-line normalization. MockPricingDataSource for tests.
  3. CruiseMapper itinerary Apify ingest: §33.4. Inngest scheduled job; writes to pricing_cache and itinerary chunks.
  4. CruiseMapper DIY static ingest (no images yet): §33.5 text-only path. Ship registry and port detail pages. Validates the fetcher + parser + rate-limit + robots.txt machinery before adding image complexity.
  5. CruiseMapper DIY deck plan ingest + image asset storage: §33.5 image path, §33.6 media asset table population. Stores images in Supabase Storage; links chunks to assets.
  6. RAG retrieve API extension for assets: §33.6.4. Extends the existing endpoint shape without breaking existing consumers.
  7. Consumer-side display markup: §33.7. System prompt extension, client-side parsing, hallucination defense layer.
  8. Price-watch subscriptions: §33.8. UI for creating/managing watches, Inngest daily check, notification integration via §23.
  9. Sample-OCR evaluation (gated decision): Per session-4 decision, run Haiku vision on a 200-image sample. Evaluate uplift over text-only descriptions. If approved, an additional prompt adds Haiku vision OCR to step 5's ingest, generating additional chunks linked to the same assets.

Steps 1–4 deliver text-only RAG enrichment and pricing data without any image work. Steps 5–7 deliver the deck plan image surface. Step 8 delivers the subscriber-facing price-watch feature. Step 9 is the OCR uplift, conditional on sample evaluation.
