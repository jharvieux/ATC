Section 6 — RAG Service Schema

The RAG (Retrieval-Augmented Generation) service runs in a separate Supabase project from the main app. This separation provides isolation: the main app’s schema can evolve without affecting RAG; the RAG service can scale independently; security boundaries are explicit.

6.1 Service Separation Rationale ¶

  • Independent scaling: RAG vector queries have different load patterns than transactional app queries
  • Security isolation: RAG service has its own credentials and access policies
  • Schema evolution: changes to RAG don’t require main app migrations
  • Independent deployment: RAG service can be redeployed without main app downtime

6.2 Tenant Registry (Synced from Main App) ¶

CREATE TABLE public.tenant_registry (

tenant_id UUID PRIMARY KEY,

tenant_type TEXT NOT NULL,

status TEXT NOT NULL,

synced_at TIMESTAMPTZ DEFAULT NOW()

);

Synced via tenant lifecycle webhook from main app. RAG service is read-only on tenant data; it doesn’t manage tenants directly. No hierarchy information is tracked — the platform’s structure is strictly two-level (platform global + tenant), so the RAG service only needs to know that a tenant exists and what type it is.

6.3 Authority Scale ¶

Knowledge chunks are scored by authority. Five-tier scale:

TierRangeDescription
authoritative_override0.96-1.0Manual override by platform admin; explicit verification
official0.85-0.95From cruise line, port authority, partner press release
tenant_verified0.70-0.84Tenant has explicitly verified accuracy
tenant_default0.55-0.69Standard tenant-submitted content
low0.30-0.54Community-sourced, unverified, or aged content

Pricing chunks auto-cap at 0.55. Manual override (with reason) bypasses the cap.

Tenants can push their tenant-scoped content to 1.0 authority within their own scope. Within their tenant, their override beats everyone else. Doesn’t affect other tenants.

6.7 Promo Lifecycle ¶

Promos transition through four states. The state is a function of the current time relative to two dates: sell_by (last date a new booking can use the promo) and sail_by (last sailing the promo covers).

not_started (NOW < sell_by_start, if defined)
  │
  ▼ (sell_by_start reached, or no sell_by_start)
open_to_new
  │
  ▼ (NOW >= sell_by)
closed_to_new ← retrieval filters this OUT for new prospects
  │            BUT includes for contacts with existing booking
  │
  ▼ (NOW >= sail_by)
expired ← retrieval excludes entirely

Idempotent state reconciliation

The promo state is NOT just a stored field that a cron flips at the right moment. It is a function of current time that the cron reconciles. This pattern matters because:

  • Cron failures (Inngest outage, DST bugs, late execution, timezone drift) must not leave promos in wrong states.
  • Backfill on recovery must reach the correct state regardless of how many transitions were missed.

The implementation:

-- The expected state for a promo at any moment is computable.
-- Implementation as a function so it's used by both retrieval and
-- reconciliation.
CREATE OR REPLACE FUNCTION public.expected_promo_state(
  sell_by_start_at TIMESTAMPTZ,
  sell_by_at TIMESTAMPTZ,
  sail_by_at TIMESTAMPTZ
) RETURNS TEXT
LANGUAGE SQL
IMMUTABLE
SET search_path = ''
AS $$
  SELECT CASE
    WHEN NOW() < sell_by_start_at THEN 'not_started'
    WHEN NOW() >= sail_by_at THEN 'expired'
    WHEN NOW() >= sell_by_at THEN 'closed_to_new'
    ELSE 'open_to_new'
  END;
$$;

The reconciliation cron (promo-state-reconcile) runs every 15 minutes and updates any drifted state. The knowledge_chunks table requires columns promo_status, promo_status_reconciled_at, sell_by_start_at, sell_by_at, sail_by_at for this — confirm they exist in §6.4 and add if missing.

Drift alerting

A separate Inngest cron (promo-state-drift-alert) runs every hour and counts promos whose promo_status does not match the expected state. If the count exceeds zero for more than 30 minutes, the platform admin is paged. Drift longer than 30 minutes implies the reconciliation cron itself is broken.

Lazy state read fallback

For retrieval (§8.4 /api/retrieve), the scope filter computes the expected state at query time rather than trusting the stored value:

WHERE (NOT is_promo) OR public.expected_promo_state(
  sell_by_start_at, sell_by_at, sail_by_at
) IN ('open_to_new', 'closed_to_new')
-- closed_to_new filtered further per §6.9 / §8.4 contact context

This is defense in depth: even if the stored promo_status is stale (reconciliation cron failed), retrieval gets the right answer based on current time.

Backfill on recovery

If the reconciliation cron is paused/broken for an extended period and then resumes, the function above naturally reaches the correct state on the next run — it operates on absolute time, not relative state-machine steps. There is no "I missed an event" problem because there are no events; the state is purely a function of time.

Calls Worth Flagging

  • Timezone correctness is the silent killer. All date columns on promos are TIMESTAMPTZ. NOW() returns UTC. Tenant-facing promo expiry messages render the date in the tenant's locale, but internal comparisons are UTC. Mixing locale-naive timestamps into this calculation produces hour-scale drift.
  • The lazy-state-read fallback in retrieval is non-negotiable. It's the recovery path for any cron failure. Without it, a cron-down weekend has tenants citing expired promos.
  • Drift count > 0 for 30 minutes pages someone. Don't tune this to be permissive; promo state drift is a customer-visible bug (AI commits to closed promos, retrieves expired ones).

6.8 Pricing Authority Cap ¶

Pricing content is volatile. Auto-cap at 0.55 reduces the risk of stale prices being treated as authoritative. The cap can be manually overridden (with reason) for content where pricing is intentionally part of authoritative communication (e.g., a freshly-confirmed group rate). The override is logged in audit and visible in chunk metadata.

6.9 Retrieval Scope ¶

Retrieval scope: global content + caller’s own tenant. No cross-tenant content visibility under any circumstances. The platform’s structure is strictly two-level — there are no ancestor tenants to inherit content from.

– Retrieval query scope:

WHERE scope = ‘global’

OR (scope = ‘tenant’ AND tenant_id = caller_tenant_id)

6.10 Customer Feedback Confidence Factor ¶

Customer feedback signals (thumbs up/down on AI responses citing specific chunks) inform a feedback confidence factor — a fourth input to retrieval ranking, additive to the existing relevance × authority × recency composite.

This is a deliberate departure from earlier draft language that described feedback as modifying chunk authority_score directly. The earlier model conflated intrinsic chunk quality (authority) with observed retrieval performance (feedback). The new model keeps these separate:

  • authority_score — chunk's intrinsic authority. Set by authority_auto at ingestion (per §6.3 ingestion quality signals); optionally overridden by authority_manual_override for platform-admin curation. NEVER modified by customer feedback.
  • feedback_confidence_factor — a separate per-chunk value derived from cumulative customer feedback with exponential time decay. Bounded to [-limit, +limit] where limit is configurable (default 0.05). Recomputed on retrieval (with a short cache).

The four configurable knobs

Stored in the new platform_settings table (per §5.5 below). Modifiable from the platform admin console:

SettingDefaultRangeEffect
feedback_adjustment_limit0.050.0–0.5Maximum signed adjustment to retrieval score from feedback
feedback_min_signal_count21–100Minimum signal count within feedback_period_days to trigger any adjustment
feedback_period_days301–365Lookback window for the minimum signal count
feedback_decay_halflife_days901–365Time at which a signal's weight has decayed to 50% of its initial value

All four are platform-wide settings; no per-tenant override. Tenants do not see these knobs.

Changes to any setting take effect on the next retrieval (no batch reprocessing — the recomputation function reads current settings each invocation).

Recomputation function

CREATE OR REPLACE FUNCTION public.compute_feedback_factor(
  p_chunk_id UUID
) RETURNS NUMERIC
LANGUAGE plpgsql
STABLE
SET search_path = ''
AS $$
DECLARE
  v_adjustment_limit NUMERIC;
  v_min_signal_count INTEGER;
  v_period_days INTEGER;
  v_halflife_days INTEGER;
  v_recent_signal_count INTEGER;
  v_decay_weighted_sum NUMERIC;
BEGIN
  -- Read current platform settings.
  SELECT value::NUMERIC INTO v_adjustment_limit
    FROM public.platform_settings WHERE key = 'feedback_adjustment_limit';
  SELECT value::INTEGER INTO v_min_signal_count
    FROM public.platform_settings WHERE key = 'feedback_min_signal_count';
  SELECT value::INTEGER INTO v_period_days
    FROM public.platform_settings WHERE key = 'feedback_period_days';
  SELECT value::INTEGER INTO v_halflife_days
    FROM public.platform_settings WHERE key = 'feedback_decay_halflife_days';

  -- Gate: minimum signal count within the lookback period.
  SELECT COUNT(*) INTO v_recent_signal_count
    FROM public.knowledge_chunk_feedback_events
    WHERE chunk_id = p_chunk_id
      AND created_at >= NOW() - (v_period_days || ' days')::INTERVAL;

  IF v_recent_signal_count < v_min_signal_count THEN
    RETURN 0;
  END IF;

  -- Cumulative-with-decay: sum of raw_weight × decay factor.
  SELECT COALESCE(SUM(
    raw_weight * POWER(0.5, EXTRACT(EPOCH FROM (NOW() - created_at)) / 86400.0 / v_halflife_days)
  ), 0) INTO v_decay_weighted_sum
    FROM public.knowledge_chunk_feedback_events
    WHERE chunk_id = p_chunk_id;

  -- Clamp to [-limit, +limit].
  RETURN GREATEST(-v_adjustment_limit,
                  LEAST(v_adjustment_limit, v_decay_weighted_sum * 0.01));
  -- The * 0.01 scaling factor converts raw weighted-sum units into
  -- the adjustment scale. Calibrate during Phase 1.
END;
$$;

Retrieval integration

The retrieval scoring in §8.4 changes from:

composite_confidence = match_score × authority × recency

to:

composite_confidence = (match_score × authority × recency) + feedback_factor

where feedback_factor comes from compute_feedback_factor(chunk_id), clamped to the configured limit. The retrieval response per §8.4 returns feedback_factor as a fifth scoring component for transparency.

Where feedback events come from

The /api/chat/feedback endpoint (per §7.2) records thumbs-up/thumbs-down on a message. When the message had a non-empty cited_chunk_ids set, each cited chunk gets a knowledge_chunk_feedback_events row inserted:

  • Thumbs up → signal_direction = 'up', raw_weight = +1.0
  • Thumbs down → signal_direction = 'down', raw_weight = -1.0

A single feedback event can produce multiple feedback rows (one per cited chunk).

Caching

compute_feedback_factor is STABLE (deterministic for a single transaction). For high-traffic retrieval, the function result is cached at the application layer per chunk for 5 minutes.

Platform admin surface

The platform admin console gains a "Feedback Tuning" page showing current knob values (editable), histograms of feedback_factor distribution, top chunks by absolute feedback_factor, and settings-change history. Settings changes are gated by withPlatformAdminAudit with reason = 'feedback_settings_change'.

Calls Worth Flagging

  • Authority and feedback are separate inputs by design. A future refactor that "simplifies" by collapsing them into a single score loses this separation. Don't.
  • Default decay halflife of 90 days is slow. A chunk that gets consistent thumbs-down for a month will accumulate signal but the adjustment grows gradually. Faster halflife (e.g., 30 days) makes the loop more reactive at the cost of being more thrash-prone. Tune in Phase 1.
  • Minimum signal count = 2 is permissive. Two thumbs is enough to start moving the factor. This is intentional during early operation when feedback volume is low. Raise as traffic grows.
  • The clamp at ±0.05 is a hard ceiling on impact. Even thousands of thumbs-down on one chunk only adjusts retrieval score by 0.05. This protects against coordinated-thumbs-down attacks while still letting genuine signal accumulate.
  • Per-tenant override is deliberately NOT supported. Tenants can't tune their own corpus's feedback dynamics. This keeps platform retrieval behavior consistent and prevents tenants from gaming their own scoring.

6.11 PII Exclusion ¶

RAG content must not contain customer PII. Ingestion pipeline (§22.4) redacts PII before chunks are created. Reports of PII slipping through trigger immediate chunk removal.

6.12 Retention ¶

  • Approved chunks: indefinite while tenant is active
  • Rejected/failed queue items: 90 days
  • Retrieval log detail: 90 days, then aggregated
  • Audit log on chunk changes: 7 years
