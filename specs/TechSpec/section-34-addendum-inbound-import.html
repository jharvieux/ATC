Section 34 - Addendum — Inbound Import (Email / Document / Manual)

Status: Addendum. Lands after Part 1–9 build prompts and after the §33 addendum. References existing sections by number; modifies §14.3 behavior for imported bookings via the adjustment in §34.7 (does not edit §14.3 in place).

Why an addendum, not a retrofit: This work adds a new intake surface (email forward via Gmail, document upload, manual entry) and a new booking origin (imported) for bookings that originated outside the platform. Each touches existing sections (§5, §12, §14, §22, §23, §26) but the existing sections are stable and have build prompts already written. The addendum lands the new behavior as a clearly-scoped extension and explicitly cross-references the existing sections it adjusts.

34.1 Overview ¶

The platform supports importing contacts and bookings that originated outside the platform — primarily for BYO-host agents whose host agency provides the lead-capture and booking-of-record systems. Imports create platform-side records so the agent can use the platform's CRM (§12), AI chat (§9), price watches (§33.8), pre-cruise email series (§23.4), and commission reconciliation (§14.8) on bookings the platform did not itself create.

Three intake paths share a common parsing pipeline:

Document uploadAgent uploads file via CRM UIPDFs of intake forms, CSV exports from host system, screenshots of lead-board entries, commission statement PDFs
Manual entryAgent fills form in CRM UIPhone leads, in-person referrals, networking events

34.2 Email Import Trigger (Gmail Integration) ¶

Inbound parsing rides the existing Gmail integration (§23.1) — no separate inbound address or provider. A Gmail message qualifies for import parsing when either of these is true (case-insensitive):

  • The subject line starts with the word IMPORT (with or without trailing punctuation: IMPORT, Import:, IMPORT -, etc.)
  • The first non-empty line of the message body starts with the word IMPORT

Messages not matching the trigger continue to flow into the normal Gmail-conversation path (the agent's regular inbox correspondence with customers). Trigger detection is the first step of inbound processing, runs before persona response logic per §9, and the result is logged on the message row.

34.2.1 Why a single trigger word rather than label or prefix-syntax ¶

  • Labels require Gmail-side configuration the agent has to set up; trigger word works in any Gmail account out of the box.
  • A bracketed prefix like [IMPORT] is easy to typo ([Import ], [ IMPORT]); a leading word is forgiving.
  • "Top of the email" lets the agent paste a forwarded message and just type IMPORT on the first line before sending — no subject editing needed.

34.2.2 Trigger detection rules ¶

Implemented as a regex check (per-line) against subject and first body line:

const IMPORT_TRIGGER = /^\s*IMPORT\b/i;

function qualifiesForImport(subject: string, body: string): boolean {
  if (IMPORT_TRIGGER.test(subject)) return true;
  const firstNonEmpty = body
    .split(/\r?\n/)
    .map(l => l.trim())
    .find(l => l.length > 0);
  return firstNonEmpty ? IMPORT_TRIGGER.test(firstNonEmpty) : false;
}

The \b word boundary ensures "IMPORTANT", "IMPORTED", "IMPORTING" do NOT match. Only the standalone word "IMPORT" (followed by whitespace, punctuation, or end-of-line) triggers parsing.

34.2.3 Agent guidance ¶

Surfaced in the CRM help docs per §32:

  • "To import: forward the email to your Gmail address connected to the platform, and either prefix the subject with IMPORT or type IMPORT as the first line of the body."
  • Worked examples shown in the help: lead notification (web-form alert from host system), booking confirmation (cruise line email forwarded), commission statement (monthly statement from host).

34.2.4 Gmail integration health requirement ¶

Email import is only functional while the Gmail integration is healthy. If the tenant's Gmail OAuth token expires or is revoked, inbound message processing stops — including import parsing. The CRM surfaces Gmail-integration health prominently:

  • Tenant settings page displays current status: connected / token_expired / revoked / disconnected.
  • A persistent banner appears in the CRM nav when status is anything other than connected.
  • An email notification is sent to the tenant owner when the integration transitions to a non-healthy state.

Without these signals, an agent could send IMPORT emails for weeks expecting parsing while no parsing is occurring — a silent failure that would corrupt their pipeline data.

34.3 Parsing Pipeline ¶

All three intake paths converge on a single parsing pipeline. The pipeline is implemented as an Inngest function with checkpointed steps so a failure at any stage does not lose work.

[Email qualifies (§34.2) | Document uploaded | Form submitted]
        │
        ▼
[Virus scan (uploads only) — pass/fail gate]
        │
        ▼
[Document type classification — Haiku]
   ├── 'lead_notification'    → contact extraction
   ├── 'booking_confirmation' → contact + booking extraction
   ├── 'commission_statement' → commission line-item extraction (§14.8)
   ├── 'intake_form'          → contact extraction
   └── 'unknown'              → flagged for agent review, no auto-extraction
        │
        ▼
[Field extraction — Sonnet, structured tool output]
        │
        ▼
[Validation layer — required fields, plausibility checks, duplicate detection]
        │
        ▼
[Agent review queue OR auto-accept above confidence threshold]
        │
        ▼
[Records created/updated in CRM]
        │
        ▼
[Original document discarded (per §34.4); extracted fields retained]

34.3.1 Virus scanning ¶

Document upload and Gmail attachment paths MUST pass virus scanning before any parsing. Implementation: ClamAV daemon running as a sidecar service, or Supabase storage's native scan if available at build time. Files failing the scan are quarantined (not in tenant-accessible storage), logged to audit_log with action = 'document.virus_detected', and the agent is notified via in-app notification. Quarantined files are deleted after 30 days.

34.3.2 Document type classification ¶

A Haiku call classifies the document into one of the five categories listed in the flow above. Classification prompt is constrained to a structured tool output (single enum value plus confidence score). Confidence below 0.60 routes the document directly to the agent review queue with type = unknown; the agent can then either set the type manually and re-process, or reject the import.

34.3.3 Field extraction ¶

A Sonnet call with the document text/image (PDF rasterized if needed) extracts structured fields based on the classified type. Each extracted field carries a per-field confidence score. The overall extraction confidence is the minimum field confidence — one weak field pulls the whole record into review.

Prompt-injection screening per §26.8 applies: scraped or forwarded content is untrusted input, and instruction-like content embedded in a document must not steer the extraction. The extraction prompt explicitly frames the document content as data, not instructions.

34.3.4 Validation layer ¶

After extraction, before persistence:

  • Required-field check: Type-specific required fields must be populated. For example, a booking_confirmation requires the §33.2 SailingKey fields. Missing required fields route to agent review.
  • Plausibility: Dates within reasonable range (not in the past for future-sailing extractions; not 100 years out), amounts within plausible bands (per-cabin price < $100,000), email format valid.
  • Duplicate detection: Contact match on (tenant_id, email) or (tenant_id, phone). Booking match on (tenant_id, cruise_line, ship, sail_date, passenger_last_names). Possible duplicates route to agent review for accept-as-new / merge / discard decisions.

34.3.5 Auto-accept threshold ¶

Default auto-accept threshold is overall extraction confidence ≥ 0.80 with no validation flags. Threshold is tenant-configurable in CRM settings (range 0.60–1.00). Records below threshold or with flags route to the §34.6 review queue. Above threshold and clean, records are written directly to the CRM and the agent is notified.

34.4 Document Retention ¶

Uploaded files and parsed email attachments are discarded after successful parse. The agent retains the original outside the platform for reference. Reasoning: minimizes PII storage surface; the agent already has the source-of-truth copy.

Retention exceptions:

  • Parse failure: File retained for 7 days behind a parse_failed flag so the agent can review what the system saw before re-attempting or correcting manually.
  • Agent review pending: File retained until the agent confirms or rejects extraction; then discarded.
  • Virus-detected files: Quarantined for 30 days per §34.3.1.

A daily Inngest scheduled function (purge-parsed-documents) sweeps storage and removes files whose extraction_status IN ('accepted','rejected') and whose extracted_at < NOW() - INTERVAL '24 hours'. Discard is logged to audit_log per §26.5 with action = 'document.purged'.

For the Gmail path, the source email itself is NOT deleted from the agent's Gmail (the platform does not manage the agent's mailbox content). Only platform-side temporary parsing artifacts are discarded.

34.5 Extracted Record Types ¶

34.5.1 Contact extraction ¶

Contact extraction populates public.contacts (§12.1). The source field is set to 'imported' (extending the existing enum from §12.1) and source_reference captures the import path (e.g., 'gmail:<message-id>', 'upload:<upload-id>').

A new audit table tracks the link between contact and import event:

CREATE TABLE public.contact_imports (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     UUID NOT NULL REFERENCES public.tenants(id),
  contact_id    UUID NOT NULL REFERENCES public.contacts(id) ON DELETE CASCADE,
  import_path   TEXT NOT NULL CHECK (import_path IN ('email','document','manual')),
  source_ref    TEXT NOT NULL,         -- Gmail message-id, upload-id, or form submission-id
  document_type TEXT NOT NULL,         -- §34.3.2 classification result
  confidence    NUMERIC(4,3),          -- overall extraction confidence; NULL for manual
  imported_by_user_id UUID REFERENCES public.users(id),
  imported_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  raw_extracted_fields JSONB,          -- snapshot of what the parser saw, for audit
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX contact_imports_tenant_contact_idx
  ON public.contact_imports(tenant_id, contact_id);
ALTER TABLE public.contact_imports ENABLE ROW LEVEL SECURITY;
-- RLS policies follow §5.1 auth_user_in_tenant + tenant_is_active pattern.

The raw_extracted_fields JSONB is the parser's verbatim output, retained even after the source document is discarded. This allows reconstructing what the parser saw if a later dispute arises (e.g., "the agent says I extracted the wrong DOB"). It does NOT contain the source document itself — only the parser's structured interpretation.

34.5.2 Booking extraction (bookings-of-record-elsewhere) ¶

Bookings made through the agent's host-of-record systems but imported into the platform for tracking. Schema additions to public.bookings:

ALTER TABLE public.bookings
  ADD COLUMN origin TEXT NOT NULL DEFAULT 'platform'
    CHECK (origin IN ('platform','imported')),
  ADD COLUMN imported_from TEXT
    CHECK (imported_from IN ('email','document','manual')),
  ADD COLUMN imported_at TIMESTAMPTZ,
  ADD COLUMN imported_by_user_id UUID REFERENCES public.users(id),
  ADD COLUMN provider_booking_ref TEXT;   -- host's reference number, for §14.8 matching
CREATE INDEX bookings_provider_ref_idx
  ON public.bookings(tenant_id, provider_booking_ref)
  WHERE provider_booking_ref IS NOT NULL;

Imported bookings MUST capture the §33.2 SailingKey fields so price watches can attach: cruise_line, ship_name, sailing_date, departure_port, duration_nights. Missing fields route the import to the §34.6 review queue rather than auto-accepting.

Booking imports also create associated contact rows per §34.5.1 if the passenger contacts do not already exist in the CRM.

34.5.3 Imported booking commission lifecycle ¶

The full adjustment to §14.3 for imported bookings is specified in §34.7. Summary: imported bookings enter the expected commission state without traversing the booking-submit path; commission rates are sourced from parsed document, then host adapter, then agent input, with the source recorded; platform_split_rate is NULL for BYO tenants.

34.5.4 Commission statement extraction ¶

Commission statements feed the §14.8 reconciliation flow. Each parsed line item matches an existing commissions row by:

  1. Exact match on provider_booking_ref (preferred). When the host's statement includes a booking reference number that matches a row's provider_booking_ref, the match is automatic and flows through the §14.8 variance thresholds.
  2. Fuzzy match fallback on (cruise_line, ship_name, sailing_date, passenger_last_name) when provider_booking_ref is absent or doesn't match any row. Fuzzy matches always surface in the §14.8 admin review flow with the match-confidence score, never auto-accepted regardless of dollar variance.

Match-confidence calculation for fuzzy matches:

cruise_line exact match     → 0.30
ship_name exact match       → 0.25
sailing_date exact match    → 0.25
sailing_date ±7 days        → 0.15
passenger_last_name exact   → 0.20
passenger_last_name fuzzy   → 0.10  (Levenshtein distance ≤ 2)

Total ≥ 0.85: high-confidence match (auto-suggest in review UI)
Total 0.60–0.84: possible match (require explicit admin confirmation)
Total < 0.60: not surfaced; treated as orphan per §14.8

Statement parsing does NOT create new bookings — it only updates existing commission records. If a statement line item has no matching booking, it surfaces as an orphan per §14.8, and the admin can choose to manually create an imported booking from the orphan or mark the line item as unmatched.

34.6 Agent Review Queue ¶

Items requiring agent review:

  • Overall extraction confidence below auto-accept threshold (default 0.80)
  • Required fields missing
  • commission_rate_missing per §34.7.3 step 3 (imported booking with no rate from parse or host adapter)
  • Possible duplicate contact detected (existing match on email or phone)
  • Possible duplicate booking detected (existing match on SailingKey + passenger name)
  • Document type classified as unknown
  • Plausibility failures (impossible dates, out-of-band amounts)

UI: a "Pending review" tab in the CRM showing each item with extracted fields, source preview (image of the document or excerpt of the email body), and actions:

  • Accept as-is — write records as parsed
  • Edit and accept — agent corrects fields, then writes
  • Merge with existing — for duplicate-flagged items, merge extracted fields into the existing contact/booking
  • Reject — discard extraction; original document also discarded (or retained per §34.4 if the agent flags for follow-up)

Reviewed items leave the queue. Audit log records the review action, the reviewing user, and the final disposition.

34.6.1 Bulk review patterns ¶

An agency owner with multiple agents may face a backlog at month-end when commission statements are forwarded in bulk. The review queue supports:

  • Filter by import path (email / document / manual)
  • Filter by document type (commission statement / booking confirmation / lead notification)
  • Filter by submitting agent (Agency-tier tenants with multiple seats)
  • Bulk accept — select multiple high-confidence items and accept all at once; useful for batches of similar lead notifications from the same source

34.7 §14.3 Adjustment for Imported Bookings ¶

This section modifies the behavior described in §14.3 (Two-Party Split — rate locking and computation) for bookings with origin = 'imported'. §14.3 as written assumes both rates resolve at POST /api/bookings/:id/submit; imported bookings have no submit step. The fail-closed rule of §14.4 is therefore replaced for imports with the resolution order specified below. §14.3 behavior for origin = 'platform' bookings is unchanged.

34.7-1 Where rate resolution happens for imports ¶

For imported bookings, rate resolution happens at import-acceptance time (the point at which the agent accepts the import out of the §34.6 review queue, or the point at which the system auto-accepts above the threshold). This timestamp replaces the §14.3 submit-time as the rate-locking moment.

34.7.2 The commissions row for imports ¶

A commissions row is written at import-acceptance time. All §14.0 money rules apply unchanged (BIGINT cents, half-away-from-zero rounding, money utility module). The row's commission_rate_source field (new — see §34.8) records how the rate was sourced.

34.7.3 Commission rate resolution order ¶

  1. From parsed document. If the imported document explicitly states a commission rate or commission amount, derive commission_rate from it. If the document gives an amount in dollars rather than a rate, the implied rate is commission_amount / commissionable_fare and is stored as such (the amount itself is also retained for cross-check). Set commission_rate_source = 'doc_parsed'.
  2. From host adapter. If no rate was parsed from the document, but the tenant's configured host adapter publishes a commission rate programmatically per §13, use that rate. Set commission_rate_source = 'host_adapter'.
  3. From agent input. If neither (1) nor (2) produces a rate, the import enters or remains in the §34.6 review queue with reason commission_rate_missing. The agent enters a rate in the review screen. Set commission_rate_source = 'agent_set'.

The import cannot be accepted (and the commissions row cannot be written) until commission_rate is resolved. This is the fail-closed behavior for imports — same intent as §14.4 but with the agent as the resolver of last resort rather than platform admin.

34.7.4 platform_split_rate for imports ¶

For BYO tenants, platform_split_rate is NULL — the platform has no commission share on BYO bookings, whether platform-originated or imported. The §14.4 fail-closed rule for platform_split_rate is therefore inapplicable to BYO imports.

For sub-host tenants: imported bookings are not permitted (see §34.9). A sub-host's bookings flow through the platform's booking flow by definition (the platform is host-of-record). If a sub-host attempts to import a booking, the UI rejects the action with explanation.

34.7.5 host_booking_fee lock for imports ¶

The host_booking_fee_cents column is locked at import-acceptance time using the same rules as §14.3:

  • If the parsed document contains the host's booking fee explicitly, use that.
  • Otherwise, snapshot from host_booking_fee_configs (or tenant override) at import-acceptance time.
  • Either way, the fee is locked on the commissions row and not re-derived later.

34.7.6 Subsequent rate changes ¶

Same rule as §14.3: subsequent host rate changes or tenant tier changes do NOT affect already-imported commissions. The locked values apply.

If the agent later discovers the resolved rate was wrong (e.g., they entered 12% but the host actually pays 13% for that cruise line), the correction path is:

  1. Agent updates commission_rate on the commissions row from the CRM UI.
  2. The system inserts an audit_log entry recording prior rate, new rate, editor, reason (free text).
  3. commission_rate_source is updated to 'agent_corrected' (new value in the enum — see §34.8).
  4. If net_commission_cents had already been computed, it is recomputed using the new rate.

34.7.7 Calls Worth Flagging — §14.3 adjustment ¶

  • §14.3 is NOT edited in place. The adjustment lives here in §34.7 and is referenced from any code path or reviewer who's reading §14.3 with imported bookings in mind. A small note in §14.3 pointing to §34.7 is the only edit recommended to §14.3 itself, and even that is optional.
  • The 'agent_corrected' value in the commission_rate_source enum is distinct from 'agent_set'. 'agent_set' = agent provided the original rate at import. 'agent_corrected' = agent overrode a previously-resolved rate. The distinction matters for audit and for the §36 reporting integrity checks.
  • commission_rate from a parsed document carries the same data-validity risk as any other extraction. The parser may misread a percent sign or a decimal. The agent review queue should highlight parsed rates for confirmation when the document type is commission_statement or booking_confirmation; rates above auto-accept threshold from lead_notification documents (which shouldn't contain rates anyway) should still require confirmation.

34.8 Schema Additions ¶

34.8.1 commissions table additions ¶

Two changes to the commissions table defined in §5 and §14:

-- Commission rate source tracking (per §34.7)
ALTER TABLE public.commissions
  ADD COLUMN commission_rate_source TEXT
    CHECK (commission_rate_source IN (
      'host_adapter',        -- resolved at submit-time from host capabilities (§14.3 platform-origin path)
      'doc_parsed',          -- imported booking, rate from parsed document
      'agent_set',           -- imported booking, agent entered rate at import
      'agent_corrected'      -- agent overrode a previously-resolved rate (any origin)
    ));

-- Clawback tracking (per §34.8.2 — used by §40 cancellations reporting)
ALTER TABLE public.commissions
  ADD COLUMN clawback_amount_cents BIGINT DEFAULT 0,
  ADD COLUMN clawback_at TIMESTAMPTZ,
  ADD COLUMN clawback_reason TEXT;

34.8.2 Why clawback fields land in §34 ¶

§14.9 describes clawback handling narratively but doesn't add explicit storage. The §36 "Lost revenue from cancellations" report needs to query clawback amounts per booking. Rather than edit §14 in place (the build prompts for §14 are already written), the storage lands here as part of the import/reporting addendum group. §14.9's clawback flow should write to these fields when it processes a clawback; the field semantics are:

  • clawback_amount_cents — total amount clawed back from received_commission_cents. Defaults to 0; non-zero only when a clawback occurred.
  • clawback_at — when the clawback was processed.
  • clawback_reason — free text; commonly populated from the booking's cancellation_reason when the clawback was triggered by a cancellation.

34.8.3 bookings table additions ¶

Already shown in §34.5.2 for clarity in context: origin, imported_from, imported_at, imported_by_user_id, provider_booking_ref.

34.8.4 contact_imports table ¶

Already shown in §34.5.1.

34.8.5 contacts.source enum extension ¶

§12.1 defines source TEXT as a free text field with stated values 'manual', 'ai_extracted', 'signup', 'imported', 'referred'. The 'imported' value is already in the documented enum — no schema change needed, just the path now actually emits it.

34.10 Calls Worth Flagging ¶

  • Trigger word collisions remain narrow but possible. An agent forwarding "IMPORTANT: client update" does NOT match (word boundary check). An agent who writes "Import these details below — IMPORT" on a line where "IMPORT" appears later does NOT match. Only the leading word "IMPORT" at the start of subject or first body line matches. If the agent's normal email vocabulary heavily uses the word IMPORT in subject lines for other reasons, false positives are possible — the agent should change the trigger word in tenant settings (future enhancement; not in v1).
  • Gmail token expiry is a silent failure mode unless the health surfacing in §34.2.4 is built. Critical to land in v1 alongside the import feature.
  • Virus scanning provider selection is deferred. ClamAV sidecar is the safe default; Supabase native scanning is a faster integration if available at build time.
  • Confidence threshold tuning will need post-launch adjustment. The 0.80 default is a starting point; real-world parsing accuracy on the actual document types tenants forward (host system emails, screenshots, varied PDF formats) will require calibration. Build the threshold as a tenant-configurable setting from day one to avoid a future migration.
  • Cancellation triggered by clawback path — when a cancellation in §14.9 causes a clawback, the clawback amount must be written to the new clawback_amount_cents field for the §36 report to work. Build coordination: §14.9 implementation and §34.8.1 schema must land together.
  • The raw_extracted_fields JSONB in contact_imports is retained even after the source document is purged. This is by design — it's the audit trail of what the parser produced. It is NOT the source document and does not contain PII the parser didn't extract. If a tenant requests full data deletion per §25, this JSONB is included in the deletion scope alongside the contact row.
  • Per-tenant parsing volume may drive AI cost. A tenant who forwards 200 commission statements per month with multi-page PDFs could generate non-trivial Sonnet costs. §27 cost-attribution and abuse monitoring should treat import-parsing AI calls the same as customer-chat AI calls for budget purposes.
