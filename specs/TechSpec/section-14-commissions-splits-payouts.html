Section 14 — Commissions, Splits & Payouts

The end-to-end money flow: from booking commission to bank deposit.

14.0 Money Representation Rules ¶

Every money value in the schema and every money computation in code follows the rules in this subsection. These rules exist because (a) NUMERIC and BIGINT-cents have different rounding behavior and mixing them silently produces fractional-cent drift, and (b) unspecified rounding means different code paths produce different results from the same inputs.

14.0.1 Storage representation ¶

All money columns store integer cents as BIGINT. No NUMERIC money columns. No DECIMAL money columns. No floating-point money columns — ever, anywhere.

Columns are suffixed _cents so the unit is unambiguous at read time:

  • total_amount_cents BIGINT
  • commissionable_fare_cents BIGINT
  • gross_commission_cents BIGINT
  • host_booking_fee_cents BIGINT
  • net_commission_cents BIGINT
  • received_commission_cents BIGINT

(Renames from earlier drafts: total_amount → total_amount_cents; commissionable_fare → commissionable_fare_cents. See §5.3 for the affected schema definitions.)

Currency is stored on the row (column currency TEXT NOT NULL DEFAULT 'USD'). At launch all currencies are USD per §2.4, but the schema allows future expansion.

14.0.2 Rates and percentages ¶

Rates and percentages are stored as NUMERIC(5,4) representing the decimal form (e.g., 0.1500 for 15%, 0.2000 for 20%), NOT as a percent-points integer or NUMERIC(5,2). This eliminates one multiply-or-divide-by-100 step and the rounding error that comes with it.

  • commission_rate NUMERIC(5,4) — host commission rate
  • platform_split_rate NUMERIC(5,4) — platform's share of net commission (e.g., 0.2000 for the Pro-tier 20/80 split)

(Rename from earlier drafts: commission_rate_percent → commission_rate.)

14.0.3 Rounding strategy ¶

All money rounding is half-away-from-zero (also called "commercial rounding" or "round half up" for positive values). This matches what spreadsheets and most accounting systems do by default and matches what the host's statements will use.

Rounding happens at exactly one place in any computation: the final write to a _cents column. Intermediate computations operate on arbitrary-precision NUMERIC and are only rounded when persisted.

14.0.4 The money utility module ¶

All money computation in code goes through a single utility module src/lib/money.ts (path indicative — exact location at engineering discretion, but a single module is non-negotiable). The module exposes:

  • toCents(amount: BigNumberLike): bigint — convert a NUMERIC-shaped input to integer cents using the rounding strategy in §14.0.3.
  • fromCents(cents: bigint): BigNumberLike — convert for display only; never for further computation.
  • multiplyRate(cents: bigint, rate: NumericRate): bigint — apply a rate (0.0000–1.0000) to a cents value, rounding the result.
  • subtractFee(cents: bigint, feeCents: bigint): bigint — subtract one cents value from another, asserting non-negative result (or raising an explicit error caller must handle).

Any code performing money arithmetic via Number, JavaScript's * operator, or parseFloat on a money string is a code-review failure. CI lint rule per §30.8 should flag these patterns.

14.0.5 Currency mixing ¶

Operations that combine values in different currencies must be explicitly rejected. The money utility module enforces this — any function that takes two money inputs validates they share a currency context, or accepts an explicit currency-conversion parameter. Silent mixing produces the worst kind of bug (numerically valid, semantically wrong).

At launch all values are USD so this is a forward-compatibility constraint, not an active concern. Document it now so the utility shape doesn't have to be retrofitted when a second currency is added.

14.0.6 Calls Worth Flagging ¶

  • Half-away-from-zero is the spec's choice. If a partnered host agency uses banker's rounding (half-to-even) for their statements, the platform's reconciliation will show ~half-a-cent variance on some bookings. This is below the §14.8 auto-accept threshold ($5) but worth understanding before disputes happen.
  • The money utility is a library boundary. Engineers will be tempted to do "just this one multiplication" inline. They shouldn't. Make it a code-review reflex.

14.3 Two-Party Split ¶

Commission splits are strictly two-party: platform and sub-host. The platform retains its tier-defined percentage of net commission; the sub-host receives the remainder. This is the entire structure — there is no chain walk, no hierarchy, no multi-level allocation. The platform's responsibility ends at paying the sub-host their share.

Rate locking

The two rates that determine the split — commission_rate (host's rate to the platform) and platform_split_rate (platform's share of net commission) — are LOCKED into the commissions row at booking submission time, not at commission-receipt time.

  • At POST /api/bookings/:id/submit, the handler resolves the current values from the host adapter capabilities (commission_rate) and the tenant's current tier (platform_split_rate) and persists them on the commissions row alongside the booking reference.
  • Subsequent changes — host adjusts their commission rate, sub-host upgrades or downgrades tier, platform changes the tier rate table — do NOT affect already-submitted commissions. The locked values apply.
  • New bookings submitted after the change use the new rates.

This rule eliminates the time-of-check-vs-time-of-use ambiguity (a sub-host upgrading from Starter to Pro between booking submission and commission receipt: which rate? — answer: whichever rate was current at submission). The trade-off is that tenants who upgrade mid-cycle don't see the better rate apply to in-flight bookings; this is deliberate and is documented in tenant-facing tier-change copy per §15.15.

Computation

All math uses the money utility per §14.0.4. The commissions row stores both the inputs and the computed outcomes so the math is auditable without re-derivation:

gross_commission_cents     = multiplyRate(commissionable_fare_cents, commission_rate)
net_commission_cents       = subtractFee(gross_commission_cents, host_booking_fee_cents)
platform_retained_cents    = multiplyRate(net_commission_cents, platform_split_rate)
subhost_payable_cents      = subtractFee(net_commission_cents, platform_retained_cents)

Note the last line subtracts rather than multiplying-by-(1 - rate). This guarantees platform_retained_cents + subhost_payable_cents == net_commission_cents exactly, eliminating sub-cent drift on the two-multiplications path. The host-side variant (× rate, × (1 - rate)) can produce a 1-cent gap on values where the rate has many decimal places.

Calls Worth Flagging

  • Rate-locked-at-submission is the spec's choice. A tenant whose tier upgrade was processed five minutes before booking submission gets the new rate; one whose upgrade landed five minutes after submission doesn't. The cutoff is the booking-submit timestamp. Tenant-facing copy on tier changes must make this clear so a sub-host doesn't expect a retroactive bump.
  • The host-fee column is locked at submission too. If the host changes their fee schedule after submission, in-flight commissions use the snapshot. Implementation must persist the fee snapshot (host_booking_fee_cents and host_booking_fee_rule_ref), not re-derive at receipt time.

14.3a Sub-Host Internal Subcontractor Tracking ¶

Sub-hosts often work with their own subcontractors — assistant agents, friends-and-family helpers, referral partners. The platform offers a private bookkeeping feature so sub-hosts can forecast their net revenue after subcontractor obligations. This is entirely internal to the sub-host’s tenant; the platform does not pay subcontractors, does not validate their identities, does not generate tax documents for them, and has no relationship with them.

How it works for the sub-host:

  • Sub-host maintains a list of named subcontractors with a percentage for each (e.g., ‘Sarah Martin — 50%’)
  • When a booking is created, the sub-host can tag it with a subcontractor
  • Revenue dashboards subtract the subcontractor’s percentage from the sub-host’s share to show net retained revenue
  • The sub-host pays their subcontractor outside the platform via whatever arrangement they have

UI gating: subcontractor feature appears only for tenants with tenant_type = ‘sub_host’. BYO-host tenants don’t see it (they handle their own structure inside their host agency relationship), nor does the platform’s own automated agency.

NOTE: The platform’s commission tracking and payouts are unaffected by the sub-host’s internal subcontractor data. Subcontractor data exists purely for the sub-host’s bookkeeping convenience.

14.4 Fail-Closed Rule ¶

The booking-submit handler MUST resolve both rates (commission_rate from the host adapter, platform_split_rate from the tenant's tier definition) before it can write the commissions row. If either is unresolvable, the submit fails closed:

  • commission_rate unresolvable (host adapter unhealthy, host doesn't publish rates programmatically, or the adapter returns null): the booking submission is paused. The booking row enters status pending_host_review with a structured reason. Platform admin is alerted. Tenant sees: "We're confirming the commission rate with the host before submitting this booking."
  • platform_split_rate unresolvable (tier_id is null, tier definition is missing, sub-host tier doesn't define a split): the booking is flagged for platform admin review with reason missing_platform_split. No commissions row is written until resolved.

In neither case does the platform silently default to a guessed rate. A silently-defaulted rate is the path to disputes that cost more than the booking is worth.

The handler logs the rate-resolution attempt and outcome to audit_log (per §26.5) on every submission, successful or not.

14.5 Hold Periods ¶

Per §3.4: 7 / 3 / 0 days by tier (Starter / Pro / Agency). Cruise commissions usually arrive AFTER sailing — clawback risk is mostly past by then. Stripe Connect’s 60-day reversal window handles residual risk.

14.7 Stripe Connect Transfer ¶

Idempotency contract

The idempotency key for a Stripe transfer is derived deterministically from the logical payout, not from wall-clock time. A retry of the same logical operation MUST produce the same key, or Stripe creates duplicate transfers and real money moves twice.

The key is constructed from the payout_records.id (a UUID created before the transfer is attempted) plus an attempt_generation integer:

idempotencyKey = `payout-${payoutRecord.id}-gen${payoutRecord.attempt_generation}`

attempt_generation defaults to 1 and is incremented ONLY when an operator (not the system) decides the payout must be retried under a fresh idempotency key — for example, after a Stripe-side failure that Stripe will not let us re-submit under the original key. System-driven retries (network timeout, transient Stripe error, Inngest retry) use the same key. This is the entire point of idempotency.

Transfer creation

import { multiplyRate, toCents } from '@/lib/money';

const transfer = await stripe.transfers.create(
  {
    amount: Number(payoutRecord.amount_cents), // safe: amount fits i32 for any realistic payout
    currency: 'usd',
    destination: tenant.stripe_connect_account_id,
    description: `Platform payout to ${tenant.display_name}`,
    metadata: {
      tenant_id: tenantId,
      platform_payout_id: payoutRecord.id,
      attempt_generation: String(payoutRecord.attempt_generation),
    },
  },
  {
    idempotencyKey: `payout-${payoutRecord.id}-gen${payoutRecord.attempt_generation}`,
  }
);

Transaction ordering contract

The order of operations matters for recoverability:

  1. Write payout_records row first, status 'processing', with attempt_generation = 1 (or current value if retry).
  2. Then call Stripe with the idempotency key derived from the payout_records.id and attempt_generation.
  3. On Stripe response, update the payout_records row with stripe_transfer_id.

This order makes the platform DB the source of truth for "did we intend to make this transfer." If step 1 completes but step 2 is interrupted (network failure, server crash, Inngest job killed), the reconciliation job (Inngest, every 5 minutes) finds the 'processing' row and queries Stripe by idempotency key to determine actual state:

  • Stripe has a transfer for the key → mark payout_records with stripe_transfer_id, status follows the Stripe state.
  • Stripe has no transfer for the key → the call never reached Stripe; re-attempt with the same key (idempotent).

If the order were reversed — Stripe call first, then DB write — a successful Stripe response that fails to reach the platform DB write step creates an orphan transfer with no platform record. Reconciliation would have no way to find it (no key to query Stripe by; the key would never have been generated and stored).

Reverse-order is forbidden. The spec asserts this as a correctness constraint, not a preference.

Failure response matrix

Step 1 (DB write)Step 2 (Stripe call)Recovery
SuccessSuccessNormal path; status updates on webhook per §14.7
SuccessTimeout / network errorReconciliation job (5-min cycle) queries Stripe by idempotency key; updates state
SuccessExplicit Stripe error (insufficient funds, etc.)payout_records status → 'failed'; alert platform admin

payout_records schema addition

public.payout_records (defined in §5.3) gains one column:

ALTER TABLE public.payout_records
  ADD COLUMN attempt_generation INTEGER NOT NULL DEFAULT 1;

The payout_records row is written in status = 'processing' BEFORE the Stripe call. The row's UUID becomes part of the idempotency key. On Stripe's response:

  • Success → update row with stripe_transfer_id, leave status 'processing' until the Stripe webhook confirms 'paid' per §14.6.
  • Stripe network error / timeout → row stays in 'processing'; a reconciliation job (Inngest, every 5 minutes) queries Stripe for the transfer by the row's idempotency key and resolves the state.
  • Stripe rejection that cannot be retried under the same key (rare): operator increments attempt_generation after investigation and re-runs.

Why deterministic key matters

A non-deterministic key (e.g., the previous draft's Date.now()) defeats Stripe's idempotency cache. Every retry produces a new key, so every retry creates a new transfer. Networks fail, Stripe times out, Inngest retries — without a deterministic key, every one of these produces a duplicate payout. This is the most expensive bug shape in the platform.

Calls Worth Flagging

  • amount_cents is BIGINT in the row, but Stripe's API takes a JavaScript number. BIGINT can hold values larger than Number.MAX_SAFE_INTEGER (2^53 - 1 cents = roughly $90 trillion). At realistic payout sizes this is fine, but the boundary is worth the assertion. The transfer code SHOULD assert amount_cents <= Number.MAX_SAFE_INTEGER before passing to Stripe.
  • The reconciliation job is part of the design, not an afterthought. Without it, a Stripe-side success that we never see (because the response timed out before reaching us) leaves the row in 'processing' forever and the operator has to investigate manually. Build the job in Phase 1 alongside the transfer code.
  • attempt_generation is operator-driven, not automatic. Auto-incrementing it on any failure would re-introduce the duplicate-payout bug. The whole point is that the system retries the same key; only humans cross the boundary to a new generation.

Two paths for ingesting host commission statements:

  • Automated (host has API): Inngest cron daily fetches and matches by provider_booking_ref
  • Manual upload (PDF/CSV): Haiku parses; admin reviews and confirms matches

14.9 Clawback Handling ¶

Cancellations during hold period: deduct from pending balance (no money has moved). After hold release: deduct from available. After payout: Stripe transfer reversal within 60 days, then contractual recovery.

14.10 Stripe Connect Pricing (Verified Mid-2026) ¶

  • Subscription billing: 2.9% + $0.30 per card transaction
  • Connect Express accounts: $2/month per active account
  • Payouts: 0.25% + $0.25 per payout
  • ACH (standard): 0.8% capped at $5
  • Instant payouts (optional): ~1%, not enabled by default

14.11 1099-NEC Reporting ¶

Stripe Connect Express handles 1099-NEC generation for sub-hosts ≥ $600/year. Platform’s only responsibility: ensure all payouts flow through Connect (no off-platform payments). Stripe files with IRS and provides sub-host’s copy via Connect dashboard.
