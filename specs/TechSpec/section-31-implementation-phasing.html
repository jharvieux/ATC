Section 31 — Implementation Phasing

This section sequences how the v6 spec gets built. It defines what ships in launch, what comes next, and what’s deferred to later phases. The goal is to minimize the time to ‘first real customer interaction on a real tenant generating a real commission’ while preserving optionality for the rest.

31.1 Phasing Philosophy ¶

Three principles drive sequencing:

  • Money path first. The platform exists to facilitate bookings that generate commissions. Anything not on the money path can wait. Auth, chat, CRM, booking flow, commission tracking, payout — these block first revenue. Group bookings, forum, white-label branding, multi-prong tenant types — these don’t block first revenue.
  • First-party before third-party. Build for the platform’s own automated agency (Prong 1) before opening to BYO-host (Prong 2) or sub-host (Prong 3) tenants. The platform itself is the safest first tenant — every bug is found by the founder, not a paying customer.
  • Ship the minimum that exposes the design. Each phase should validate a meaningful chunk of the architecture against reality, not just cross items off a list. A phase that ships infrastructure with no observable customer value is a phase to compress or skip.

31.3 Phase 0 — Foundation (8-10 weeks) ¶

Goal: infrastructure in place, schema deployed, auth functional, skeleton app deployable. Nothing customer-facing yet.

Scope

  • Monorepo setup, two Vercel projects (main + RAG), CI pipeline per §29
  • Two Supabase projects (main + RAG) with initial schema from §5 and §6
  • RLS policies for all tenant-scoped tables — get this right early
  • Supabase Auth configured for Google, Microsoft, Facebook (per §17.1)
  • Tenant resolver middleware (§3.6)
  • Application-layer encryption setup for credentials (§13.5, §26.6)
  • Audit log table and write helper (§26.7)
  • assertPermission() pattern wired into a few sample routes (§26.3)
  • Stripe account in test mode; webhook handler skeleton verifies signatures
  • Anthropic + OpenAI integration smoke test
  • Inngest connected; one trivial scheduled job runs
  • Resend connected; one transactional email template renders
  • Sentry connected; errors are tracked
  • Boot-time env verification (§28.19)

Explicit exclusions

  • No real customer features
  • No persona system prompt design yet
  • No RAG retrieval (RAG service schema exists but isn’t queried)
  • No branding system
  • No public landing page beyond a placeholder

Done definition

Engineering team can: sign in via OAuth, see their resolved tenant, hit a permission-gated endpoint that audit-logs, deploy a change end-to-end via the pipeline, observe errors in Sentry. Cross-tenant probe tests (§30.8) pass.

31.4 Phase 1 — First Revenue (8-10 weeks) ¶

Goal: the platform’s own automated agency (Prong 1) can take a real customer through chat → quote → booking → commission tracking → first payout. One tenant. One persona. Bare functionality. Real money.

Scope

  • AI personas (§9): Marcus Cole only at first. Single persona, full prompt design, anti-instructions, tool-use wired up. Other 5 personas designed but not deployed.
  • AI Supervisor (§10): all preflight checks live. Topic-level escalation table working. Kill switch operational.
  • Chat UI (§24): customer-facing chat, streaming via SSE, AI disclosure banner, feedback buttons. Tone matching at default cap level 3 — full feature, no phasing.
  • Memory (§11): extraction every 10 turns. Customer memory page. Opt-out functional.
  • CRM (§12): contacts, basic pipeline, quotes. Multi-traveler support.
  • Host agency abstraction (§13): fallback email adapter live. One real adapter scaffolded but possibly not connected to a real host yet.
  • Booking flow (§20): native flow (since host selection may still be open). DOB-not-ages enforced. Pre-fill from CRM/memory.
  • Commissions (§14): lifecycle tracking, expected → received, manual statement reconciliation. Stripe Connect Express not yet required for Prong 1 (the platform pays itself).
  • RAG consumer side (§21): retrieval working. RAG knowledge block in prompts. Source attribution in responses.
  • RAG ingestion (§22): platform admin can submit content via batch + manual. Browser extension nice-to-have but defer if it slows things down. Pipeline normalization functional.
  • Email & notifications (§23): transactional emails (signup, quote sent, booking confirmation). Pre-cruise email series scaffolded but only 1-day email enabled at first.
  • Hallucination defense (§21.10): all 8 layers active. AI eval suite running nightly.
  • Versioned consent (§17.4): all three platform-level documents (ToU, Privacy, AI Disclaimer) accepted by every user.

Explicit exclusions

  • No BYO-host or sub-host onboarding (Prong 2, 3 sit dormant)
  • No tenant branding customization (platform’s own colors only)
  • No custom domains
  • No Pro/Agency tier features (single tier essentially)
  • No group bookings
  • No forum chat
  • No Gmail integration
  • No abuse monitoring enforcement (track but don’t throttle yet)
  • 5 personas designed but not deployed; Marcus only

Done definition

A real customer can: visit the platform, chat with Marcus, get a quote, book a real cruise, receive booking confirmation email, get a 1-day pre-cruise email, sail. The platform receives commission from host, reconciles it manually, and the founder takes home actual money.

The platform also: catches AI hallucinations in the eval suite at acceptable rates, logs every audit event, recovers from a Vercel deploy rollback test, recovers from a Supabase PITR test.

This phase ends with at least one paid booking — that’s the unambiguous success signal.

31.5 Phase 2 — Multi-Tenant (8-10 weeks) ¶

Goal: other tenants can onboard. BYO-host and sub-host paths both work. Full tier matrix enforced.

Scope

  • All 6 personas live (§9). Persona handoff working.
  • Sub-host onboarding (§15): full flow from signup through Stripe Connect Express setup through platform admin review to active. ICA acceptance live.
  • BYO-host onboarding: similar flow without sub-host commission split.
  • Stripe subscriptions: all tier prices set up in Stripe. Trial logic working. Billing webhook reliable.
  • Commission split (§14.3): two-party split (platform retains tier-defined percentage, sub-host receives remainder). Tier-rate lookup; missing tier flagged for admin.
  • Subcontractor tracking (§14.3a): sub-host can maintain named subcontractor list, tag bookings, see internal revenue forecast.
  • Stripe Connect Express transfers: payouts working with hold periods per tier. Statement PDFs generated.
  • White-label branding (§16): colors, logos, slogans, all tiers. Persona overrides (Pro+ display name, Agency addendum with Haiku screen).
  • Custom domains (§16.3): CNAME-based provisioning. Sub-Host Agency + BYO Agency only.
  • Custom email-from domain (§16.4): Pattern A and Pattern B both supported.
  • Group bookings (§18): full feature including invitation flow, hero images, RSVP system, reminder cadence.
  • Forum chat (§19): AI moderation pipeline, threading, reactions, coordinator tools.
  • Gmail integration (§23.7): optional per-tenant; OAuth + Pub/Sub.
  • All persona variants and tone levels open (already shipped in Phase 1 but now exercised across many tenants).
  • Full pre-cruise email series live (all 4 emails enabled per §23.6).
  • AI co-pilot in booking flow (§20.4) if not already in Phase 1.
  • Abuse monitoring enforcement (§27): all dimensions tracking AND enforcing soft1/soft2/hard. Tenant-facing usage UI live.

Explicit exclusions

  • No multi-region (US-East only)
  • No native mobile apps
  • No Twilio SMS
  • No photo uploads in forum (text only)
  • No internationalization
  • No Apple OAuth

Done definition

A real outside sub-host can: sign up, complete onboarding, pass platform admin review, receive their first paying customer’s commission, see a real Stripe payout land in their bank account. A real BYO-host tenant can do the same without the Connect Express piece.

By end of Phase 2, the spec is feature-complete in everything customer-facing. Phase 3 is about scale, polish, and the explicitly-deferred items.

31.6 Phase 3 — Scale & Deferred (8-12 weeks) ¶

Goal: the explicitly-deferred features ship, and the platform absorbs real-world load.

Scope

  • Twilio SMS for notifications (TCPA-compliant)
  • Apple OAuth (requires $99/yr developer account; deferred per §17.1)
  • Email-in via forward-to address for RAG ingestion
  • Forum photo uploads with EXIF stripping and moderation pipeline extension (deferred per §19.11)
  • Native mobile apps consideration: spec the API contract, evaluate React Native vs native vs PWA; build if business case is clear
  • Internationalization scaffolding (locale resolution, content packs, but English-only content at launch)
  • Multi-region infrastructure investigation — DR posture review, decide whether to invest
  • Performance work informed by real production data: index tuning, query optimization, caching layer if needed
  • Threshold recalibration (§27) based on first 90 days of usage
  • AI eval expansion based on production conversation patterns
  • Read replicas if DB load justifies
  • Anthropic Tier 5 or higher if rate limits are being hit

Open Items From MEMORY (resolved in Phase 3 or earlier as needed)

  • ICA template SoT + E&O coverage clause language (attorney — needed before any sub-host onboarding, so really Phase 2 blocker)
  • ToU RAG content license clause for submissions (attorney — also Phase 2 blocker for ingestion ToU acceptance)
  • §20 final design after host agency selected (Phase 1 or 2 trigger event)
  • Persona avatar URLs (Phase 1 trigger)
  • Port info chunks seeding for major North American departure ports (Phase 1 launch task)
  • Tenant owner death/incapacitation handling (operational policy, can defer to Phase 3 unless event forces sooner)
  • Generated image moderation latency (Phase 2 when used in groups)
  • Native mobile API contract considerations (Phase 3 prep)
  • Stripe Connect KYC failure UX flows (Phase 2 when sub-host onboarding lives)

Done definition

Spec is fully delivered. Platform operates at sustained tenant scale (target: 50+ active tenants, 500+ active customers). Operational runbooks are battle-tested. Engineering capacity shifts from build to maintain + grow.

31.7 Cross-Phase Risks & Decisions ¶

A few items don’t fit neatly inside a phase and need explicit decision points:

Host agency selection

The host agency selection blocks the §20 booking flow design. Two paths:

  • Decide host before Phase 1 starts: ideal. Booking flow gets designed once. Higher confidence in Phase 1 timeline.
  • Phase 1 ships with fallback email adapter only; host selection during Phase 1: acceptable for Prong 1 since the platform IS its own host operationally. Real bookings can be manually submitted to chosen host while integration is built.

The decision affects whether real customer bookings in Phase 1 are end-to-end automated or have manual steps. Neither breaks the phase, but the user experience differs.

Pre-cruise email enablement

The 90-day, 30-day, and 7-day emails involve more dynamic content (destination teasers, packing checklists, ship highlights) than the 1-day port-info email. Enabling them all in Phase 1 is fine if content authoring keeps pace. Otherwise: 1-day first, others as content gets written.

Browser extension and iOS shortcut

These are tenant-facing tools for RAG submission. The platform admin can submit content without them. If platform admin is willing to use the manual / batch ingestion paths in Phase 1: defer extension and shortcut to Phase 2. If platform admin’s content workflow specifically needs browser-clip behavior: ship the extension in Phase 1.

Tenant-facing usage UI vs. enforcement timing

Abuse monitoring (§27) has two pieces: (a) track usage in real-time, (b) enforce soft/hard limits. Phase 1 does (a) but not (b) — too risky to enforce limits on the platform’s own tenant while the system is still being calibrated. Phase 2 turns enforcement on for all tenants.

But: the platform’s own tenant doesn’t get rate-limited at any phase (it’s the platform). Other tenants face enforcement from the moment they onboard in Phase 2.

Legal documents

ToU, Privacy Policy, AI Liability Disclaimer must be lawyer-reviewed before any user (even Phase 1 customers) accepts them. ICA must be lawyer-reviewed before any sub-host signs.

The reviewed-by-attorney lead time is a real risk to Phase 1 if not started early. Recommend: brief attorney during Phase 0; have drafts ready by mid-Phase 1.

Initial RAG seeding

Phase 1 needs enough RAG content for personas to actually be useful. Empty RAG → AI relies on training data alone → quality degrades, freshness suffers. Phase 0 should include a content-seeding effort (port info per departure city, major cruise line basics, common cabin categories).

This isn’t full coverage; it’s enough that retrieval consistently returns at least 2-3 relevant chunks for typical queries.

31.8 What Each Phase Validates ¶

PhaseValidates
0Architecture deployable. Cross-tenant isolation correct. Audit log captures meaningful events.
1AI behavior is acceptably safe and useful for real customers. Commission tracking is accurate. Hallucination defense works. Per-customer AI cost is in plan.
2Multi-tenancy holds under multiple real tenants. Branding and custom domains work. Stripe Connect Express handles real KYC and payouts. Tier matrix actually maps to tenant economics.

Each phase’s done-definition is ‘this thing genuinely works in production with real users and real money,’ not ‘the feature exists in the codebase.’

31.9 Resource Assumptions ¶

I’ve sized phases for a small dedicated team: 2-3 engineers, 1 platform operator wearing PM + design + ops hats. Larger teams compress; solo engineering extends. Real time-to-feature-complete depends heavily on:

  • Whether the operator is the engineer (faster decisions, slower hands)
  • Host agency integration complexity (the unknown)
  • Attorney response times on legal docs
  • Cumulative Anthropic spend during pre-launch eval iterations
  • Stripe Connect onboarding-flow friction (sometimes Stripe support is in the loop)

The phase estimates are planning anchors. Real-world iteration will diverge.

31.10 What’s Explicitly Out Of v6 ¶

  • Multi-region active-active deployment
  • White-label of the platform itself (sub-licensing the SaaS to other operators)
  • Per-tenant Stripe products / custom pricing UI
  • Non-English customer content (quotes, emails, legal docs)
  • Non-USD currency
  • Air + hotel bookings beyond cruise
  • Loyalty program integration beyond storing membership numbers
  • Native mobile apps as a hard commitment (Phase 3 evaluates; may not build)
  • Email-in for customer chat (separate concern from RAG ingestion email-in)

31.11 Calls Worth Flagging ¶

  • Phase 0 has no customer value. It’s pure setup. Resist the urge to cut it short. Cross-tenant bugs found here cost minutes; cross-tenant bugs found in Phase 2 cost weeks.
  • Phase 1 success is binary: at least one paid booking. Without that signal, the platform hasn’t validated its core business proposition. Optimize ruthlessly toward that outcome.
  • Host agency selection is the highest-leverage early decision. It blocks §20 and influences §13. Don’t let it drift into Phase 1 if possible.
  • Attorney time is the most common Phase 1 schedule slip. Brief legal counsel during Phase 0. Send drafts early. Don’t wait for ‘feature-complete’ before sending; legal review can run in parallel.
  • The platform’s own Prong-1 tenant should keep operating throughout Phase 2 and 3 as a real-money proof of concept and as the canary for new features. New AI behavior, new email templates, new flows — try on Prong 1 first, then expose to tenants.
  • My phase estimates of 8-10 weeks each are conservative-optimistic, not pessimistic. Engineering projects routinely overrun. If you need to commit dates to anyone external, double these estimates and treat the original as stretch.
  • No formal ‘v6.0 launch event.’ The platform goes live with Phase 1 (Prong 1 only) and grows. There’s no big-bang launch — there’s ‘first booking’ then ‘first outside tenant onboarded’ then ‘tenth tenant active’ then ‘first month of profitable operation.’
  • Phase 3 length is the most uncertain. Heavy production data informs scope. Could be 6 weeks if things go smoothly or 16 weeks if Anthropic pricing changes or scale exposes issues.
