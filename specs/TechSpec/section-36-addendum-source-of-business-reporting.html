Section 36 - Addendum — Source-of-Business Reporting

Status: Addendum. Lands after §35 (which produces the underlying data). References existing sections by number; adds a new cancellation_reason_category enum to the bookings table.

Why an addendum, not a retrofit: Reporting is downstream of attribution capture and cancellation tracking. Both data sources land in §35 and §36.5 respectively. The reports themselves are a self-contained surface that does not modify any existing build-prompted section.

36.1 Overview ¶

The platform provides a Source-of-Business Reporting dashboard in the CRM, available to tenant owners and agents. Reports answer questions like:

  • Which campaigns acquire the most leads?
  • Which channels close the most bookings, by count and by commission?
  • What is the conversion funnel from contact to quote to booking?
  • How much revenue are we losing to cancellations, broken down by reason?

Data sources:

  • §35 attribution data — contacts.first_touch_*, quotes.conversion_touch_*, bookings.conversion_touch_*, attribution_touches
  • §12 CRM tables — contacts, quotes
  • §14 commission tables — bookings, commissions
  • §34.8 clawback fields — commissions.clawback_*
  • New cancellation category enum (§36.5)

36.3 Date Filters and Grouping ¶

All reports support:

  • Date range — default trailing 90 days; user-adjustable. Date applies to:
    • Leads by source: contacts.first_touch_at
    • Bookings/Campaigns/Funnel: bookings.created_at
    • Cancellations: bookings.cancelled_at
  • Grouping — day, week, month, quarter; default by month for ranges > 30 days, by day for shorter ranges
  • Tenant scope — automatically scoped via RLS; no cross-tenant aggregation possible
  • Agent filter — Agency-tier tenants with multiple users can filter by which agent created the contact/quote/booking

Maximum date range is bounded by the tenant's data retention horizon per §25.

36.4 Campaigns Table ¶

The Campaign performance report needs per-campaign cost data for cost-per-lead calculations. A new optional table:

CREATE TABLE public.campaigns (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),
  utm_campaign TEXT NOT NULL,
  display_name TEXT,
  campaign_cost_cents BIGINT,         -- nullable: agent may not record cost
  currency TEXT NOT NULL DEFAULT 'USD',
  campaign_start DATE,
  campaign_end   DATE,
  notes TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (tenant_id, utm_campaign)
);

ALTER TABLE public.campaigns ENABLE ROW LEVEL SECURITY;

Tenants register campaigns proactively (before sending traffic with a new utm_campaign value) or retroactively (after observing a campaign in their attribution data). The Campaign report joins attribution_rollup against campaigns on (tenant_id, utm_campaign); campaigns not registered show up with NULL cost and the cost-per-lead column shows "not set" rather than zero.

Money rules from §14.0 apply unchanged: campaign_cost_cents is BIGINT cents, computations go through the money utility module, currency stored on row.

36.5 Cancellation Reason Category Enum ¶

A new optional enum on bookings for structured cancellation reporting. The existing free-text cancellation_reason field (per §5) is retained for nuance; the new category enum provides the grouping dimension for the cancellations report.

ALTER TABLE public.bookings
  ADD COLUMN cancellation_reason_category TEXT
    CHECK (cancellation_reason_category IN (
      'customer_change_of_mind',
      'medical',
      'family_emergency',
      'financial',
      'cruise_line_change',
      'weather_or_natural_disaster',
      'poor_prior_experience_with_line',
      'other'
    ));

CREATE INDEX bookings_cancel_category_idx
  ON public.bookings(tenant_id, cancellation_reason_category)
  WHERE cancellation_reason_category IS NOT NULL;

36.5.2 Setting the category ¶

Category is set by the agent during the cancellation flow (§20.9). The cancellation UI presents:

  • The free-text cancellation_reason field (existing, required)
  • The new cancellation_reason_category dropdown (optional in v1; the agent can leave it null if no category fits)
  • Optional AI suggestion: a Haiku call on the free-text reason proposes a category; the agent can accept or override

If the agent does not set a category, the field stays NULL and the cancellations report groups it as uncategorized (a UI-derived label, not a DB value).

36.6 Materialized View (attribution_rollup) ¶

High-volume attribution reports query a nightly-refreshed materialized view. Live queries are used for the First-touch vs Last-touch comparison report (small result set with complex dimension pair) and the Cancellations report (low volume — cancellations are infrequent relative to bookings).

36.6.1 View definition ¶

CREATE MATERIALIZED VIEW public.attribution_rollup AS
  SELECT
    c.tenant_id,
    DATE_TRUNC('day', c.created_at) AS day,
    c.first_touch_channel,
    c.first_touch_utm_source,
    c.first_touch_utm_medium,
    c.first_touch_utm_campaign,
    COUNT(DISTINCT c.id) AS contacts_acquired,
    COUNT(DISTINCT q.id) AS quotes_created,
    COUNT(DISTINCT b.id) FILTER (
      WHERE b.status NOT IN ('cancelled','draft')
    ) AS bookings_confirmed,
    COUNT(DISTINCT b.id) FILTER (
      WHERE b.status = 'cancelled'
    ) AS bookings_cancelled,
    COALESCE(SUM(cm.gross_commission_cents) FILTER (
      WHERE b.status NOT IN ('cancelled','draft')
    ), 0) AS gross_commission_cents,
    COALESCE(SUM(cm.net_commission_cents) FILTER (
      WHERE b.status NOT IN ('cancelled','draft')
    ), 0) AS net_commission_cents
  FROM public.contacts c
  LEFT JOIN public.quotes      q  ON q.contact_id = c.id  AND q.tenant_id = c.tenant_id
  LEFT JOIN public.bookings    b  ON b.contact_id = c.id  AND b.tenant_id = c.tenant_id
  LEFT JOIN public.commissions cm ON cm.booking_id = b.id AND cm.tenant_id = c.tenant_id
  GROUP BY 1, 2, 3, 4, 5, 6;

-- Unique index required for CONCURRENTLY refresh
CREATE UNIQUE INDEX attribution_rollup_pk
  ON public.attribution_rollup(
    tenant_id, day,
    first_touch_channel,
    first_touch_utm_source,
    first_touch_utm_medium,
    first_touch_utm_campaign
  );

-- Tenant-scoped query indexes
CREATE INDEX attribution_rollup_tenant_day_idx
  ON public.attribution_rollup(tenant_id, day);
CREATE INDEX attribution_rollup_campaign_idx
  ON public.attribution_rollup(tenant_id, first_touch_utm_campaign)
  WHERE first_touch_utm_campaign IS NOT NULL;

36.6.2 Refresh cadence ¶

Nightly refresh via Inngest scheduled function:

export const refreshAttributionRollup = inngest.createFunction(
  { id: 'attribution-rollup-refresh' },
  { cron: '0 3 * * *' },           // 03:00 UTC nightly
  async ({ step }) => {
    await step.run('refresh', async () => {
      // CONCURRENTLY so reports do not block during refresh.
      // Service-role DB client required (per §26.3a discipline).
      await serviceRoleClient().query(
        'REFRESH MATERIALIZED VIEW CONCURRENTLY public.attribution_rollup'
      );
    });
  }
);

CONCURRENTLY requires the unique index defined in §36.6.1 and prevents read locks during refresh, so dashboards remain responsive overnight.

36.6.3 Freshness expectations ¶

Reports built on attribution_rollup show data as of the previous nightly refresh. The dashboard surfaces a freshness indicator: "Reports current as of [timestamp]." For tenants who want same-day data (e.g., to evaluate a campaign launched that morning), the First-touch vs Last-touch and Cancellations reports query base tables live and reflect the current state. Other reports remain on the MV.

36.6.4 Why MV for some reports and live for others ¶

  • Leads / Bookings / Funnel / Campaign — aggregate over many rows across long time windows. MV cost amortized over the day; query latency ~sub-second.
  • First-touch vs Last-touch comparison — dimension pair (first_channel, conversion_channel) has at most ~50 distinct value combinations. Live query is fast and benefits from same-day freshness.
  • Cancellations — low volume (cancellations are a minority of bookings). Live query handles drill-down to individual cancelled bookings without an MV-to-base-table hop.

36.7 Lost Revenue from Cancellations — Report Detail ¶

36.7.1 Report measures ¶

  • Cancelled bookings count — COUNT(*) WHERE bookings.status = 'cancelled' AND cancelled_at BETWEEN :date_range
  • Lost expected commission — sum of gross_commission_cents for cancelled bookings whose commission state was expected at cancellation time (commission never received). This is the commission that would have been earned. Calculated as: SUM(commissions.gross_commission_cents) WHERE bookings.status = 'cancelled' AND commissions.received_commission_cents = 0.
  • Clawed-back received commission — sum of clawback_amount_cents from the §34.8 clawback fields. Actual money out.
  • Net financial impact — sum of the above two: total lost agency revenue from cancellations in the period.

36.7.2 Dimensional drill-down ¶

The report defaults to grouping by cancellation_reason_category (or uncategorized for NULL values). Secondary grouping options:

  • By conversion_touch_channel — reveals patterns like "Facebook leads cancel more often"
  • By cruise line (bookings.cruise_line) — reveals patterns like "Royal cancellations spiked Q3"
  • By sail-date quarter (DATE_TRUNC('quarter', bookings.sailing_date)) — reveals which future quarters have the most cancellation exposure
  • By agent (Agency-tier) — workload distribution analysis

36.7.3 Drill-down to bookings ¶

Each aggregated row supports drill-down to the underlying bookings: clicking the count or amount opens a list of the bookings contributing to that cell, with links to each booking's detail page. Standard CRM permission gates apply.

36.7.4 Query shape ¶

-- Tenant scope enforced via RLS; tenant_id in WHERE is defense-in-depth.
SELECT
  COALESCE(b.cancellation_reason_category, 'uncategorized') AS category,
  b.conversion_touch_channel,
  DATE_TRUNC('quarter', b.sailing_date) AS sail_quarter,
  COUNT(*) AS cancelled_count,
  COALESCE(SUM(cm.gross_commission_cents) FILTER (
    WHERE cm.received_commission_cents = 0
  ), 0) AS lost_expected_cents,
  COALESCE(SUM(cm.clawback_amount_cents), 0) AS clawback_cents,
  COALESCE(SUM(cm.gross_commission_cents) FILTER (
    WHERE cm.received_commission_cents = 0
  ), 0)
    + COALESCE(SUM(cm.clawback_amount_cents), 0) AS net_impact_cents
FROM public.bookings b
LEFT JOIN public.commissions cm ON cm.booking_id = b.id AND cm.tenant_id = b.tenant_id
WHERE b.tenant_id = :tenant_id
  AND b.status = 'cancelled'
  AND b.cancelled_at BETWEEN :start AND :end
GROUP BY 1, 2, 3
ORDER BY net_impact_cents DESC;

36.8 Export ¶

Every report supports CSV export. Export contents are exactly what's visible in the report (respects current filters, date range, grouping). Money values export as plain decimal dollars (e.g., 1234.56) with currency as a separate column, not as cents. This format matches what tenants expect when importing into spreadsheets or other accounting tools.

Larger exports (> 10,000 rows) are processed asynchronously: the tenant receives an in-app notification and email when the export is ready for download. Synchronous export ceiling: 10,000 rows.

36.9 Dashboard UX ¶

  • Single "Reports" entry in the CRM nav, with the six standard reports listed in §36.2
  • Each report is a single page with filters at top, visualization in the middle (chart appropriate to the data shape), data table below
  • Charts default to bar charts for categorical dimensions and line charts for time-series
  • Mobile-responsive (per §24 general UX guidance), but reports are primarily a desktop experience
  • "Last refreshed" indicator on MV-backed reports; "Live" indicator on live-query reports

36.11 Calls Worth Flagging ¶

  • Cancellation report depends on §14.9 clawback handling writing to the new clawback_* fields per §34.8. If §14.9 is implemented without writing those fields, the "Clawed-back received commission" measure will report zero for all bookings. Build coordination required: §14.9 implementation must populate clawback fields.
  • Materialized view stale by up to ~24h. A tenant launching a campaign at 9am may not see leads in the report until the next 03:00 UTC refresh. Documented in the freshness indicator. If demand for hourly refresh emerges, the tradeoff is increased DB load — defer until measured.
  • Cancellation category enum will evolve. The eight values in v1 may prove insufficient or have overlap (e.g., is a death in the family medical or family_emergency?). Plan a v1.1 review after 6 months of real data to add/refine categories. Schema migration to add an enum value is straightforward.
  • The Haiku-suggested category from §36.5.2 needs validation against tenant patterns. If suggestions are routinely wrong, agents will ignore them and the field will stay sparse, degrading report value.
  • Cost-per-lead requires campaign cost entry. Tenants who don't track their ad spend in the platform get NULL cost-per-lead. The Campaign report should make missing cost data obviously visible ("Set cost to see CPL") to drive tenants to enter it.
  • Multi-tenant fairness in the MV refresh. If one tenant has 10x the data volume of others, the nightly refresh consumes proportionally more DB resources for that tenant. Acceptable at v1 scale; partitioning attribution_rollup by tenant_id is the answer if it becomes a problem.
  • Date-range edge cases for the cancellations report. A booking made in Q1 that's cancelled in Q3 will show up only when the report date range includes Q3 (because the filter is on cancelled_at). If a tenant wants "all cancellations that affected my Q1 revenue," that's a different report — flag for future enhancement.
