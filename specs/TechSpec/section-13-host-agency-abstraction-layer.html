Section 13 — Host Agency Abstraction Layer

The platform must work without being tightly coupled to any specific host agency. v6 makes the host agency a pluggable adapter — adding a new host means writing an adapter, not rewriting the platform.

13.1 Goals ¶

  • Decouple application from host-specific API quirks
  • Allow multiple host configurations simultaneously
  • Support ‘no host configured’ state gracefully (via fallback email adapter)

13.2 The HostAgencyClient Interface ¶

13.4 Tenant Host Configuration ¶

CREATE TABLE public.tenant_host_configs (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

tenant_id UUID NOT NULL REFERENCES public.tenants(id) ON DELETE RESTRICT,

adapter_id TEXT NOT NULL REFERENCES public.host_adapters(adapter_id),

credentials JSONB NOT NULL, – encrypted at rest (AES-256-GCM, KMS key in env)

UNIQUE (tenant_id, adapter_id)

);

13.5 Credential Storage Pattern ¶

Tenant host credentials are encrypted at the application layer before being written to the DB. The encryption uses AES-256-GCM with a per-record IV. This protects against DB-level breach: an attacker who somehow gets read access to the DB sees only ciphertext.

Per-tenant credentials cannot be in environment variables (would require deployment per onboarded tenant). DB storage with app-layer encryption is the right pattern for this cardinality.

13.5.1 Key storage and rotation ¶

The encryption key set is held in environment variables:

  • APP_ENCRYPTION_KEY_CURRENT — 256-bit key (base64 encoded), used for new writes.
  • APP_ENCRYPTION_KEY_PREVIOUS — set during key rotation; used for decrypting records written under the previous key. Read-path only.
  • APP_ENCRYPTION_KEY_ID_CURRENT — short identifier (e.g., v3) stamped onto every ciphertext so the decryption path knows which key to use.

Rotation is annual per §28.20. The rotation flow:

  1. Generate new key. Set APP_ENCRYPTION_KEY_PREVIOUS = <current>, APP_ENCRYPTION_KEY_CURRENT = <new>, APP_ENCRYPTION_KEY_ID_CURRENT = <new id>. Deploy.
  2. All new writes use the new key.
  3. Decryption path: tries CURRENT first; on key-id mismatch, falls back to PREVIOUS.
  4. A background job (Inngest, re-encrypt-old-records) re-reads and re-writes records still ciphered under the previous key. Job runs until zero records remain at the old key id.
  5. Remove APP_ENCRYPTION_KEY_PREVIOUS from environment. Rotation complete.

13.5.2 Disaster recovery — the failure modes ¶

The encryption keys are operator-managed secrets. Three failure modes:

  1. Both keys lost (env vars deleted in Vercel, no offsite backup): every encrypted record becomes unrecoverable. The data is intact in the database but cannot be decrypted. Effect: every tenant's host adapter credentials, every tenant's Resend API key, every tenant's encrypted secret is dead. Recovery requires every tenant to re-enter their credentials.
  2. Decryption failure on a specific record (corrupt ciphertext, key-id mismatch with no matching key, GCM auth tag mismatch): a single tenant credential cannot be decrypted. Effect depends on which credential — if it's the tenant's host adapter, bookings for that tenant pause until resolved.
  3. Key rotation gone wrong (CURRENT key incorrect, PREVIOUS key removed prematurely, key IDs mismatched): some records decrypt correctly, others don't. The system appears to work for some tenants and not others; diagnosis is harder than (1) or (2).

13.5.3 Disaster recovery — controls ¶

To prevent failure mode (1):

  • Offsite key backup is mandatory. At setup time and on every rotation, the current and previous keys are stored in a secondary location independent of Vercel env vars. Recommended: 1Password business vault, or AWS Secrets Manager in a separate AWS account, or a hardware-backed offline copy stored physically. The choice is operator preference; the discipline is non-negotiable.
  • Backup verification quarterly. Operator restores the key set from the backup to a sandbox environment and confirms decryption of a known-good test ciphertext. If the test fails, the backup is unreliable — fix immediately. Logged to MEMORY.md per §A.X (see cross-reference at the end of this section).
  • Vercel env var deletion is gated. Platform admin's Vercel account does NOT have permission to delete APP_ENCRYPTION_KEY_* env vars without 2FA challenge. (Vercel may or may not support this granularity natively; if not, a runbook step requires the deletion to be performed only after the backup is verified — enforced by operator discipline.)

To handle failure mode (2):

  • The decryption wrapper catches decryption failures and returns a structured error (NOT a thrown exception that crashes the request). The error includes the record's key id so investigation is fast.
  • Code paths that consume credentials check for the structured-error result and pause the tenant's affected operations rather than silently retrying or returning incorrect data.
  • Specifically: if a host adapter's credentials fail to decrypt, the booking submission path returns a tenant-facing error ("Your host adapter credentials need to be re-entered — please visit Settings > Host Integration"). It does NOT silently fall back to the email adapter (per §13.6) — that would mask a security incident.
  • Decryption failures are logged to audit_log with action = 'credential.decryption_failed' and a redacted ciphertext hash (NOT the ciphertext itself) for forensic correlation.

To handle failure mode (3):

  • A boot-time check (extending §28.19's env validation) confirms that BOTH APP_ENCRYPTION_KEY_CURRENT and APP_ENCRYPTION_KEY_ID_CURRENT are present and that the keys are valid 256-bit base64 strings. If APP_ENCRYPTION_KEY_PREVIOUS is set, it must also be valid.
  • The re-encrypt-old-records job has a monitoring metric: credentials_at_previous_key_count. Alert if this metric is non-zero for more than 7 days after a rotation — indicates the job is stuck or rotation is incomplete.

13.5.4 Decryption-failure tenant operations ¶

When a tenant's credential cannot be decrypted, the tenant's state transitions to a partial-degraded mode. The semantics:

  • Reads of historical data unaffected. Booking history, commission records, conversation messages — all still readable. The affected credential is specifically the host-adapter or external-service credential.
  • New operations requiring the failed credential are blocked. The tenant sees a clear in-app banner: "Your [host adapter / Resend account / etc.] credentials cannot be loaded. Please re-enter them in Settings to resume [bookings / outbound email / etc.]"
  • Tenant-facing operation that doesn't need the failed credential proceeds normally. A tenant whose host-adapter credential failed can still send and receive emails, view CRM, etc.
  • Platform admin alerted on first occurrence per tenant. Not on every retry — first decryption failure for a given credential per tenant per 24 hours opens a high-priority issue.

13.5.5 Calls Worth Flagging ¶

  • Offsite key backup is the single point of failure prevention. The cost is low (a few minutes to copy keys to 1Password); the cost of skipping it is unrecoverable data. Make backup verification a Phase-0 launch gate.
  • The decryption-failure tenant-facing error is deliberately specific. A generic "something went wrong" lets the tenant click Retry indefinitely; a specific "credentials need to be re-entered" gets the tenant to the right place quickly.
  • Re-encryption job timing matters during rotation. The job re-writes every encrypted record. For a tenant with many encrypted records (multiple host adapters, many API keys), the re-write produces audit log noise. Acceptable, but expect a spike in credential.rotation_reencrypt audit rows during the days following rotation.
  • **The APP_ENCRYPTION_KEY_* env vars are NOT the same secret class as the Supabase service role key.** Service role key rotation per §28.20 is "on compromise only"; encryption keys rotate annually. Different threat models, different cadences. Don't conflate.

This subsection cross-references §28.13 (env var definitions) and §28.20 (rotation policy).

13.6 The Fallback Email Adapter ¶

Always-available adapter. Implements HostAgencyClient but does no integration — emails structured booking details to a configured destination. Used when:

  • Platform is in early operation without a host integration
  • A BYO-host tenant hasn’t configured their own host adapter
  • A real adapter is degraded or down

Returns synthetic provider_booking_ref like ‘EMAIL-{tenant_id}-{timestamp}’. Tenant admin manually updates with real reference once host confirms.

13.8 Sub-Host Credential Patterns ¶

  • Pattern A — Host-aware: host supports N sub-accounts under platform; each booking submitted with sub-host’s credentials
  • Pattern B — Aggregated: platform submits all bookings under master credentials; tracks sub-host ownership internally

Adapter declares which pattern it supports via capabilities. Both patterns supported in v6.

13.10 Anti-Patterns ¶

  • No host-specific code outside apps/main/src/lib/host/adapters/
  • No business logic in adapter implementations (translation only)
  • No adapter calling another adapter
  • No long-lived adapter state (cached credentials only)
  • No silent adapter failures (structured HostError)
  • No undocumented adapter capabilities
  • No PII in host_adapter_calls audit log
