Section 8 — RAG Service Architecture

Architectural details for the standalone RAG service: deployment, authentication, API contracts, and inter-service patterns.

8.1 Deployment ¶

  • Separate Next.js project deployed on Vercel
  • Own Supabase project (separate from main app)
  • Endpoint pattern: rag.ai-travelconcierge.com or similar subdomain
  • Independent versioning and deployment cadence

8.2 Tenant Registry Sync ¶

The RAG service maintains a tenant_registry_shadow table mirroring the main app's tenants table. The shadow is kept in sync via the webhook from /api/tenant-events (§8.7) plus a nightly reconciliation cron. See §8.3 for the full shadow-table design and the fail-closed authentication contract.

Lazy auto-registration from JWT claims (earlier spec language) is REMOVED. It created a tenant-injection vector and has been replaced by the explicit shadow-table model. If a JWT arrives for a tenant_id not in the shadow, the request fails with 403; the tenant lifecycle event will sync via the main app's retry queue (per §8.7a) and nightly reconcile.

8.3 Service-to-Service Authentication ¶

All inter-service calls use JWT signed by the main app, verified by the RAG service.

  • Algorithm: RS256
  • TTL: 5 minutes
  • Claims: tenant_id, user_id (or service-identifier), persona_id, scope (read/write), jti
  • Replay protection: jti cache in RAG service Redis
  • Signing key in environment variable; rotated every 90 days with overlap window (raised from "annually" per H-5 — RS256 keys protecting cross-service auth should rotate more frequently than app-data encryption keys)

Fail-closed contract

Every check in the JWT validation path fails CLOSED. There is no fallback or fail-open mode. Each potential failure mode and its behavior:

Failure modeResponseWhy
JWT signature invalid401 rejectForged or wrong key
JWT expired (>5 min old)401 rejectReplay window exceeded
jti already seen (Redis cache)401 rejectReplay attempted
Redis unreachable503 rejectCannot verify replay protection; FAIL CLOSED. Do NOT proceed with un-checked jti.
tenant_id not in registry shadow403 rejectTenant unknown to RAG; lazy auto-registration removed per §8.2
tenant_id in registry shadow but status != 'active'403 rejectTenant suspended or terminated
Any other unexpected error500 rejectSurface for investigation; never proceed with partial validation

The contract is: if any check cannot complete, the request fails. There is no "best effort" mode.

Shadow tenant table

Per H-5 and C-7, the previous "lazy auto-registration" pattern is REMOVED. The RAG service must independently know which tenants are valid; it cannot derive that information from a JWT alone.

The RAG service maintains a tenant_registry_shadow table that mirrors the main app's tenants table, kept in sync via:

  1. Webhook from main app on every tenant lifecycle event (create, status change, terminate) — §8.7.
  2. Nightly full reconciliation cron that compares the shadow against /api/admin/tenants listing from the main app. Any drift produces an alert; the reconcile process corrects it.
CREATE TABLE public.tenant_registry_shadow (
  tenant_id UUID PRIMARY KEY,
  status TEXT NOT NULL CHECK (status IN (
    'active', 'suspended', 'terminated',
    'pending_review', 'onboarding'
  )),
  tenant_type TEXT NOT NULL,
  display_name TEXT NOT NULL,
  last_webhook_sync_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_reconcile_sync_at TIMESTAMPTZ,
  source_revision INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX tenant_registry_shadow_status_idx
  ON public.tenant_registry_shadow(status);

The source_revision increments on every change in the main app and is shipped with the webhook payload. The RAG service uses it to detect out-of-order webhook delivery (a source_revision < shadow.source_revision webhook is ignored as stale).

Webhook delivery on failure

If the main app's webhook to RAG fails (network error, RAG service down), the main app:

  1. Retries 3 times with exponential backoff (1s, 5s, 30s).
  2. On final failure: writes to a pending_rag_sync table in the main app (per §8.7a) and returns success to the originating handler. The tenant lifecycle event is NOT blocked on RAG sync.
  3. A periodic cron (rag-sync-retry, every 5 minutes) processes pending_rag_sync rows.
  4. The nightly reconciliation handles anything still stuck.

A tenant lifecycle event that cannot reach RAG within 24 hours produces a platform admin alert. This bounds the worst-case inconsistency window.

Calls Worth Flagging

  • Redis unavailability is treated as service failure, not a bypass condition. The alternative (allow the request when Redis is down) re-opens the replay-attack window. Operational cost: a Redis outage takes down RAG retrieval. Mitigation: Redis HA + monitoring.
  • The shadow table is part of the RAG service Supabase project, not the main app's. Maintaining a copy is a deliberate duplication for defense in depth — the RAG service should be able to authorize requests without round-tripping to the main app.
  • 90-day key rotation is a tighter cadence than the encryption key rotation (§28.20 annual). Different threat models: app encryption keys protect data at rest; JWT signing keys protect cross-service auth. A leaked signing key is a faster path to tenant impersonation.
  • The nightly reconcile is the safety net for the entire shadow system. Without it, a missed webhook becomes permanent. The reconcile catches both directions of drift (extra rows in shadow, missing rows in shadow, status mismatches).

8.5 POST /api/ingest ¶

Submission endpoint. Accepts raw content for the normalization pipeline (§22). Returns queue item ID for status tracking.

8.6 POST /api/approve/tenant and /api/approve/global ¶

Approval endpoints called by main app when a tenant admin (or platform admin for global) approves a queue item. Creates the chunk.

8.7 POST /api/tenant-events ¶

Webhook receiver for tenant lifecycle events from main app: create, update status, terminate. Keeps tenant_registry in sync.

8.7a Main-App Retry Queue for RAG Sync ¶

The main app retries failed webhook deliveries to the RAG service before falling back to the nightly reconcile (which is the safety net per §8.3). The retry queue is stored in pending_rag_sync table.

Schema

CREATE TABLE public.pending_rag_sync (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id) ON DELETE RESTRICT,
  event_type TEXT NOT NULL CHECK (event_type IN (
    'tenant.created', 'tenant.status_changed',
    'tenant.terminated', 'tenant.metadata_updated'
  )),
  payload JSONB NOT NULL,
  source_revision INTEGER NOT NULL,
  attempt_count INTEGER NOT NULL DEFAULT 0,
  next_retry_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_attempt_at TIMESTAMPTZ,
  last_error TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  delivered_at TIMESTAMPTZ
);

CREATE INDEX pending_rag_sync_ready_idx
  ON public.pending_rag_sync(next_retry_at)
  WHERE delivered_at IS NULL;

Flow

  1. Tenant lifecycle event occurs in main app.
  2. Handler tries direct webhook delivery to RAG service.
  3. If delivery succeeds (HTTP 200): proceed normally; do NOT write to pending_rag_sync.
  4. If delivery fails: write a pending_rag_sync row with next_retry_at = NOW() + 1 minute.
  5. Inngest cron rag-sync-retry runs every 5 minutes:
  • Selects rows where delivered_at IS NULL AND next_retry_at <= NOW().
  • For each, attempts webhook delivery with the stored payload.
  • On success: set delivered_at = NOW(). Row is hard-deleted in nightly cleanup.
  • On failure: increment attempt_count; compute backoff; set next_retry_at. Log last_error. 6. If a row reaches attempt_count >= 10 (~20 hours of total retry time): alert platform admin.

Ordering and source_revision

The source_revision column (per Batch 4 B4-E5) is preserved on the retry queue. The RAG service's shadow-table sync logic uses source_revision to detect out-of-order delivery: a webhook with source_revision < shadow.source_revision is acknowledged but ignored. The retry queue does NOT need to deliver events in order.

Relationship to nightly reconcile

The retry queue handles short-term recovery (minutes to hours). The nightly reconcile (per §8.3) is the safety net for cases the retry queue cannot fix (extended RAG service downtime, handler bugs, schema mismatches).

Calls Worth Flagging

  • pending_rag_sync rows are deleted on success. No retention beyond active retry.
  • Idempotency on the RAG side matters. The source_revision filter is the primary defense against duplicate processing.
  • Platform admin alert at attempt_count >= 10 is a real intervention trigger.
  • Order independence enables aggressive parallelism.

8.8 PII Redaction at Ingestion ¶

Per §6.11 and §22.4: regex pre-filter for obvious patterns, then Haiku pass for subtler cases. Quarantine zero-tolerance items (passport, credit card). Redact tolerable items (names, emails, phones) with placeholders.

8.9 Scope Isolation ¶

RAG scope is strictly two-level: global (visible to all tenants) and tenant (visible only to that tenant). There is no inheritance, no ancestor walk, no cross-tenant visibility. A tenant’s submitted content stays in that tenant unless platform admin explicitly promotes it to global per §22.8.
