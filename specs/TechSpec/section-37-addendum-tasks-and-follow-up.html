Section 37 - Addendum — Tasks & Follow-up

Status: Addendum. Lands after Part 1–9 build prompts. Adds a task surface to the CRM that augments §12 pipeline stages with concrete actionable items. References existing sections by number; does not modify them in place.

Why an addendum, not a retrofit: Tasks are a cross-cutting feature that attaches to contacts, quotes, bookings, and conversations. The existing §12 pipeline defines stages but not the per-record action layer agents need to actually work the pipeline. Lands as a self-contained addition without modifying the pipeline definition.

37.1 Overview ¶

The platform's CRM pipeline (§12.3) defines lifecycle stages — Lead, Qualified, Quote Sent, Quote Accepted, Booked, Sailed. The Tasks & Follow-up surface adds the work agents do at each stage: "call back Tuesday," "send follow-up if quote not accepted in 5 days," "remind customer about final payment deadline."

Tasks cover three patterns:

  1. Ad-hoc tasks — agent-created, one-off, attached to a contact / quote / booking / conversation
  2. Sequenced follow-up cadences — predefined sequences (e.g., "post-quote nurture") that fire tasks on a schedule when triggered by a pipeline event
  3. System-generated tasks — automatically created from platform events (final payment approaching, passport expiring before sailing, document review pending)

Tasks have due dates, reminders, completion tracking, and optional assignment to specific seats in multi-agent tenants.

37.2 Task Schema ¶

CREATE TABLE public.tasks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),

  -- What this task is about (exactly one of contact/quote/booking/conversation is required)
  contact_id      UUID REFERENCES public.contacts(id)      ON DELETE CASCADE,
  quote_id        UUID REFERENCES public.quotes(id)        ON DELETE CASCADE,
  booking_id      UUID REFERENCES public.bookings(id)      ON DELETE CASCADE,
  conversation_id UUID REFERENCES public.conversations(id) ON DELETE CASCADE,

  -- Task content
  title TEXT NOT NULL,
  description TEXT,
  task_type TEXT NOT NULL CHECK (task_type IN (
    'call','email','text','meeting','follow_up','review','document','custom'
  )),

  -- Lifecycle
  status TEXT NOT NULL DEFAULT 'open'
    CHECK (status IN ('open','in_progress','completed','snoozed','cancelled')),
  priority TEXT NOT NULL DEFAULT 'normal'
    CHECK (priority IN ('low','normal','high','urgent')),

  -- Timing
  due_at TIMESTAMPTZ,
  due_is_all_day BOOLEAN NOT NULL DEFAULT FALSE,
  snoozed_until TIMESTAMPTZ,
  completed_at  TIMESTAMPTZ,

  -- Assignment
  assigned_to_user_id UUID REFERENCES public.users(id),
  created_by_user_id  UUID REFERENCES public.users(id),

  -- Origin (where did this task come from)
  origin TEXT NOT NULL DEFAULT 'manual'
    CHECK (origin IN ('manual','sequence','system','ai_suggested')),
  origin_reference TEXT,   -- e.g., sequence_id when origin='sequence', event_id when origin='system'

  -- Sequence tracking (per §37.4)
  sequence_run_id UUID REFERENCES public.task_sequence_runs(id) ON DELETE SET NULL,
  sequence_step_index INT,

  -- Audit
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- Exactly one record link required
  CHECK (
    (contact_id IS NOT NULL)::int +
    (quote_id IS NOT NULL)::int +
    (booking_id IS NOT NULL)::int +
    (conversation_id IS NOT NULL)::int = 1
  )
);

CREATE INDEX tasks_tenant_status_due_idx
  ON public.tasks(tenant_id, status, due_at)
  WHERE status IN ('open','in_progress','snoozed');

CREATE INDEX tasks_tenant_contact_idx
  ON public.tasks(tenant_id, contact_id)
  WHERE contact_id IS NOT NULL;

CREATE INDEX tasks_assigned_idx
  ON public.tasks(tenant_id, assigned_to_user_id, status)
  WHERE assigned_to_user_id IS NOT NULL AND status IN ('open','in_progress');

ALTER TABLE public.tasks ENABLE ROW LEVEL SECURITY;
-- RLS per §5.1: auth_user_in_tenant + tenant_is_active.

37.2.1 Why a single tasks table with optional FKs ¶

The schema uses four nullable foreign keys (contact_id, quote_id, booking_id, conversation_id) with a CHECK ensuring exactly one is populated. Alternative designs (separate tables per record type, polymorphic association) trade off differently:

  • Separate tables — would require four task tables. Increases query complexity (must UNION ALL to show all tasks for an agent). Rejected.
  • Polymorphic (target_type + target_id without FK) — loses referential integrity. Rejected.
  • Single table with nullable FKs — chosen. Database-enforced referential integrity per link type, single query path, simple indexes.

37.3 Task Reminders ¶

CREATE TABLE public.task_reminders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  task_id   UUID NOT NULL REFERENCES public.tasks(id) ON DELETE CASCADE,

  remind_at TIMESTAMPTZ NOT NULL,
  channel TEXT NOT NULL CHECK (channel IN ('in_app','email')),
  -- 'sms' deferred per §23.1 Twilio future scope
  fired_at TIMESTAMPTZ,
  fired_status TEXT CHECK (fired_status IN ('delivered','suppressed','failed')),

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX task_reminders_pending_idx
  ON public.task_reminders(remind_at)
  WHERE fired_at IS NULL;

ALTER TABLE public.task_reminders ENABLE ROW LEVEL SECURITY;

Multiple reminders per task supported (e.g., 1 day before, 1 hour before, at due time). Reminders fire via Inngest scheduled function that runs every minute and processes rows where remind_at <= NOW() AND fired_at IS NULL. After firing, fired_at and fired_status are set; rows are not deleted (retained for audit).

37.3.1 In-app reminders ¶

In-app channel produces a notification badge in the CRM nav and an item in the notifications panel. The notification links to the task. Notifications are read/unread tracked; suppressing further is the agent's responsibility.

37.3.2 Email reminders ¶

Email channel sends a templated email to the assigned user (or task creator if unassigned) per §23. Templates use React Email components and respect tenant branding. Suppression: if the user has unsubscribed from operational emails or the tenant has hard-bounced this address, the reminder is suppressed and fired_status = 'suppressed'.

37.3.3 Snoozing ¶

Snoozing a task sets status = 'snoozed' and snoozed_until. Future reminders prior to snoozed_until are suppressed; reminders at or after snoozed_until fire normally, and the system automatically transitions the task back to open at the snooze expiry.

37.4 Sequenced Follow-up Cadences ¶

Sequences are predefined task templates triggered by pipeline events. Example: when a quote enters status sent, a "post-quote nurture" sequence triggers:

  • Day 2: Task "Call to confirm receipt"
  • Day 5: Task "Follow up if not accepted"
  • Day 9: Task "Final follow-up before quote expires"

37.4.1 Sequence definition ¶

CREATE TABLE public.task_sequences (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),

  name TEXT NOT NULL,
  description TEXT,
  trigger_event TEXT NOT NULL CHECK (trigger_event IN (
    'lead_created',
    'quote_sent',
    'quote_accepted',
    'booking_created',
    'booking_confirmed',
    'pre_sail_60d',
    'post_sail_7d',
    'manual'              -- agent triggers explicitly
  )),

  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  applies_to_record TEXT NOT NULL DEFAULT 'auto'
    CHECK (applies_to_record IN ('auto','contact','quote','booking')),
  -- 'auto' = derived from trigger_event (lead_created→contact, quote_sent→quote, etc.)

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE public.task_sequence_steps (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  sequence_id UUID NOT NULL REFERENCES public.task_sequences(id) ON DELETE CASCADE,

  step_index INT NOT NULL,
  offset_days INT NOT NULL,            -- days from trigger event to task due_at
  offset_hours INT NOT NULL DEFAULT 0, -- additional hour offset for finer scheduling

  task_title_template TEXT NOT NULL,
  task_description_template TEXT,
  task_type TEXT NOT NULL,
  task_priority TEXT NOT NULL DEFAULT 'normal',
  reminder_offsets_minutes INT[] DEFAULT ARRAY[]::INT[],   -- minutes before due_at for reminders

  skip_if_status TEXT[],   -- skip step if record currently in any of these statuses (e.g., quote already accepted)

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (sequence_id, step_index)
);

CREATE TABLE public.task_sequence_runs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  sequence_id UUID NOT NULL REFERENCES public.task_sequences(id),

  -- What this run is for (exactly one)
  contact_id UUID REFERENCES public.contacts(id) ON DELETE CASCADE,
  quote_id   UUID REFERENCES public.quotes(id)   ON DELETE CASCADE,
  booking_id UUID REFERENCES public.bookings(id) ON DELETE CASCADE,

  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','completed','cancelled')),
  triggered_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  triggered_by_user_id UUID REFERENCES public.users(id),  -- null for system triggers
  completed_at TIMESTAMPTZ,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CHECK (
    (contact_id IS NOT NULL)::int +
    (quote_id IS NOT NULL)::int +
    (booking_id IS NOT NULL)::int = 1
  )
);

ALTER TABLE public.task_sequences      ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.task_sequence_steps ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.task_sequence_runs  ENABLE ROW LEVEL SECURITY;

37.4.2 Sequence triggering ¶

When a pipeline event occurs (e.g., a quote transitions to sent), the platform looks up active sequences whose trigger_event matches. For each match:

  1. A task_sequence_runs row is created.
  2. An Inngest event is dispatched: task_sequence.step_scheduled for each step in the sequence, with delay computed from offset_days + offset_hours.
  3. Each delayed event, when it fires, creates the corresponding tasks row (with origin='sequence', sequence_run_id, sequence_step_index) and any associated reminders.
  4. Before creating each task, the step checks skip_if_status against the record's current status. If matched, the step is skipped (logged but no task created).

37.4.3 Sequence cancellation ¶

A sequence run is cancelled when:

  • The associated record transitions to a terminal status (e.g., quote accepted, booking cancelled, contact deleted)
  • Agent explicitly cancels the run from the CRM UI
  • Tenant deactivates the sequence definition (existing runs continue or are cancelled per tenant choice during deactivation)

Cancellation sets task_sequence_runs.status = 'cancelled' and cancels all future (not yet fired) Inngest delayed events for that run. Already-created tasks remain — the agent decides whether to mark them complete or cancel them individually.

37.4.4 Template substitution ¶

Task title and description templates support simple variable substitution drawn from the associated record:

VariableValue
{{contact.first_name}}Contact's first name
{{contact.last_name}}Contact's last name
{{quote.cruise_line}}Cruise line on the associated quote
{{quote.sailing_date}}Sailing date on the quote
{{booking.cruise_line}}Cruise line on the associated booking
{{booking.sailing_date}}Sailing date on the booking
{{days_until_sailing}}Computed at task-creation time

Missing variables (e.g., {{quote.cruise_line}} on a contact-scoped sequence) render as empty string. Templates are stored as plain text; substitution is a string replace, not a Handlebars or Jinja runtime — keep it simple and safe.

37.4.5 Default sequences ¶

New tenants are seeded with the following starter sequences (active by default; tenant can disable or modify):

  • New lead nurture — trigger: lead_created. Steps: Day 1 "Initial outreach call", Day 3 "Follow up if no response", Day 7 "Final follow-up before marking cold"
  • Post-quote nurture — trigger: quote_sent. Steps: Day 2 "Confirm receipt", Day 5 "Follow up on questions", Day 9 "Quote expires soon — final push"
  • Booking confirmation follow-through — trigger: booking_confirmed. Steps: Day 1 "Send welcome packet", Day 30 "Check excursion preferences", Day -60 (pre-sail) "Confirm passport and travel docs"
  • Post-cruise review request — trigger: post_sail_7d. Steps: Day 0 "Ask about the trip", Day 7 "Request review and referrals"

37.6 AI-Suggested Tasks ¶

The AI co-pilot (§20.4) and the customer-memory extraction (§11.2) can propose tasks based on conversation content. Examples:

  • Customer mentions in chat "my passport expires next year" → AI suggests task "Confirm exact passport expiry with [name]"
  • Conversation indicates customer is researching a specific cruise line → AI suggests task "Send [cruise line] suite category options"
  • Customer expresses concern about a sailing date → AI suggests task "Discuss alternative sail dates with [name]"

AI-suggested tasks have origin='ai_suggested' and start in status='open' with a clear marker in the UI. The agent can accept, edit, or dismiss. Dismissed suggestions are logged so the AI can learn patterns over time (per §11 memory mechanisms).

AI task suggestion is gated by ai_mode (§9.10): if a tenant has ai_mode = 'disabled', AI-suggested tasks do not appear.

37.7 Task UI ¶

37.7.1 Task list views ¶

  • "My Tasks" dashboard — default view; shows tasks assigned to the current user, grouped by due date (Overdue, Today, This Week, Later)
  • "All Tasks" (Agency-tier only) — owner view across all seats
  • Per-record task list — tasks scoped to a single contact / quote / booking, shown on that record's detail page

37.7.2 Task creation paths ¶

  • "+ Task" button on contact / quote / booking detail pages
  • Quick-add from "My Tasks" dashboard (defaults to contact_id null until agent picks a record)
  • System and sequence and AI-suggested paths described above

37.7.3 Mobile considerations ¶

The task surface is one of the highest-value features for mobile-first usage (agents check tasks between calls or while traveling). The mobile-responsive web UI must support: viewing today's tasks, marking complete, snoozing, adding a quick task. Native mobile app is out of scope for v1 per the broader spec posture.

37.7.4 Notifications ¶

The CRM nav shows a badge with the count of overdue + due-today tasks for the current user. Clicking opens the notifications panel where each due task is listed with a quick-complete action.

37.8 Sequence Management UI ¶

Tenants manage sequences in CRM settings:

  • List all sequences (active and inactive) with their trigger event and step count
  • Create new sequence via guided form (name, trigger, then add steps one at a time)
  • Edit existing sequence — changes apply to NEW runs only; in-flight runs continue with the steps captured at run-start time
  • Deactivate sequence — stops new runs; existing runs continue or are cancelled per tenant choice
  • View active runs — see which contacts/quotes/bookings currently have an active run, with the next step's task and due date

37.8.1 Step snapshot at run-start ¶

To make sequence editing safe, the step definitions are snapshotted into the run at the moment of triggering. Editing the sequence definition does not retroactively change in-flight runs. Implementation: when a task_sequence_runs row is created, the application copies the current task_sequence_steps rows into a JSONB field on the run (or a per-run snapshot table — implementation choice at build time). The delayed Inngest events use the snapshot, not the current definition.

37.9 Calendar Integration (Future Hook) ¶

Tasks with due_at can in principle be exposed as calendar events (iCal feed, Google Calendar sync). The schema supports this (due_at, due_is_all_day are calendar-compatible fields). Implementation deferred to a future phase. v1 surfaces tasks only in the CRM UI.

37.11 Calls Worth Flagging ¶

  • Inngest delayed events for long-horizon sequences. A post-cruise sequence step at "30 days after sailing" could be 18+ months out from quote creation. Inngest delayed events are reliable but the long delay means a sequence definition edit window is large. The step-snapshot pattern in §37.8.1 protects correctness; verify Inngest's supported delay maximum at build time (it's well over a year, but worth confirming).
  • Sequence cancellation race conditions. If a quote is accepted at the same moment the sequence's "follow up if not accepted" task is being created, the skip_if_status check might fire before or after the status transition commits. Use an explicit lock or check status at task-creation time (post-snapshot read of the live record), not at scheduling time.
  • System tasks producing duplicates. Without origin_reference uniqueness, the daily passport-check job could create the same task every day. Recommend a UNIQUE constraint on (tenant_id, origin, origin_reference) where origin = 'system'.
  • Email reminder volume. A tenant with hundreds of tasks could generate substantial email volume. Respect rate limits per §23.3 and consider a daily-digest option for non-urgent reminders.
  • Sequence triggers depend on event emission. Pipeline status transitions in §12 must emit the trigger events listed in §37.4.1. Build coordination: §12 implementation must emit these events; verify event names match between §12 emission code and §37 sequence definitions.
  • Template substitution safety. Simple string replace is intentional to avoid template-injection risk. Variables are populated from typed record fields, never from free-text or AI output, which keeps the substitution surface controlled.
  • Conversation-scoped tasks. Tasks can attach to conversations (the AI chat conversation thread). Useful for "AI flagged this conversation for review" cases. Verify §10 supervisor design generates these where appropriate.
