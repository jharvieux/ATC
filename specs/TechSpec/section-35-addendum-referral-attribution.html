Section 35 - Addendum — Referral Source Attribution

Status: Addendum. Lands after Part 1–9 build prompts. References existing sections by number; does not modify them in place. Schema additions augment §5, §12, and the bookings table.

Why an addendum, not a retrofit: Attribution capture is a new cross-cutting concern that touches contacts, quotes, bookings, and the platform's HTTP middleware. The existing sections are stable. The addendum lands new columns and a new table without modifying the existing schema definitions in §5.

35.1 Overview ¶

The platform captures and stores referral source attribution for every contact, quote, and booking. Attribution data answers questions like "which campaign acquired this customer?" and "which channel closed this booking?" for the §36 reporting layer.

Attribution uses three storage locations:

LocationWhat it storesMutability
contacts columnsFirst-touch attributionImmutable after contact creation
quotes / bookings columnsConversion-touch attribution: snapshot of the contact's most recent touch at the moment of quote/booking creationImmutable
attribution_touches tableRolling 10 most recent touches per contactTrigger-evicted oldest on insert

This trades full history for a bounded, queryable working set that supports first-touch reporting, last-touch (conversion) reporting, and a short backward-looking trail for investigation. Storage cost is bounded: at most 10 rows per contact in attribution_touches, regardless of how many sessions the contact has had.

35.2 Capture Mechanism ¶

35.2.1 UTM parameter parsing ¶

The platform's HTTP middleware (alongside the tenant-resolution logic in §1.4) parses standard UTM parameters from inbound URLs on every request:

  • utm_source — e.g., facebook, google, newsletter
  • utm_medium — e.g., social, cpc, email
  • utm_campaign — e.g., wave_season_2027
  • utm_content — optional ad variant or content slot
  • utm_term — optional search term

Additional captured at the same touch:

  • referrer_url — the HTTP Referer header value
  • landing_path — the URL path the user landed on

UTM values are case-preserved as-received but lowercased for indexed columns (the indexed lowercase form is used for grouping in reports; the original case is retained in a separate field for display).

35.2.2 Session attribution flow ¶

[Request arrives with utm_* params]
        │
        ▼
[Middleware extracts UTM + referrer + landing_path]
        │
        ▼
[Store in session cookie: attribution_pending]
        │
        ▼
[Anonymous browsing — no contact row yet]
        │
        ▼
[User identifies themselves (signs up / starts chat / submits form)]
        │
        ▼
[Contact row created OR existing contact resolved]
        │
        ▼
[Insert attribution_touches row for this contact with the pending UTM data]
        │
        ▼
[If contact is brand new: also populate contact.first_touch_* columns]

The session cookie holds pending attribution until a contact is created or resolved. Multiple pageviews in the same session do not create multiple touch rows — only the first UTM-bearing request in a session creates pending attribution. Subsequent UTM-bearing requests in the same session overwrite the pending attribution (last-write-wins within a session).

35.2.3 Returning visitor handling ¶

When a returning identified user lands with new UTM parameters, a new attribution_touches row is inserted for their existing contact. The contact's first_touch_* columns are NOT modified. The rolling 10-touch trigger (§35.4.2) evicts the oldest touch if the new touch is the 11th.

35.2.4 Direct visits (no UTM) ¶

Visits without any UTM parameters are recorded with utm_source = NULL and channel = 'direct' (derived per §35.5). Direct visits still produce touch rows if they are accompanied by identification events (the user signs up, chats, etc.); pure direct browsing without identification does not produce touch rows because there is no contact to attach them to.

35.3.1 First-touch immutability ¶

The first_touch_* fields on the contact are write-once at contact creation. An agent editing the contact's source via the CRM UI produces an agent_edit touch in the rolling attribution_touches table — it does NOT overwrite first_touch_*. This preserves the audit value of first-touch reporting: the original acquisition channel is never lost to subsequent edits.

If an agent or platform admin needs to correct a genuinely incorrect first-touch (rare — e.g., a misattributed bot visit was recorded first, or a UTM parameter was malformed), the correction path is restricted to platform admin via direct DB edit with mandatory audit_log entry. This is surfaced in admin tooling, not tenant UI. The friction is intentional: routine "corrections" of first-touch would undermine its analytical value.

35.4 Rolling Touch Table ¶

35.4.1 attribution_touches table definition ¶

CREATE TABLE public.attribution_touches (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  UUID NOT NULL REFERENCES public.tenants(id),
  contact_id UUID NOT NULL REFERENCES public.contacts(id) ON DELETE CASCADE,

  occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  source_origin TEXT NOT NULL
    CHECK (source_origin IN ('utm_parsed','agent_set','agent_edit','imported')),

  utm_source   TEXT,
  utm_medium   TEXT,
  utm_campaign TEXT,
  utm_content  TEXT,
  utm_term     TEXT,
  referrer_url TEXT,
  landing_path TEXT,
  channel      TEXT,

  manual_label    TEXT,    -- for agent_set / agent_edit / imported
  manual_category TEXT,
  editor_user_id  UUID REFERENCES public.users(id),   -- non-null for agent_set / agent_edit

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX attr_touches_contact_idx
  ON public.attribution_touches(tenant_id, contact_id, occurred_at DESC);

CREATE INDEX attr_touches_campaign_idx
  ON public.attribution_touches(tenant_id, utm_campaign, occurred_at)
  WHERE utm_campaign IS NOT NULL;

ALTER TABLE public.attribution_touches ENABLE ROW LEVEL SECURITY;
-- RLS policies per §5.1: auth_user_in_tenant + tenant_is_active.

35.4.2 Rolling 10-touch window via trigger ¶

CREATE OR REPLACE FUNCTION public.attribution_touches_trim_to_ten()
RETURNS TRIGGER AS $$
BEGIN
  DELETE FROM public.attribution_touches
  WHERE contact_id = NEW.contact_id
    AND id NOT IN (
      SELECT id
      FROM public.attribution_touches
      WHERE contact_id = NEW.contact_id
      ORDER BY occurred_at DESC, created_at DESC
      LIMIT 10
    );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_attribution_touches_trim
  AFTER INSERT ON public.attribution_touches
  FOR EACH ROW EXECUTE FUNCTION public.attribution_touches_trim_to_ten();

The trigger runs after every insert, deleting any rows beyond the 10 most recent for that contact. ORDER BY occurred_at DESC, created_at DESC — important because two touches could share an occurred_at value (rare but possible with fast clicking or a clock-precision tie). created_at as tiebreaker keeps the eviction deterministic.

The trigger is AFTER INSERT FOR EACH ROW. For a contact with 10 existing rows and one new insert, exactly one row is deleted. Cost is bounded and predictable: one DELETE per INSERT, scoped to a single contact via an indexed query.

35.4.3 Touch semantics ¶

EventWhat gets written

Returning identified user with new UTMINSERT to attribution_touches with source_origin='utm_parsed'. First-touch columns on contact UNCHANGED.

Booking createdSame as quote, copied to bookings.conversion_touch_* per §35.6.

35.4.4 What an edit counts as ¶

An agent edit (source_origin='agent_edit') consumes a slot in the rolling 10-touch window, same as any other touch. This is deliberate: it preserves the audit trail of who changed what and when. If an agent makes 11 corrections to a contact's source over time, the oldest correction is evicted alongside any other touch. The 10-touch limit is the hard ceiling for all touch types combined.

35.5 Channel Normalization ¶

The channel field is a normalized category derived from utm_medium (or manual_category for offline touches). The normalization map is platform-admin-managed (not tenant-managed) so that reporting categories remain stable across tenants. The map is versioned: changes to the map produce a new version, and historical touch rows retain their channel as computed at the time they were inserted (not retroactively recomputed).

utm_medium valuechannel
social, sm, social_mediasocial
cpc, ppc, paid_search, searchsearch
email, e-mail, newsletteremail
(none / direct visit / no UTM)direct
referral, partner, affiliatereferral
(manual entry / imported, default)offline
(anything else)other

Tenants can supply a manual_category override on agent_set / imported touches to override the default 'offline' channel. Examples: "phone_referral", "trade_show", "past_client_referral". These are free-text values that the platform-admin map can be extended to handle in future versions, but at v1 they are stored verbatim in manual_category and the channel field is 'offline' for all of them.

35.6.1 Population at row creation ¶

When a quote or booking row is created, the application code reads the most recent attribution_touches row for the contact and copies its values to the conversion_touch_* columns. If no attribution_touches rows exist for the contact (rare — implies a contact with first_touch columns but no touch table rows, which can happen if the contact predates this addendum), the conversion_touch_* columns are populated from the contact's first_touch_* values.

35.6.2 Quote-to-booking handoff ¶

When a quote converts to a booking (per §12.4 quote lifecycle), the booking's conversion_touch_* values are populated independently — read fresh from the contact's current most recent touch, NOT copied from the quote. This means a booking created weeks after the quote, after additional intermediate visits with new UTMs, attributes to the most recent touch at booking time. If the agent prefers the quote's attribution to carry forward (e.g., "the campaign that produced the quote should own the booking"), they can override via agent_edit on the booking.

35.6.3 Imported booking attribution ¶

For bookings imported via §34 (origin = 'imported'), conversion_touch_* is populated from whatever the contact's most recent touch is at the time of import-acceptance. If the contact is created by the same import (no prior touches), the conversion-touch values mirror the import's first-touch values (channel = 'offline' unless overridden).

35.7 Manual Entry of Source ¶

35.7.1 At contact creation ¶

The CRM contact-creation form prompts for source as a required field. The agent picks from a tenant-configurable list of categories or enters free text in manual_label. Examples of default categories shipped with new tenants:

  • Past client referral
  • Facebook
  • Instagram
  • Trade show / networking event
  • Phone walk-in
  • Email referral
  • Other

The category list lives in a new table:

CREATE TABLE public.tenant_attribution_categories (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES public.tenants(id),
  category_label TEXT NOT NULL,
  display_order INT NOT NULL DEFAULT 0,
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (tenant_id, category_label)
);

ALTER TABLE public.tenant_attribution_categories ENABLE ROW LEVEL SECURITY;

Tenants edit their category list in CRM settings. Default categories are seeded at tenant creation but can be edited/deleted/reordered.

35.7.2 Editing existing attribution ¶

The CRM exposes an "Edit source" action on:

  • Contact detail page (edits create agent_edit touches; first-touch on contact unchanged)
  • Quote detail page (edits update quotes.conversion_touch_* in place — quotes have no rolling touch table)
  • Booking detail page (edits update bookings.conversion_touch_* in place)

Every edit writes an audit_log entry per §26.5 with the prior values, new values, and editing user.

35.7.3 Permission model ¶

BYO Research tenants can SET source at contact creation but CANNOT EDIT after creation (the cheapest tier omits the editing UI to keep complexity low). All other paid tiers support both set and edit. This is a UI gating decision, not a schema constraint.

35.8 Privacy and Retention ¶

35.8.1 PII in attribution data ¶

Attribution fields contain no inherent PII — UTM values, referrer URLs, and campaign names describe how the contact found the platform, not who they are. The referrer_url field could contain personal information if the referrer happens to be a personal site (e.g., a user's own blog), but this is a rare edge case and not a PII vector that warrants special handling.

35.8.2 Deletion alongside contact ¶

When a contact is deleted per §25 data deletion rules, all associated attribution_touches rows are deleted via the ON DELETE CASCADE in the foreign key definition. The contact's own first_touch_* columns are part of the contact row itself, deleted with it. conversion_touch_* on quotes and bookings is retained even after the contact is deleted (the quote/booking is a financial record retained per §25); these columns contain no PII, only campaign metadata.

35.8.3 Cross-tenant isolation ¶

Attribution data is strictly tenant-scoped. RLS policies on attribution_touches and tenant_attribution_categories enforce auth_user_in_tenant + tenant_is_active per §5.1. A campaign run by tenant A is not visible to tenant B even if both happened to use the same utm_campaign string.

35.10 Calls Worth Flagging ¶

  • Attribution_touches grows linearly with engaged contacts. Capped at 10 per contact by the trigger. For a tenant with 10,000 contacts, max 100,000 rows. Well within Postgres comfort zone. Index on (tenant_id, contact_id, occurred_at DESC) handles the trigger's subquery efficiently.
  • Trigger correctness under fast successive inserts. Two touches inserted in the same millisecond could share occurred_at. The created_at tiebreaker in the ORDER BY makes eviction deterministic, but the "10 most recent" definition depends on physical insert order, not logical session order. In practice this is fine — the user wouldn't notice — but worth knowing during debug.
  • Platform-admin first-touch correction is direct DB edit + audit_log entry. Clunky but acceptable for an edge case. If correction requests exceed ~2/month across all tenants, a small admin UI is worth building.
  • Multi-touch journey ambiguity. First-touch and last-touch don't capture multi-touch attribution models (linear, time-decay, U-shape). The rolling 10-touch table contains the data to support custom multi-touch attribution in future, but no calculation is provided in v1. §36 reports use first-touch and conversion-touch only.
  • Cookie persistence and privacy. The session cookie holding pending attribution must respect any active cookie-consent posture. §17 consent flow should set a flag controlling whether pending attribution is set; if consent is refused, the attribution is discarded and direct/no-source treatment applies.
  • UTM spoofing. An adversary could craft URLs with arbitrary utm_* values to skew a tenant's reporting. Low-impact issue — the worst case is a tenant's own reports being misleading, not a security breach. No mitigation in v1; flag for future if abuse is observed.
  • Channel map versioning is described but the storage isn't specified here. Recommend adding a small platform-admin table attribution_channel_map_versions and storing the map_version_id on each touch row in a future iteration. Out of scope for v1 because the default map will not change frequently.
