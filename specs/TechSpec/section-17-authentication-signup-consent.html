17.2 Microsoft No-Email Handling ¶

Personal Microsoft accounts often don’t expose email in OAuth claims. Email extraction chain:

  • oauth.email (work accounts and most personal)
  • Microsoft Graph API /me.mail (work accounts especially)
  • Microsoft Graph API /me.otherMails[0] (personal accounts with alternate)
  • Prompt user for email BEFORE account creation
NOTE: Cannot screen-scrape Microsoft’s login form — that’s behind OAuth security boundary on Microsoft’s domain. The platform never sees what the user typed.

Email is HARD-REQUIRED at signup. If none found via OAuth + Graph, user enters email on a prompt screen before public.users row is created. Schema keeps users.email NOT NULL; the complexity is in the flow.

17.4 Versioned Consent System ¶

CREATE TABLE public.legal_documents (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

document_type TEXT NOT NULL CHECK (document_type IN (

‘tou’,‘privacy_policy’,‘ai_disclaimer’,‘cookie_policy’,

‘ica_subhost’,‘can_spam_addendum’,‘tcpa_addendum’

)),

version INTEGER NOT NULL,

content_markdown TEXT NOT NULL,

content_html TEXT,

summary_of_changes TEXT,

effective_at TIMESTAMPTZ NOT NULL,

superseded_at TIMESTAMPTZ,

created_by_user_id UUID REFERENCES public.users(id),

created_at TIMESTAMPTZ DEFAULT NOW(),

UNIQUE (document_type, version)

);

CREATE TABLE public.legal_consents (

id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

auth_user_id UUID REFERENCES auth.users(id),

tenant_id UUID REFERENCES public.tenants(id), – nullable for platform-level docs

document_id UUID NOT NULL REFERENCES public.legal_documents(id),

document_type TEXT NOT NULL,

document_version INTEGER NOT NULL,

action TEXT NOT NULL CHECK (action IN (‘accepted’,‘declined’,‘withdrawn’)),

ip_address TEXT,

user_agent TEXT,

notes TEXT, – for ICA: typed legal name as signature

acted_at TIMESTAMPTZ DEFAULT NOW()

);

Platform-level documents (ToU, Privacy, AI Disclaimer) accepted once per auth.users globally — not per tenant. Tenant-specific documents (ICA) accepted per tenant relationship.

17.5 Document Version Change Flow ¶

Platform admin publishes new version via /admin/legal-docs. On publish:

  • New legal_documents row inserted with effective_at = NOW (or scheduled)
  • Previous version’s superseded_at set
  • Users with latest_accepted_version < new_version flagged
  • On next authenticated request → redirect to /consent?missing=…
  • Email blast to affected users with change summary

17.6 AI Liability Disclaimer ¶

Distinct legal document separate from ToU. Acknowledges:

  • AI is a tool, not a licensed travel agent
  • AI may make mistakes; verify pricing and policies before booking
  • Platform not responsible for AI hallucinations or errors
  • Final booking confirmation comes from human/host system, not AI
  • State-specific AI disclosure requirements (California, Illinois, Utah, New York)

Disclaimer banner persistent in chat: ‘This conversation may include AI-assisted responses.’

17.7 Session Management ¶

  • Supabase Auth handles JWT issuance and refresh
  • Access token TTL: 1 hour
  • Refresh token TTL: 30 days with sliding window
  • Re-auth required after 4 hours for sensitive operations (commission overrides, role changes, ICA acceptance)

17.9 CCPA Data Export ¶

GET /api/user/data initiates export. Inngest job assembles. User receives email with signed download URL (24-hour validity). Rate-limited: 1 export per user per 30 days.

17.10 CCPA Data Deletion ¶

DELETE /api/user/data with confirmation. Sets status = 'deleted', deleted_at = NOW(). 30-day grace period for recovery. After 30 days: data purged per retention; required-retention records (bookings, commissions) anonymized per §25.4 and §25.4a.

Staging propagation

Customer deletions propagate to staging via the next release pipeline run (which restores staging from production data per CI/CD §5). With release cadence of <30 days, propagation falls within the 30-day grace period.

If release cadence stalls (freeze for major release planning), manual staging cleanup may be required to maintain CCPA compliance. The trigger:

  • Customer deletion was performed in production.
  • 25+ days have elapsed since the deletion (5-day safety margin before 30-day grace + 15-day reporting buffer = 45-day CCPA SLA).
  • No release pipeline run has refreshed staging in those 25+ days.

The operator's runbook: run scripts/staging-fixups.sql against staging with an additional purge clause for the specific deleted_user_id. Documented in CI/CD spec §9.5.

Why this works under Option B (D-038)

The Option B staging posture has reduced forensics (no PITR, no daily backups). Side effect: there's no historical staging state where the customer's data lives — the only copy is on the current staging instance. A targeted purge on that instance satisfies the propagation requirement; there's no backup to also purge.

Under Option A or Option C (if upgrade is triggered), additional purge of backed-up staging state would be required.
