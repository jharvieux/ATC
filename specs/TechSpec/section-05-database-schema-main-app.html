5.1.X Hard-delete protection for tenants ¶

Tenants are soft-terminated, not deleted. The combination of FK ON DELETE RESTRICT (above) and a hard-delete prevention trigger makes accidental hard delete structurally difficult.

-- Prevent accidental hard DELETE on tenants. Tenant termination
-- uses status = 'terminated' (per §15.14), not row deletion.
-- Hard delete requires explicit override via a session-level flag.

CREATE OR REPLACE FUNCTION public.prevent_tenant_hard_delete()
RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = ''
AS $$
BEGIN
  IF current_setting('app.allow_tenant_hard_delete', true) = 'true' THEN
    RETURN OLD;
  END IF;
  RAISE EXCEPTION 'Hard delete of tenants is not permitted. Use status = ''terminated'' instead. To override (e.g., for compliance hard-delete after data retention period), execute SET app.allow_tenant_hard_delete = ''true'' in the same transaction.';
END;
$$;

CREATE TRIGGER tenant_prevent_delete_trigger
  BEFORE DELETE ON public.tenants
  FOR EACH ROW
  EXECUTE FUNCTION public.prevent_tenant_hard_delete();

Override pattern for legitimate hard delete (GDPR Right-to-be-Forgotten after retention period, or compliance with regulatory order):

BEGIN;
SET LOCAL app.allow_tenant_hard_delete = 'true';
DELETE FROM public.tenants WHERE id = '<uuid>';
COMMIT;

The SET LOCAL ensures the override is transaction-scoped — it does NOT persist to subsequent transactions or other sessions.

Operators performing legitimate hard delete:

  1. Verify retention obligations have been met (audit log review).
  2. Document the delete in MEMORY.md with reason and timestamp.
  3. Execute with the override pattern shown above.
  4. Verify cascading cleanup of related rows (commissions, bookings, etc. — these have ON DELETE RESTRICT so the DELETE will fail until those rows are individually removed or also overridden).

This is intentionally friction-heavy. Hard-delete of a tenant should require deliberate action, not be a side effect of a script or admin tool.

RLS Helper Functions

The platform uses two helper functions in RLS policies. Both are SECURITY DEFINER with a locked search_path to prevent the canonical Postgres privilege-escalation pattern (an attacker creating a same-named table/function in a schema the function might resolve against). Every SECURITY DEFINER function in the platform follows this convention — see §5.1.1 below.

auth_user_in_tenant(target_tenant_id UUID)

Returns TRUE if the authenticated user has an active row in the named tenant. Used in row-level policies that scope SELECT/UPDATE/DELETE to the caller's tenant.

CREATE OR REPLACE FUNCTION public.auth_user_in_tenant(target_tenant_id UUID)
RETURNS BOOLEAN
LANGUAGE SQL
SECURITY DEFINER
STABLE
SET search_path = ''
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.users
    WHERE auth_user_id = auth.uid()
      AND tenant_id   = target_tenant_id
      AND status      = 'active'
  );
$$;

REVOKE EXECUTE ON FUNCTION public.auth_user_in_tenant(UUID) FROM public;
GRANT EXECUTE ON FUNCTION public.auth_user_in_tenant(UUID) TO authenticated;

This function does NOT check tenant status. It answers only the question "is this user a member of this tenant?" Use tenant_is_active (below) when the policy also needs the tenant to be operational.

tenant_is_active(target_tenant_id UUID)

Returns TRUE if the named tenant is in a state that permits user-initiated writes. Used in tandem with auth_user_in_tenant on write policies.

CREATE OR REPLACE FUNCTION public.tenant_is_active(target_tenant_id UUID)
RETURNS BOOLEAN
LANGUAGE SQL
SECURITY DEFINER
STABLE
SET search_path = ''
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.tenants
    WHERE id     = target_tenant_id
      AND status = 'active'
  );
$$;

REVOKE EXECUTE ON FUNCTION public.tenant_is_active(UUID) FROM public;
GRANT EXECUTE ON FUNCTION public.tenant_is_active(UUID) TO authenticated;

Tenants in suspended, terminated, pending_review, or onboarding status return FALSE. This blocks user-initiated writes at the database layer even if the application-layer permission check is skipped or buggy.

System-initiated writes (Stripe webhooks, Inngest jobs running under service-role context) do NOT go through these RLS policies — they bypass RLS by definition. The discipline for service-role usage is defined in §26.3a.

Policy authoring convention

Read policies (SELECT) use auth_user_in_tenant alone — a user can read their data from a suspended tenant (e.g., to download historical bookings before termination) but cannot write to it.

Write policies (INSERT, UPDATE, DELETE) use BOTH:

-- Example: bookings policy
CREATE POLICY bookings_write_policy ON public.bookings
  FOR ALL
  USING (auth_user_in_tenant(tenant_id))
  WITH CHECK (auth_user_in_tenant(tenant_id) AND tenant_is_active(tenant_id));

The USING clause governs visibility; the WITH CHECK clause governs writes. A user in a suspended tenant can SELECT their historical bookings but cannot INSERT new ones.

5.1.1 Convention for all SECURITY DEFINER functions ¶

Every SECURITY DEFINER function in the platform — including any helper added in future migrations — MUST:

  1. Set SET search_path = '' in the function definition.
  2. Fully qualify every table/function reference (public.users, not users).
  3. Be created in the public schema (so the security boundary is clear).
  4. REVOKE EXECUTE FROM public after creation, then GRANT EXECUTE to the specific role that needs it (typically authenticated).

Migrations that introduce a SECURITY DEFINER function without these four steps fail the migration lint gate per §30.8.

5.1.2 Required RLS Policy Coverage ¶

Every tenant-scoped table in this section MUST have RLS enabled AND policies covering all four operations (SELECT, INSERT, UPDATE, DELETE). A table with RLS enabled but missing policies for one or more operations is a tenant-isolation hole — Postgres denies the uncovered operation entirely (no rows visible, no writes possible), which engineering will be tempted to "fix" by disabling RLS.

The minimum policy set for every tenant-scoped table:

ALTER TABLE public.<table_name> ENABLE ROW LEVEL SECURITY;

CREATE POLICY <table>_select_policy ON public.<table_name>
  FOR SELECT
  USING (auth_user_in_tenant(tenant_id));

CREATE POLICY <table>_insert_policy ON public.<table_name>
  FOR INSERT
  WITH CHECK (
    auth_user_in_tenant(tenant_id)
    AND tenant_is_active(tenant_id)
  );

CREATE POLICY <table>_update_policy ON public.<table_name>
  FOR UPDATE
  USING (auth_user_in_tenant(tenant_id))
  WITH CHECK (
    auth_user_in_tenant(tenant_id)
    AND tenant_is_active(tenant_id)
  );

CREATE POLICY <table>_delete_policy ON public.<table_name>
  FOR DELETE
  USING (
    auth_user_in_tenant(tenant_id)
    AND tenant_is_active(tenant_id)
  );

Tables that legitimately deviate from this pattern (e.g., platform-admin tables like host_adapters, legal_documents, tier_definitions that are not tenant-scoped) require explicit documentation in db/rls-snapshot.sql (per §30.8) with a comment explaining the exception.

Deviation: read-only-after-suspension behavior

The policy set above lets a user in a suspended tenant SELECT their data but blocks writes. This is the default. Tables that should block reads from suspended tenants too (e.g., active conversation context, where reading the suspended tenant's data is misleading rather than helpful) override with:

CREATE POLICY <table>_select_policy ON public.<table_name>
  FOR SELECT
  USING (
    auth_user_in_tenant(tenant_id)
    AND tenant_is_active(tenant_id)
  );

The choice is per-table and documented in the table's DDL comment.

Enforcement

§30.8's RLS policy snapshot diff is extended to also assert:

  • Every table with a tenant_id column has RLS enabled.
  • Every such table has at least one policy for each of SELECT, INSERT, UPDATE, DELETE (or is explicitly listed in the exception file).
  • No policy uses USING (true) or WITH CHECK (true) — these are no-op policies that defeat RLS.

Migrations that violate these rules fail the gate. See §30.8.

5.4 Database Access Patterns ¶

The schema in §5.1–§5.3 (and the RAG schema in §6) is multi-tenant. Tenant isolation is enforced at three layers — RLS, application-layer permission check, and a typed TenantContext boundary at the data-access layer. This subsection defines the third layer, which exists to keep the other two layers honest.

Without this layer, every code path that uses the service-role key silently bypasses RLS, and tenant isolation reduces to "did the developer remember to put tenant_id in the WHERE clause." That has been a recurring bug shape in multi-tenant SaaS history. The TenantContext pattern below makes the boundary explicit in TypeScript types and makes raw service-role usage a clearly-named anti-pattern that lint can catch.

5.4.1 The three database client kinds ¶

The platform has exactly three database client patterns. Code at any level must pick one consciously.

Client kindUse caseAuthority
userClient(req)Any code path serving an authenticated user requestUses the user's JWT; subject to RLS
tenantClient(ctx: TenantContext)Background jobs, webhook handlers, or admin paths that act on behalf of a specific tenantService role under the hood, but every query is filtered by ctx.tenant_id in a wrapper
platformAdminClient()Strictly platform-admin operations crossing tenant boundaries (e.g., the global RAG promotion queue)Raw service role with no scoping

userClient is the default for HTTP handlers. tenantClient is the only correct client for Inngest jobs and webhook handlers acting on one tenant. platformAdminClient is rare, named, and audited.

5.4.2 The TenantContext type ¶

// src/lib/db/tenant-context.ts (path indicative)

export type TenantContext = {
  tenant_id: string;
  // Source of the context — recorded for audit. Cannot be derived in code.
  source:
    | { kind: 'http_request'; user_id: string }
    | { kind: 'stripe_webhook'; stripe_event_id: string }
    | { kind: 'inngest_job'; function_name: string; event_id: string }
    | { kind: 'platform_admin'; admin_user_id: string; reason: string };
};

A TenantContext carries tenant_id plus a provenance — where the context was constructed and under whose authority. The provenance is required, audited in the database client wrapper, and prevents "context laundering" (a function receiving a TenantContext from one source and using it in a way that doesn't belong to that source).

5.4.3 The tenantClient wrapper ¶

// src/lib/db/tenant-client.ts (path indicative)

export function tenantClient(ctx: TenantContext) {
  const supabase = createServiceRoleClient();

  // Wrap from() so every query is automatically scoped.
  return new Proxy(supabase, {
    get(target, prop) {
      if (prop === 'from') {
        return (table: string) => {
          // Tables NOT in the tenant-scoped allowlist still go raw —
          // explicit list in db/tenant-scoped-tables.ts.
          if (!TENANT_SCOPED_TABLES.has(table)) {
            return target.from(table);
          }
          // For tenant-scoped tables, transparently inject the filter.
          return target.from(table).eq('tenant_id', ctx.tenant_id);
        };
      }
      return Reflect.get(target, prop);
    },
  });
}

What this gets us:

  1. Every query against a tenant-scoped table is automatically filtered by tenant_id. A developer cannot forget the filter — the wrapper applies it before the query reaches Postgres.
  2. Raw service-role usage is a separate, named function (createServiceRoleClient()). It exists but is rare and only invoked inside tenantClient or platformAdminClient. Direct calls from handler code are caught by the lint rule in §29.

5.4.4 The lint rule ¶

A CI lint rule (per §29) enforces:

  • createServiceRoleClient cannot be called outside src/lib/db/tenant-client.ts and src/lib/db/platform-admin-client.ts. Any other call site fails the build.
  • tenantClient requires a TenantContext argument typed exactly. Constructing a TenantContext requires going through one of four named factory functions, one per provenance kind (see §5.4.5).
  • Raw Supabase URL usage is forbidden outside the three client factories.

The lint runs in every PR. The gate is hard (red CI = no merge).

5.4.5 TenantContext factory functions ¶

Constructing a TenantContext is restricted to four named factories, one per provenance kind. This is where the provenance metadata gets attached and where the authority-to-act check happens.

// HTTP request — derives tenant from middleware-resolved tenant +
// validates user belongs to it. Called by assertPermission() per §26.3.
export async function tenantContextFromRequest(req: Request): Promise<TenantContext>;

// Stripe webhook — derives tenant from the event's metadata or by
// looking up the stripe_customer_id. Validates the event is for a
// known tenant.
export async function tenantContextFromStripeEvent(event: Stripe.Event): Promise<TenantContext>;

// Inngest job — derives tenant from the job's event payload, which
// MUST include tenant_id. Jobs that don't have a tenant_id in their
// event use platformAdminClient instead.
export async function tenantContextFromInngestEvent(event: InngestEvent): Promise<TenantContext>;

// Platform admin — explicit, requires admin user identity and a
// reason string for audit. The reason is recorded in audit_log.
export async function tenantContextForPlatformAdmin(
  admin: { user_id: string },
  target_tenant_id: string,
  reason: string,
): Promise<TenantContext>;

Each factory is responsible for:

  • Verifying the caller has authority to construct a context for the named tenant_id.
  • Attaching the right source discriminant.
  • Recording the context construction to audit_log for the stripe_webhook and platform_admin cases (high-trust paths).

5.4.6 What the application code looks like ¶

// HTTP handler
export async function POST(req: Request) {
  const { ctx, user } = await assertPermission(req, {
    resource: 'booking',
    action: 'submit',
  });
  // ctx is a TenantContext sourced from http_request.
  const db = tenantClient(ctx);
  // db.from('bookings') is automatically scoped by tenant_id.
  await db.from('bookings').insert({ ... });
}

// Inngest job
export const handleCommissionPayout = inngest.createFunction(
  { id: 'commission-payout' },
  { event: 'commission.payout.requested' },
  async ({ event }) => {
    const ctx = await tenantContextFromInngestEvent(event);
    const db = tenantClient(ctx);
    // Same scoping discipline as HTTP — same client surface, same safety.
    const commissions = await db.from('commissions').select('*');
    // ...
  },
);

// Platform admin (rare)
export async function GET(req: Request) {
  const admin = await assertPlatformAdmin(req);
  const db = platformAdminClient(); // No tenant scoping. Audited heavily.
  const allTenants = await db.from('tenants').select('*');
  // ...
}

5.4.7 Calls Worth Flagging ¶

  • The Proxy trick in tenantClient is the architectural centerpiece. It works because every Supabase query goes through .from(table). If the codebase later adds raw SQL execution paths (.rpc(), .from('arbitrary_sql_function')), those paths must either be added to the proxy's scoping logic or be moved to platformAdminClient.
  • The lint rule is non-optional. Without it, an engineer in a hurry imports createServiceRoleClient directly and the type-system protection is gone. The lint is the enforcement; the type is the design.
  • Provenance metadata is what makes audit useful. A bug investigation asking "who constructed a TenantContext for tenant X at time Y" needs the source field to answer. Skipping the audit on context construction breaks the forensic chain.
  • tenantClient does not invoke RLS — it uses service role under the hood. Defense in depth: the application enforces scoping via the proxy AND the database has RLS as a backstop. Either layer alone is insufficient; both together are the design.

5.4.8 Platform-Admin Audit Wrapper ¶

The withPlatformAdminAudit utility is the single supported way to construct a platformAdminClient. It manages the per-job audit row that §26.3a.3 requires.

// src/lib/db/platform-admin-client.ts (path indicative)

type PlatformAdminAuditOptions = {
  admin_user_id: string;
  reason: PlatformAdminReason;  // Typed enum — see platform-admin-reasons.ts
  operation: string;            // Function name, e.g., 'platformAdminListTenants'
  request_context?: {           // Optional HTTP context for ip/user_agent recording
    ip?: string;
    user_agent?: string;
    request_id?: string;
  };
  reason_detail?: string;       // Required ONLY when reason = 'manual_emergency_intervention'
};

type QueryRecord = {
  op: 'select' | 'insert' | 'update' | 'delete' | 'rpc';
  table: string;
  columns?: string[];
  row_count?: number;
  rpc_name?: string;
};

export async function withPlatformAdminAudit<T>(
  options: PlatformAdminAuditOptions,
  fn: (
    db: SupabaseClient,
    recordQuery: (q: QueryRecord) => void,
  ) => Promise<T>,
): Promise<T> {
  // Nested-call detection (per §26.3a.3 "What 'one job' means")
  if (isInsidePlatformAdminAudit()) {
    // Reuse outer context — same db client, same recordQuery
    const outer = currentPlatformAdminAuditContext();
    return fn(outer.db, outer.recordQuery);
  }

  const correlation_id = generateULID();
  const start = performance.now();
  const queries: QueryRecord[] = [];

  const db = createServiceRoleClient();
  const recordQuery = (q: QueryRecord) => queries.push(q);

  let outcome: 'success' | 'error_thrown' = 'success';
  let error_message: string | null = null;
  let result: T;

  // Enforce reason_detail for the emergency escape hatch
  if (options.reason === 'manual_emergency_intervention' && !options.reason_detail) {
    throw new Error(
      'withPlatformAdminAudit: reason_detail is required when reason is ' +
      '"manual_emergency_intervention". This is a deliberate friction.',
    );
  }

  try {
    result = await runInsidePlatformAdminAudit(
      { db, recordQuery, correlation_id },
      () => fn(db, recordQuery),
    );
    return result;
  } catch (err) {
    outcome = 'error_thrown';
    error_message = err instanceof Error ? err.message : String(err);
    throw err;
  } finally {
    // Audit row commits regardless of success/failure
    const duration_ms = Math.round(performance.now() - start);
    await writeAuditRow({
      tenant_id: null,
      actor_user_id: options.admin_user_id,
      actor_type: 'admin',
      action: `platformAdmin.${options.reason}`,
      resource_type: 'platform_admin_operation',
      resource_id: null,
      changes: {
        correlation_id,
        operation: options.operation,
        reason: options.reason,
        reason_detail: options.reason_detail ?? null,
        outcome,
        duration_ms,
        queries,
        error_message,
      },
      context: options.request_context ?? {},
    });
  }
}

Implementation notes

  • isInsidePlatformAdminAudit() and runInsidePlatformAdminAudit() use Node's AsyncLocalStorage (or equivalent) to track whether the current async context is already inside an audit wrapper. This is what makes nesting safe and idempotent.
  • The audit row write uses a separate, dedicated database client (NOT db from the wrapped function's scope) so an audit-row write doesn't participate in any transaction the wrapped function may have started. Audit row commits even if the wrapped function's database work was rolled back.
  • recordQuery is intentionally lightweight — it pushes a small object onto an in-memory array. It does NOT perform any database I/O of its own. Engineers can call it freely without worrying about audit latency dominating the operation.
  • recordQuery invocation is voluntary, NOT mandatory. A platformAdmin* function that uses db without recording any queries produces an audit row with changes.queries = []. This is a deliberate design choice: read-only check operations ("does this tenant exist?", "is this admin permission still valid?") should not be forced to inflate the audit row. The audit row itself — the fact that the function ran, with what reason, by which admin, at what time — is the primary forensic value. The query summary is a useful enrichment when present but is not required to make the audit row meaningful.

Future engineers may be tempted to make recordQuery mandatory via a runtime assertion at audit-write time ("the queries array is empty, throw an error"). DO NOT make this change. It creates friction for legitimate use cases and produces audit-write failures inside finally blocks, which is the worst failure ergonomics in the stack.

  • The lint rule in §5.4.4 is extended to forbid platformAdminClient() or createServiceRoleClient() calls outside this utility's body. The only way to get a platformAdminClient is through withPlatformAdminAudit. There is no escape hatch.

Reason values are a closed enum

The reason field on withPlatformAdminAudit is typed as PlatformAdminReason, a union of string literals defined in src/lib/db/platform-admin-reasons.ts. Adding a new reason requires:

  1. Edit platform-admin-reasons.ts to add the value to the enum.
  2. Document the new reason's intent in a comment alongside the enum value.
  3. Pass code review — see §26.11 quarterly review.

The enum exists for three reasons:

  • Forensic vocabulary stays bounded. Investigations against audit_log filter on action = 'platformAdmin.<reason>'. A closed enum keeps that filter predictable.
  • Spelling drift is impossible. Free-text reasons inevitably produce tenant_listing_for_admin_dashboard AND tenant_listing_for_dashboard AND tenant_listing — three variants for one operation. The enum eliminates this.
  • New reasons get reviewed. Adding a new reason is a PR that a reviewer sees, not a string literal someone types into a handler. This is the discipline that keeps platform-admin operations visible.

The manual_emergency_intervention value is a deliberate escape hatch for incident response. When used:

  • reason_detail is REQUIRED (the type enforces this at the call site — a future small refinement is a discriminated union; for now the runtime check in withPlatformAdminAudit enforces it).
  • A MEMORY.md entry MUST be added in the same PR (or, for during-incident use, by the end of the incident).
  • The incident postmortem references the audit row's correlation_id.

This escape hatch exists so engineering can act in emergencies without first writing a new enum value. Its use should be rare — target zero in a healthy quarter.

Calling convention

Every platformAdmin* function:

  1. Calls assertPlatformAdmin(req) at entry to verify admin identity.
  2. Wraps the rest of the function body in withPlatformAdminAudit(...).
  3. Inside the wrapped body, calls recordQuery(...) for each meaningful database operation.

A platformAdmin* function that does NOT use withPlatformAdminAudit is a lint failure (the lint rule sees a function name matching ^platformAdmin that doesn't contain a withPlatformAdminAudit call in its body).
