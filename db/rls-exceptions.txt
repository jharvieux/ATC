#
# Format: one entry per line as `table_name # reason`
#
# Tables listed here are exempt from the migration lint gate's requirement
# that every tenant_id-bearing table have RLS enabled plus a policy for
# each of SELECT, INSERT, UPDATE, DELETE (per spec §5.1.2 and §30.8).
#
# Only add a table here when the deviation is intentional and reviewed.
# Each entry MUST include a reason.
#
# Examples (illustrative, not active):
#   host_adapters # platform-admin table, not tenant-scoped despite carrying tenant_id
#   audit_log_partitions # append-only, INSERT-only by service role

stripe_webhook_events # tenant_id is nullable (NULL for platform-level events, non-null for Connect tenant events). INSERT/UPDATE/DELETE are exclusively via service_role webhook handlers, which bypass RLS by design per §5.4.1. User-facing SELECT policy restricts visibility to tenant_id IS NOT NULL rows only.
pending_rag_sync # platform-internal retry queue; no user-facing access paths. All reads and writes are via service_role (Inngest cron + publishTenantEvent fallback). No authenticated-user policies needed per §8.7a.
supervisor_review_queue # platform-internal review queue; SELECT/UPDATE for platform admins only via withPlatformAdminAudit (service_role), INSERT by supervisor sampling path (service_role), DELETE by retention purge (service_role). No authenticated-user policies per §10.5a design.
host_booking_fee_configs # platform-scoped (no tenant_id column). SELECT to authenticated (tenants can read fee catalog). INSERT/UPDATE/DELETE service_role only (platform admin). Per §12.6 design.
host_adapters # platform-scoped adapter registry (no tenant_id column). SELECT to authenticated so tenants can browse adapters. INSERT/UPDATE/DELETE service_role only (platform admin). Per §13.3.
